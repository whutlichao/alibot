# 自动续跑：受派者用结构化动作申请，编排落一条记录再唤醒同一人，每世代有界

用户于 2026-10-20 报「接完任务后不会自己接着干」：认领轮回复一句「我会继续补全…」，任务停在
`in_progress`，此后再没有任何一轮。正文里的承诺没有执行面——本 ADR 记录这次裁定、执行面落在哪里、
以及它**不**扩展到什么。

## 背景：「唤醒的扳机」只有消息落库，而 Agent 自己的消息唤不醒自己

ADR-0016 把认领扩成开工动作后，「任务不会开始」在**状态面**已经修好（`todo → in_progress`、两条可读
记录、必答轮）。但「开始之后不会继续」是另一件事，且是既有机制的**结构性**结果，不是某个分支写错：

1. **唤醒的唯一扳机是消息落库之后的 `notify`**（ADR-0017 的构造性前提）。一轮结束时的落库点是
   `_commit_reply`：它调用 `notify`，而 `notify` 的第一件事是**排除作者**——唤醒面是「该 target 的
   Agent 成员 **减去**作者」。
2. **单 Agent 的任务线程因此零唤醒**：认领者回复之后，`_wake_targets` 为空，没有任何下一轮；
   也没有第二个扳机——用户没有发消息，任务行没有变化，提醒到点只落 `system`（不唤醒）。
3. **模型看不到自己的上一轮**：一轮是一次模型调用的**新实例**，输入只有「游标之后的新消息」且再次
   排除作者。哪怕有下一次唤醒，它也无从接上「我上一轮做到哪了」。

现场读数（用户任务线程）：`已认领 → 认领后自动开工 → Agent 回复（末尾「我会继续补全…」）` 之后，
`round_outcome` 只有一条 `replied`，线程再无新消息；任务保持 `in_progress`，`target_budget.used = 0`。

## 一、续跑是**受派者显式申请**的结构化动作，不是编排的猜测

新增类型化动作 **`ContinueTaskAction`**（`continue_task` 工具，只在任务线程、且只在**本轮 Agent 就是
受派者**时挂出）：本轮结束时模型用它声明「这张任务还没干完，请再叫我一轮」。它**不改任务行**，
与 `set_task_status` / `transfer_task` 同一条收集路径（每轮最多一个动作，写入仍由编排授权）。

**为什么不是正文里的「我会继续」**：正文是 append-only 的对话事实，不是执行请求。从正文里解析
承诺（关键词 / 「下一步」标题）会把措辞变成协议，且模型换一种说法就失效——那正是本次现场发生的事。

**为什么不是编排无条件续跑**：编排没有「干完了没有」的事实。无条件续跑会在一张**正在等人回答**的
任务上继续烧模型调用，而模型唯一的停机方式变成「改任务状态」——那会逼它把「我在等你确认」写成
`待审`，把协作事实写错。由模型在轮次收口时显式申请，才是「接着干」与「干完了 / 在等人」的分界线。

## 二、续跑仍以「一条消息」为载体：先落 `system.task.continue`，再唤醒

唤醒的构造性前提不变（ADR-0017）：**没有消息就没有唤醒**。编排在受派者申请之后：

```text
本轮收口（in-flight 已清掉）
  任务仍在 in_progress、受派者仍是本轮 Agent、非 team、Agent 可用
  世代轮数未到上限
    落 system「自动续跑：受派者申请继续推进这张任务」  ← 新键 system.task.continue
    以它的 seq 投递一轮（reason=continue，signal=CONTINUE，history=True，不计跳）
  世代轮数已到上限
    落 system「自动续跑已暂停：… 发一条消息可继续」    ← 新键 system.task.continue_paused
```

- **投递必须在 in-flight 清掉之后**：同成员同 target 的新一轮若在收口前投递，会被既有的「重复唤醒
  合并」当成 merged 吞掉——续跑当场消失。落点在 `run_round` 的 `finally`（与 deferred 轮次同一个
  位置、同一把锁）。
- **`system` 记录的作者恒为 owner**：这是**系统事件消息**的既有口径（ADR-0016 三），不表示人推的；
  「受派者自己申请」由词条键表达，不由 author 表达。
- **续跑轮是确定信号**：新增 `ReplySignal.CONTINUE`（与 `claim` 同级、来源不同）。它的提示词来源句是
  「本轮由自动续跑唤醒：上一轮你申请继续推进这张任务」，可读文案是 `reason.continue_*`——复用认领
  那套会写下「编排把这张任务交给你」，而那是上一轮已经发生过的事。沉默 / 自判忽略 / 无正文无动作
  照既有判据收口成 `failed`。

## 三、续跑轮看**整个任务线程**（含自己的历史回复）

`run_round` 的输入口径按轮次分叉：普通轮次仍只喂「游标之后、且不是自己」的新消息（一字不变）；
**续跑轮**（`history=True`）把该 target 的整个消息流交给接缝，接缝把**作者就是本轮 Agent** 的那些
消息按 `assistant` 角色回传。否则续跑轮会从零重做上一轮的产出，看起来像「重复劳动」而不是「继续」。

`mentions` 与 `base_seq` **只看本轮新消息**：历史里的旧点名不能把续跑轮改判成「被个人提及」。
`system` 记录（含自己的历史回复之外的 system）仍按 user 消息送入，与既有形状一致。

## 四、每世代有界：读 `round_outcome` 计数，不新增 DDL

一轮续跑要花一次模型调用，因此必须有界。上限落在**「本次人类世代内，受派者在这张任务上最多跑几轮」**：

- `TASK_CONTINUE_ROUNDS = 3`（续跑轮数），`TASK_WORK_ROUNDS_PER_EPOCH = 1 + 3 = 4`（含第一轮 /
  认领轮）。到上限后不再投递，落一条可读的暂停记录——不停在一个没人解释的静默里。
- 计数读 `round_outcome`：`base_seq >= target_budget.epoch_seq`、`member_id = 受派者`、`merged = 0`。
  它是**持久事实**（跨重启一致）、不依赖 locale，因此不需要为新计数器加列，也不 bump
  `SCHEMA_VERSION`（沿用 ADR-0016 六的处置：这不是库形态变更）。
- **世代**沿用既有口径：人类消息 / owner 改派 / 首次认领开世代。用户再发一条消息 ⇒ 新一轮上限额度；
  「续跑被暂停」因此是一条**可操作**的事实（发一句话就能继续），不是死路。

## 五、续跑不是跳，`target_budget.used` 一字不动

`CONTEXT.md` 的**跳**定义是「一条 **Agent 消息**投递了至少一个唤醒给**其它** Agent」。续跑轮的载体是
`system` 记录、被唤醒的是**同一个人**，两条都不满足。因此它**不消耗**跳数，也不复用预算上界：上限是
上面那个独立常量。把「续跑」记进 `used` 会把「一次跳投递了几个成员」的计量口径搅成第三种量，
而 `used` 是预算压制的唯一正本——不做。

## 六、team 任务线程不提供续跑

team 的 task target 只唤醒队长（ADR-0022）：受派者可能是普通成员，续跑会绕开那条裁决。因此
`TaskActionContext.allow_continue` 在 team 下为假——**工具不挂、提示词不出现**，行为逐字不变。
队长自己的任务线程是否该有续跑，属于下一次产品决策，本 ADR 不替它开口子。

## 七、与既有 ADR 的关系

- **ADR-0002（三跳上界）**：不变。续跑不计跳，也不开世代；「续跑 → 用满 → 再续跑」不可达（续跑由
  模型申请、每世代有硬上限，且不会重置 `used`）。
- **ADR-0010 / ADR-0016（认领）**：不变。认领仍是一次性开工动作；续跑是**开工之后**的轮次，不改
  `claimed_at`、不重开世代、不重提认领记录。
- **ADR-0017（提醒到点落 `system`、不唤醒）**：不变。续跑的唤醒不是「system 消息自动唤醒」——
  编排在**同一个动作**里显式投递，与提醒的「只落消息」边界不同；那条边界仍是「到点本身不构成唤醒」。
- **ADR-0022 / ADR-0025（team）**：不变，且本 ADR 显式不覆盖 team。
- **ADR-0015（迁移）**：不 bump，无迁移步骤。

## 代价（明确登记）

- **依赖模型调用工具**：模型若只在正文里说「我会继续」而不调用 `continue_task`，任务仍会停住。
  提示词把「不要只在正文里承诺」写成显式指令（与 `set_task_status` 同一条纪律），但这是模型遵循度，
  不是构造性保证。被否的替代是「编排无条件续跑」——它用可控的成本换来了「在等人的任务也被继续烧」
  与「停机只能靠改状态」两个更坏的错误面。
- **续跑轮的输入变长**：整个任务线程进上下文，token 成本随线程长度增长；上限 3 轮是成本闸门。
- **`round_outcome` 的计数口径**：上限数的是「该成员在该世代的轮数」，不是「续跑次数」——
  如果同一世代里还有被提及 / 人类消息带来的轮次，实际可续跑的次数会少于 3。这是有意取窄：
  一个计数器、一条可解释的规则，好过第二个计数表。
- **team 缺口留在原地**：team 任务线程仍然只跑队长那一轮；用户若在 team 里遇到同一病症，
  需要另外的产品裁定。
