# 认领是一次**开工动作**：编排在同一事务里推状态、交出任务本体，并要求认领者必须回应

用户于 2026-10-17 人定（U1 / U2 / U3 三条）：**认领即开工**——认领之后由**编排**把任务推进到 `in_progress`，
把**任务本体**（标题、状态、受派者身份）同时交给消息流与被唤醒的 Agent，并让那一轮**不允许沉默**（沉默按 `failed`）。
本 ADR 记录这次裁定与它的边界。

本 ADR 是 **ADR-0010 的扩展，不是推翻**；ADR-0010 原文**一字不改**（沿用 ADR-0007 / ADR-0010 处置旧 ADR 的既有惯例：
旧 ADR 记录的是当时那次决策与**被否方案**，就地改写会让「当时为什么这么定」消失）。边界差异只在这里、
`CONTEXT.md` 的**认领** / **任务状态** / **人类世代**词条、以及 `app/specs/claim-starts-work-design-notes.md`（设计正本）里声明。

## 背景：ADR-0010 定对了预算语义，但没有定「认领之后发生什么」

ADR-0010 把认领钉成三件事：**编排发起**、**不是跳**、**开一次世代**，并用「每张任务至多一次」守住 ADR-0002 的三跳上界。
它的动作表把「认领」与「改状态」列为**两格**，于是 `Database.claim_task` 只落结构事实（`assignee_member_id` /
`claimed_at` / `target_member` / `target_read` / 一条 `system` 记录 / 开世代），**不碰 `task.status`**；
`app/tests/test_auto_claim.py` 还把这一条断言成契约（`status == "todo"`）。

这条设计在**预算面**是对的，在**用户可观察面**上败露成三个缺陷，且三者在同一次真实使用里同时发生（现场读数见设计正本 §0）：

1. **任务不会自己开始**：认领后状态仍是 `todo`，看板上的卡片不动，「被认领」与「在干活」在界面上无法区分。
2. **被唤醒的 Agent 拿不到任务本体**：任务线程里只有「任务已创建」（`system.task.created` 正文**不带标题**）与
   「已认领：某人接手了这张任务」两条 owner 署名的第三人称记录；`TaskActionContext` 只有 id 与成员表，
   `_system_prompt` 在任务轮次里既没有标题也没有「你已是受派者」。于是模型必须从两条第三人称记录里推断自己在干什么——
   而它推断**失败**了：那一轮的回复原文是「这张任务是别人认领的、不是我，也没人直接点名我 —— 所以我应当保持沉默」。
   任务标题从未出现在任何一条消息里，也没进过 prompt。
3. **唤醒纪律允许它沉默**：认领走的是 `notify_task_assignment` → `_notify_task_assignee`，那一轮传的 reason 是
   普通消息唤醒（`channel-message`），而基础 rubric 是「没被点名就该保持沉默」。只有 `mention` 是确定信号。

## 一、认领仍是编排发起、不扩接缝的输出形状

ADR-0010 一 的裁定**不变**：认领由后端按该频道的 Agent 配置裁决，**不让模型自己改数据库**；
**成员面适配接缝**的输出仍是「零或多条待落库回复 + 一个轮次结果」，**不新增第三种输出**。
本 ADR 扩的只是**输入侧**：任务轮次另带**任务上下文**（任务标题、当前状态、受派者身份）——
那本来就是接缝既有的内部类型 `TaskActionContext`，扩它的字段不算改形状。

认领的**执行者是编排**；`claimed_at` 记录的是被裁定接手的人。该路径**不新增 actor 痕迹字段**、不改 DDL。

## 二、认领仍是「不是跳」，但现在是「开工动作」

**「认领不是跳」不变**：跳的载体必须是一条 **Agent 消息**，认领的载体是任务型 target 上的 `system` 记录。
因此认领**不消耗**回应预算，在**预算耗尽**的世代里也照常投递——这不是一条新规则，而是「认领不进预算账」的直接推论，
所以不存在「因为预算耗尽所以认领轮可以沉默」这条路。

**被扩展的是「认领做什么」**：它从「只落结构事实」扩成**编排发起的开工动作**，在**同一个事务**里完成七件事：

```text
认领事务（单事务，任一步失败 ⇒ 全部零改动）
  assignee_member_id / claimed_at / updated_at
  target_member（认领者入成员面）+ target_read（消费游标归零）
  system 记录 ①「已认领：{name} 接手了这张任务」   ← 世代标识取它的 seq
  target_budget(epoch_seq = ①的 seq, used = 0)      ← 开一次世代（ADR-0010 三不变）
  task.status: todo → in_progress
  system 记录 ②「认领后自动开工：状态推进至 进行中」 ← 新键，不与「有人推了状态」共键
  唤醒认领者（reason = claim，不计跳，那一轮必须回应）
```

选**单事务**而不是「认领成功后再调一次状态写路径」：后者会出现「已认领但没开工」的时间窗，而那正是本 ADR 要消灭的
那类状态；它还要回答「以谁的名义推进」，而答案只能是撒谎（冒充 owner）或造特权（编排专用身份）。
写成状态记录**第二条**而不是「只 UPDATE 不落记录」：ADR-0006 定的纪律是**每一次任务变更追加一条 `system` 消息**，
而前端任务线程的「状态变更记录」段渲染的正是这些行——不落记录会让看板说进行中、线程里查不到原因，
那正是「用户看不出它到底开没开工」的第二形态。

## 三、认领推进复用迁移表，但不复用 actor 校验

`claim_task` 内部走一条**私有**的状态推进实现（同事务 UPDATE + 追加那条记录），**不经** `update_task_status`：

> 认领推进复用迁移表 `TASK_STATUS_TRANSITIONS` 做合法性判定，但不复用 `update_task_status` 的 actor 校验 ——
> 认领的授权来自**编排**（配置层裁决），不来自成员身份。

两条被否的路：**在 claim 事务里嵌一次 `update_task_status`**（伪原子：两个事务嵌套 begin/commit，破坏单事务结论）；
**用 `actor_member_id=OWNER_ID` 调既有路径**（语义撒谎——不是 owner 推的，且 owner 恒可绕过「受派者不能自我批准」那一格，
未来收紧权限时它会变成后门）。拿掉迁移表校验同样被否：它会把唯一那条可判定的边界变成「认领可以写任意状态」。

**一处必须写准的取证口径**：`system` 记录的 `author` 恒为 owner，这是**系统事件消息**的既有口径
（`_append_task_system_message_locked`），**不表示人推的**。「人推的」与「编排替它开工」的区别**只在词条键**
（`system.task.status` vs `system.task.claim_started`），**不在 author**。既有键继续只表示「有人推了状态」，
新键才表示「编排替它开工」；将来若再加编排自动动作，照这个模式加键，不要复用系统的通用键。

## 四、任务本体：消息流与 prompt 都带

**消息流**：`system.task.created` 的正文从「任务已创建」改为「任务已创建：{title}」（同键、加 `title` 参数）。
只补标题、不写状态：本 ADR 要求任务随即被推进，若把**写记录时的状态**一并固化进 append-only 历史，
同一条线程里会立刻出现互相矛盾的记录。**历史不回填**——存量任务的第 1 条仍是旧正文。

**prompt**：任务轮次的 system prompt 增一段「任务上下文」，含标题、当前状态、受派者身份
（仅当本轮 Agent 就是 `assignee_member_id` 时声明「你是这张任务的受派者」）；**认领轮**另加一句显式声明
「本轮由认领唤醒，你必须回应」。受派者身份是承重的一句——现场那条错误回复恰恰是模型自己推出「我不是受派者」。

## 五、认领唤醒必须推进：判据落在显式标记上，不落在 reason 上

认领轮自判忽略按 `failed` 记录，与「被 @点名」**同一套判据、同一处落点**（`ignored` ⇒ `failed`；
`replied` 但没有可落库正文**且**没有提交任务动作 ⇒ `failed`）。于是「只调用一次 `set_task_status` 而不说话」**算回应**；
**措辞质量**（「说了等于没说」）不由本 ADR 收敛，它归 #35 / #57 / #58 那条线。

判据**不读 reason**，读一个投递时算好的显式布尔（`mandatory_reply`，**不落库**、只走进程内参数），
因为同一 Agent 同 target 的重复唤醒会被**合并**、跨 target 的 deferred 轮次会**继承**参数，而合并后的 reason
由先到者决定——认领的强制语义不该取决于「谁先到」。合并时**取或**：任一方强制 ⇒ 合并后强制。

这条同时是对既有代码语义的一次**收窄**：`reason` 从此只承担「可读诊断 + 正在回复指示」，
**不再**承担纪律判据。新增 `WAKE_REASON_CLAIM = "claim"` 只进进程内参数与 typing 事件，不落库；
「本轮由认领唤醒」按 `reason.pierced_suffix` 的既有先例追加进 `round_outcome.reason` 文本。

**适用范围只圈认领唤醒**。owner 手动改指派（同一条唤醒路径，reason 仍是 `channel-message`）维持既有纪律：
任务本体照旧给到它，但**不强制发言**。同类缺口登记在本 ADR 的代价栏，是否另立票由用户后续决定。

## 六、`schema_version` 不 bump

本 ADR 零 DDL：`message.body` 与 `round_outcome.reason` 都是既有 TEXT 列，新词条是代码不是库形态。
因此本能力**不带** `from → to` 迁移步骤——理由：ADR-0015 的链只覆盖 **schema 形态变更**，
「链连续性」这条纪律不适用于「新增一条文案与一个进程内参数」。

## 七、与 ADR-0002 / ADR-0005 / ADR-0006 / ADR-0010 的关系

- **ADR-0002（三跳上界）**：`每张任务至多一次`（`claimed_at` 构造性保证）**仍然足够**守住 ≤3。理由链：
  跳的载体必须是 Agent 消息 ⇒ 认领不计跳；「每任务一次」⇒「认领 → 用满 → 再认领」不可达；
  新建任务的唯一扳机是 owner 的 HTTP 动作 ⇒ Agent 造不出任务来刷世代。**不改成会计跳**——那会推翻用户 2026-10-16 的裁定。
- **ADR-0005（派任务与有界响应同构）**：动作表多一格——「认领（编排发起，推状态 + 要求必答）」。
  「唤醒的载体是**指派**这个动作」这条判断不变，认领正是它的又一次应用。**原文不改。**
- **ADR-0006（当前态在行上、变更史在流里）**：本 ADR 是它的直接应用——认领既改行（status）又留记录（两条 `system`）。
  两条记录而不是一条，是因为它们说的是**两个事实**（谁接手了 / 开工是谁推的）。
- **ADR-0010（认领开一代）**：**三**（认领开一次世代）**不变**，世代标识仍取「已认领」那条记录的 `seq`；
  **二**（认领不是跳）**不变**；**四**（每张任务至多一次）**不变**且是本次扩展仍然可执行的前提；
  **一**（编排发起、不扩输出形状）**不变**；**被扩展的是「认领做什么」**——从落结构事实扩成开工动作。

## 代价（明确登记）

- **认领不再是一条「便宜」的写路径**：它现在多两件事（推状态、要求必答），比 ADR-0010 当时描述的重。
  守这条边界的只有一把锁——`claimed_at` 那一条构造性保证。它的失效方式是可预见的：将来若有人给「重新认领」开一个口子，
  「每任务一次」当场破，三跳上界也随之可被拆。
- **「认领后自动开工」是编排的确定性规则，不是模型的判断**：Agent 不会「申请」开工，`auto_claim` 决定编排替不替它接手。
  于是「状态已被推到 `in_progress` 而那一轮 `failed`」是**可能**的可观察结果（例如 PATCH `enabled` 的并发窗口让 wake 时才发现不可用）。
  这不是 bug：编排的裁决（谁该接手、该不该开工）与「模型此刻能不能跑」是两件事。
- **`reason` 的职责被收窄**：它从此只做可读诊断与 typing 指示。取窄的代价是「必须回应」这条纪律多了一个**不落库**的
  进程内参数——它没有取证面，只能在测试里断言，事后翻库看不到。
- **同类缺口留在原地**：owner 手动改指派 + 受派者沉默这一格**不在本 ADR 内**（U3 原句只圈认领唤醒）。
  它与「认领即开工」是同一个用户可见病症的另一种触发路径，登记在此，由用户决定是否另立票。
- **存量库不回填**：迁移链不做、启动路径不做、本能力不做。见到 `claimed_at IS NOT NULL` 而 `status` 仍是 `todo`
  的存量行，行为是**不动它**——这是一条明确的**不作为**，不是遗漏。
