# 消息正文渲染 Markdown：自写最小渲染器，不引第三方库、不加载图片、搜索面保持纯文本

用户于 2026-10-26 人定：**human / agent 的对话正文一律把 Markdown 渲染出来**。此前消息正文由
`messageText()` 逐字符 `textContent` 拼出，只有**提及区间**会包 `<span class="mention">`；`.msg-text`
带 `white-space: pre-wrap`，于是 Agent 回的 `**加粗**` / `## 标题` / 围栏代码块 / `| 表格 |` 全部按
原字符呈现。用户要的是「读得懂」，不是「看得见记号」。

本 ADR 只记录这个决定与它的边界，不记录实施步骤与逐条 CSS 值。

## 决策记录

- **Context**：设计系统 `ui_kits/app/app.css:198-205` **早就写好了**消息正文渲染后的形态——
  `.msg-text > .markdown-body`、`.msg-text p`、`.msg-text code`、`.msg-text pre`，连 `pre` 里的
  `.cmt` / `.kw` 两个高亮 span 都留了位；原型 `alibot-app.html:1129` 也是 `highlight(m.code)` 渲染 `<pre>`。
  也就是说这不是「新增一个能力」，是**把设计系统已经承诺、产品侧从未落地的形态补上**。
  同时仓库有三条既有事实构成约束：① 前端零第三方依赖（`studio/` 只有 5 个手写文件，无 `package.json`、
  无 `node_modules`、无 CDN 运行时引用）；② 「DOM 一律用 `createElement`/`textContent` 构建，不用
  `innerHTML`」是写进 `app.js:33` 的纪律，且 `agent_capabilities_ui.test.cjs:1539` 已把它断言成契约；
  ③ 所有成熟 Markdown 库都产出 **HTML 字符串**，要塞进 DOM 就得 `innerHTML`，要么破纪律，要么再引一个
  净化库（等于用两个依赖换一个子集）。
- **Decision**：写一个**最小渲染器**，纯 `document.createElement`，只覆盖 Agent 实际会用的子集；
  放在新文件 `app/alibot/studio/markdown.js`，是**纯函数模块**（输入字符串、输出 DOM 节点，不碰
  `state`、不调 `t()`、不发请求），在 `index.html` 里挂于 `app.js` 之前。渲染面**只限 human / agent
  的对话正文**。链接只放行 `http` / `https` / `mailto` 并一律 `target="_blank" rel="noopener noreferrer"`；
  图片**不加载**，`![alt](url)` 保持原字符；HTML 内联标签**一律当字面文本**（不解析），这是把「不用
  `innerHTML`」的纪律贯彻到数据面。
- **Consequences**：正文的呈现不再等于正文字符串——同一条消息渲染前后**行距会变**（`pre-wrap` 让位给
  `<p>` / `<br>`）。这带来三件事：① `.msg-text` 的 `white-space: pre-wrap` 必须移除（否则每个源码换行
  再加一次，形成双重行距），但 `.msg.sys .msg-text`（系统事件，不渲染）**保留不动**；② 搜索面
  `searchHitText()` **不渲染**，保持纯文本 + 后端高亮区间，因为区间是在**原始正文**上算出来的，正文一旦
  成树区间就落不到字符上；③ 技能详情页的 `SKILL.md` 正文**不渲染**，保持纯文本——那是配置文件
  （缩进与 `#` 有语义），渲染成 HTML 会丢掉「这是原文」这层信息。ADR-0031 起技能字节的正本在家目录，
  它的呈现契约不变。

## 一、渲染面：只渲染「说话」，不渲染「记录」

| 面 | 落点 | 渲染？ | 理由 |
| --- | --- | --- | --- |
| 频道消息流正文 | `messageText()` → `app.js:8918` | **是** | 对话正文，本 ADR 的正题 |
| 任务线程回复行 | `app.js:1950` | **是** | 复用 `messageText()`，同一套呈现不另造 |
| 系统事件消息 | `app.js:8892` | 否 | 正文 100% 由后端 i18n 模板生成，不含用户输入 |
| 旁白式交代 | `narrationNode` `app.js:8843` | 否 | 已折叠成一行，且正文被一对圆括号包住 |
| 状态变更记录 | `ttHistory` `app.js:1968` | 否 | 是记录列表，不是说话 |
| 搜索命中行 | `searchHitText()` `app.js:540` | 否 | 高亮区间基于原始正文，见 §三 |
| 技能 `SKILL.md` 正文 | `agent_capabilities_ui` | 否 | 配置文件，不是对话 |

「说话」与「记录」的分界不是新造的：`CONTEXT.md` 的**消息**词条早已把 `kind='system'` 的事件行与人类 /
Agent 的发言区分开。本 ADR 只是把这条区分**落到呈现层**。

## 二、不引第三方库：三条理由里没有一条是「库不好」

1. **产出形状不合**：成熟库的公开 API 是 `parse(src) -> html string`。本仓的 DOM 纪律要求节点，
   于是要么 `innerHTML`（破纪律），要么再引 DOMPurify（两个依赖换一个子集功能）。
2. **安全责任错位**：后端渲染 HTML 会把「转义」挪到服务端，而 `CONTEXT.md` 的**高亮区间**词条立的是
   「判定在后端、**呈现**在前端」。渲染是呈现，不是判定。
3. **offset 语义要自己说了算**：提及区间由后端给出（见 §三），渲染器必须保留**每个文本节点在原始正文里的
   起始 offset** 才能把区间映射上去。第三方的树结构不为这件事设计，接上去要写一层适配，比自写更绕。

代价是子集有限。**明确不进渲染器的**：图片、HTML 内联标签、脚注、任务列表 `- [ ]`、数学公式、
自动链接（裸 URL 保持文本，要链接就写 `[]()`）、语法高亮。

## 三、提及：先建树，再把后端区间映射到文本节点上

`CONTEXT.md` 的**高亮区间**词条立着一条硬纪律：区间由**后端**给出，前端只按区间包标签，**不做判定**。
渲染器必须遵守它，于是顺序是：先按 Markdown 建树，再在树里的**文本节点**上按后端区间包 `mention`。
这样 `**@小明**` 得到「加粗的提及」、`` `@小明` `` 得到「行内代码样式的提及」，两种写法都符合直觉，
而前端仍然不判定「是不是提及」。

**这条路径暴露了一个既有 bug（本 ADR 不修，独立成票）**：提及区间是 Python **码点**下标
（`mentions.py:99`），前端用 JS **UTF-16** `slice`（`app.js:503`）。含 emoji 的消息**现在就是切错的**——
`"😀 @小明"` 后端给 `start=2 end=5`，前端 `slice(2,5)` 得到 `" @小"`；且 `app.js:503` 的
`span.end > body.length` 守卫挡不住（码点下标恒 ≤ UTF-16 长度）。同一个坑**搜索侧已经修对了**
（`db.py:5407` 显式转 UTF-16，`test_search.py:114` 有 emoji 用例），所以修法有现成先例。
另有一处独立缺陷：`service.py:1165` 用**原始 body** 解析提及，而 `db.py:5254` 落库前 `.strip()`，
于是 `"  你好 @小明"` 的区间按未 strip 的串算、存库却是 strip 过的。

**渲染器必须等这两处修完再落地**：Markdown 建树后文本节点中间有被消费掉的 `**` 空洞，offset 映射比
现在的 `slice` 更经不起单位错。这是本 ADR 与那个 bug 票的**硬顺序**。

## 四、视觉：照抄 kit，但把「表格破 68ch」写成唯一例外

`.msg-text` 的 14px / 68ch / 1.65 出自设计系统的**局部可读性例外**（`SKILL.md:102-110`、
`DESIGN.md:176` 三处都引「ADR-0016」，而那个 ADR 本体不在树里——这是**既有文档债**，本 ADR 只记一笔，
不顺手修）。渲染器新增的块级元素**全部在这条 68ch 之内**，只有一个例外：

**表格突破 68ch**（`width: max-content` + 横向滚动容器）。理由：表格的可读性依赖列对齐，三列表格硬塞进
68ch 会挤成一团，等于让它不可读。这是 `.msg-text` 那条规矩的**唯一例外**，在 CSS 里必须写明理由。

代码块**照抄 kit 的深底浅字**（`oklch(24% 0.015 255)` / `oklch(94% 0.01 250)`），浅色主题下也深底——
代码块本来就该跳出来。但**不产出** kit 里那 `.cmt` / `.kw` 两个高亮 span：它们需要词法分析器，而原型那两档
正则着色（`alibot-app.html:1166`）在真实代码上会把字符串里的 `//` 也染成注释色。CSS 里那两个类名保留
不删（它是设计系统的资产），产品侧不产出。

新 token 加进 `studio/product-tokens.css`，规则加进 `studio/app.css` 的 `.msg-text` 段。**不往设计系统
`tokens.css` 里塞 code / table token**：那个包是只读挂载（`api.py:2288`），且它明确声明
「color + type are canonical there」，往里加产品侧的形状是跨层。

## 五、被否的方案

- **引 marked / markdown-it + DOMPurify**：见 §二。功能更全，但换来两个依赖 + 一条破纪律的路径。
- **后端渲染成 HTML**：把转义挪到服务端，且违反「呈现在前端」的分界。
- **前端把码点区间换算成 UTF-16**：等于让前端补偿「后端本该给对的口径」，且区间口径的正确落点只有一处。
- **图片加载 `<img>`**：会让「消息正文」变成一条**数据外流通道**——谁发一条带追踪像素的消息，就能拿到
  「谁在什么时候看了这条消息」。`CONTEXT.md:279` 对「会离开本机的数据面」立的是**显式列出**的规矩。
  真要看图走附件（本机对象、不联网）。
- **给每行加「查看原文」开关**：每行多一个常驻控件，而这个仓库对常驻控件的边际价值一向抠得很紧。
  代价（`snake_case_name` 被误当强调）记进 `CONTEXT.md` 词条作为已知代价。
- **节点缓存（`WeakMap` 以消息对象为 key）**：`messageNode()` 的输出还依赖 `state.tasks`（任务标题）、
  审批记录、成员表（作者名与色位）——缓存会让这些读数僵在上一帧，切语言时更会整片停在旧语言。
  这类「看起来变快了、实际把刷新正确性换掉」的优化不该混进功能票；真要做，方向是「只追加新消息」的
  增量渲染，独立成票。
- **语法高亮**：要引第三方，且仓库没有构建步骤；代码块在聊天里的主要价值是保住缩进与等宽，不是配色。
