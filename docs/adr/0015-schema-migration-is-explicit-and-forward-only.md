# 数据迁移是显式命令、逐版推进、以整目录备份为前置条件

用户于 2026-10-16 人定：普通的 `python -m alibot` **仍然拒绝** schema 版本与本代码不等的库（不猜、不跳过），但报错正文直接给出迁移命令与备份指引；**迁移本身要用户显式执行**（`python -m alibot --migrate`）。

本 ADR 取代 **ADR-0004 第 20 行**「`SCHEMA_VERSION` 要 bump 且**不做旧数据迁移**」这句口径，以及第二版规格的**决策 8**。ADR-0004 正文**一字不改**（沿用 ADR-0007 / ADR-0010 处置旧 ADR 的既有惯例：旧 ADR 记录的是当时那次决策与**被否方案**，就地改写会让「当时为什么这么定」消失，而且那处「不做迁移」是 ADR-0004 那次取舍的**代价栏**，删掉它就抹掉了那次取舍的记账）。取代关系只在这里、以及 `CONTEXT.md` 的**数据迁移**词条里声明。

## 一、命令面与退出码

迁移入口是 **`python -m alibot --migrate`**：一个布尔旗标，与既有的 `--repair-targets` / `--data-dir` 同族（本仓 CLI 是单 argparse 入口，不引入子命令）。

退出码沿用既有三类语义：

| 码 | 含义 | 与既有常量的关系 |
| --- | --- | --- |
| `0` | 迁移成功；**库里版本已是目标版本**（无事可做）也走这里 | 无 |
| `3` | 库不被本代码接受（版本低于 3 / 版本号缺失但有业务数据 / 认不出的号 / **未来版本**） | 复用 `DATA_NOT_ACCEPTED_EXIT_CODE`：同一个库，三条路径（启动、`--migrate`、`--repair-targets`）给同一个答复 |
| `5` | 迁移失败，**已回滚**（含备份失败） | 新常量，与 `--repair-targets` 自己的 `4`（版本匹配但不是本入口能处置的形态）区分 |

**没有「部分完成」退出码**：迁移在一个事务里收口，这个状态不存在，一个不可达的码是死代码。

**幂等**：对已经是目标版本的库再跑一次 `--migrate` ⇒ 改动 0 行、退出 0，不报错、不新建备份。

**预演（原库零字节改动）**：`--migrate --dry-run` 在**数据目录内的临时副本**（`alibot.db` 与旁边的 `-wal` / `-shm` 一起复制）上跑**完整迁移链**，打印将执行的步骤与每步将改动的行数，并在报告里打出**原库文件 sha256 的前后两个读数**作证，随后删掉副本。它回答的是「这条链在这个库上能不能跑通」，不是「大概齐」。

**被否方案与代价**：

- **只读判定、不跑步骤**（在同一连接上只做判定与规划，绝不执行写语句）：更便宜、也不需要临时空间，但它证明不了「步骤真能跑通」——用户仍然要拿真库赌一次，而预演的全部价值正是免掉这一赌。
- **不做预演**：用户对一次不可逆操作零信息。
- 采纳方案的代价：需要一份临时副本的磁盘空间（与库同量级，附件字节不复制），且预演与真跑之间有时间差——副本不会在真跑时被复用。

## 二、支持的源版本范围

**从 3 起连续支持到 `SCHEMA_VERSION`。** 取证：`SCHEMA_VERSION` 的起点其实是 1（当时的路径是 `app/worksplice/db.py`），**3** 是项目改名 worksplice → alibot（`858a92d`，2026-10-14）落地时的号，因此它是唯一**同时**存在于新旧数据目录的号；v1 / v2 的库只可能在旧数据目录 `~/Worksplice` 里，而 `app/README.md` 已明写改名不保留兼容、「那是另一个项目的目录」。

- **低于 3、版本号缺失但有业务数据、认不出的版本号** ⇒ 拒绝（退出码 `3`），正文给库路径、两个版本读数、备份指引与「换一个数据目录启动」这条既有出路。
- **未来版本（库版本 > 代码版本）一律拒绝。** 理由不是保守：本仓**没有降级步骤**，而「旧代码打开并改写一个新版库」是数据损坏的唯一来源——闸门存在的原始理由就是它（`db.py` 的 `_assert_schema_compatible`：不修版本号、不跳过、不猜测）。给未来版本开一条「试试看」的路，等于把闸门从构造性保证降级成建议。

**被否方案与代价**：

- **只支持 N-1**（每次只保证从上一个发布版本可迁）：代价是本仓必须**每次发布都留一棵 N-1 的代码树**，而中间版本的用户被逼向手工逐版升级——那正是「显式命令」想消除的体力活。
- **把起点抬高到 7**（例如"更早的号没有真实用户"）：代价是丢掉 3–6 的唯一迁移路径，而那段步骤在 git 里可复现，成本只是几步注册项。
- 采纳方案的代价：注册表必须长期维护 3..N 全链，链上任一步的测试都要保留；这条代价由第三节的连续性测试承担。

## 三、迁移步骤的组织方式

**骨架是逐版步骤注册表**：每个步骤声明 `from_version → to_version`，**严格 +1**，链**连续**覆盖 3..`SCHEMA_VERSION`，执行器**从库里的版本起逐步走，不跳步**。步骤内部可以是**显式数据搬迁**（如 channel 型作用域数据从 `channel_*` 搬到 `target_*`），也可以是**按目标 `SCHEMA` 幂等对齐**（建表 / 加列用 `IF NOT EXISTS` 兜底）——两者组合，而不是二选一。

**链前另有一个形态步骤（shape-conditioned）**：它**不依赖版本号**，只看库的形态——「`channel` 行在，而 channel 型的影子行 / 成员 / 已读 / 预算有缺」就执行搬迁，且**幂等**（`INSERT OR IGNORE` 语义，重复跑改动 0 行）。它存在的理由是一个真实的历史事故：#24 把作用域升为 `target` 时，v4 的 `_initialize` 曾静默接受 v3 库，于是有库停在「`schema_version` 已是 4、数据还留在旧表名里」的**半改名**状态。按版本号走链会**跳过** v3→v4 那一步，于是这类库会被"顺利地"迁到最新版却仍然缺影子行——这正是 `--repair-targets` 今天存在的原因，也是它不能被简单转发到链尾的原因。

**撞号（同一版本窗内多张在途票各自 bump）**：注册表要求 `from → to` **唯一且连续**，并由**一条源码测试**断言链的连续性。今天的 `9 → 11 → 12` 就是实例：#67 被分配的 9 低于当时 main 的 10，带着 9 合入会让版本号在历史上不单调。判据是「**必须高于当前 main**」而不是「等于被分配的预留号」。有了连续性测试，这类落后号 / 撞号会**在 CI 立刻红**，而不是在用户库里静默错位。

**纪律：此后每次 schema 变更必须随票携带迁移步骤。** 三处强制，漏带者当场失败：

| 强制点 | 谁、什么时候失败 |
| --- | --- |
| 链连续性测试（源码） | 漏带步骤的票：`SCHEMA_VERSION` 已 bump 而链断了 / 某步的 `from` 落后于 main 的号 ⇒ CI 红，PR 合不进去 |
| 票面 DoD | 动 schema 的票必须声明"携带 from→to 步骤"并给该步骤的验收；不声明即不符合本 ADR，审查者可拒收 |
| 本 ADR | 提供判据来源：链的连续性不是风格要求，是这条契约的落点 |

**被否方案与代价**：

- **纯「按目标 `SCHEMA` 结构对齐」**（一次性把库改造成当前形态 + 显式搬数）：看起来更优雅（没有版本链要维护），但它回答不了**「这一步该搬哪些行」**——对齐只能造出**结构**，数据搬迁的判据本来就是"上一代形态里它在哪"；而且它对未来版本给不出判据（没有版本链，就没有"我只认得 ≤ 我的号"这句话）。
- **纯逐版步骤、不加连续性检查**：撞号与落后号**静默通过**，错了要等到用户库上报才发现。
- 采纳方案的代价：维护全链 + 一条链测试；且形态步骤与版本步骤的职责必须在代码里分清（前者判定形态、后者推进号），否则会出现"两个地方都在搬同一批行"。

## 四、备份与失败恢复契约

- **迁移前自动备份整数据目录**（含 `attachments/` 的字节），落点与命名**同级**：`<数据目录>-backup-<from>-to-<to>-<UTC 时间戳>`。备份单位是**整个数据目录**，与 `app/README.md` 的既有口径一致（只备份 `alibot.db` 是「有元数据、没字节」的半份）。
- **备份失败即拒绝迁移**（退出码 `5`），不退化成「放行 + 一句警告」。于是「先备份再迁移」不是正文里的一句请求，而是执行器的**前置条件**。
- **事务边界是单事务**：`BEGIN IMMEDIATE` → DDL + 数据搬迁 → `COMMIT`。SQLite 的 DDL 是事务性的，因此进程被杀 / 断电 / 磁盘满都落在**回滚**那一侧，库**停在原版本**、仍可被原版本代码打开。
- **审计**：每次迁移写一条 **append-only** 的记录（从哪版到哪版、起止时间、结果、备份路径）。它不在人类面暴露写入口。

**被否方案与代价**：

- **不自动备份**（正文里给指引、让用户自己备份）：把不可逆操作的风险留给用户，而报错正文那句「请先备份该数据目录」就变成一句**空话**——没有人会为一次撤销不了的操作去赌一个自觉。
- **自动备份但失败仍放行**：等于没有备份保证，只是多了一个"备份过了"的错觉。
- **只备份 `alibot.db`**：与「备份单位是整个数据目录」冲突，会丢附件字节；恢复出来是一个半份库。
- 采纳方案的代价：一次迁移需要与数据目录同量级的临时空间；且备份副本需要用户自行清理（本仓不引入保留策略与自动化清理器）。

## 五、`--repair-targets` 与 ADR-0004 的处置

**吸收 + 保留弃用别名。** `--repair-targets` 今天的语义（把当前 schema 库里缺失的 channel 型 target 作用域数据补齐）成为第三节那个**形态步骤**；`--repair-targets` 保留为**已弃用别名**：同一入口、同一条链、同一退出码，先打印一句「请改用 `--migrate`」，`app/README.md` 的指引改指 `--migrate`，下一个版本周期再删。

**别名必须仍能处置半改名库**：半改名库的 `schema_version` 已是 4，而本代码的常量是 12，因此别名**不能**沿用今天那道「恰好等于当前版本」的版本门。它的版本门放宽为 `[3, SCHEMA_VERSION]`（下限与上限的理由见第二节：**未来版本仍一律拒绝**），然后**只跑形态步骤**——于是「版本号已是 4、数据还没搬」的库仍然能被它补齐，而这正是 #37 那次事故的处置能力。这条边界必须写清：**别名放宽的是"离目标有多远"，没有放宽"方向"**——未来版本一个都不碰。

**ADR-0004**：正文**一字不改、不加 Status 行**（本仓 14 条 ADR 没有一条用 frontmatter，加一行会是体例首例）；新契约由本 ADR 承载，取代关系在本 ADR 首段声明，并在 `CONTEXT.md` 的**数据迁移**词条里可查。

**被否方案与代价**：

- **并存两套入口**（repair 继续独立处置"当前版本的半改名库"，migrate 管跨版本）：长期分裂成「同一个库、两个答复、两套语义」，而两者处置的其实是同一批行。
- **直接删除 `--repair-targets`**：存量文档与脚本的引用当场断，且丢掉 #37 的历史处置能力。
- **就地改写 ADR-0004 那句话**：抹掉那次取舍的被否方案记录（ADR-0004 是"target 升一等"的决策记录，「不做迁移」是它登记的代价）。
- 采纳方案的代价：一个名字要在文档里活一个版本周期（别名 + 一句弃用提示 + 一条别名等价性测试）。

## 六、兼容面与文档面

- **旧表命运：保留。** 迁移后 `channel_member` / `channel_read` / `channel_budget` **原样留着**（与 `repair.py` 今天的处置一致），作为回退面；同时用一条测试断言**当前代码没有任何读路径引用旧表**（旧表名只允许出现在迁移 / 修复模块与测试里），保证旧值不会被读成**第二正本**。既有端点的读口径一个字不改：未读、预算、成员面仍走 `target_*`。
- **`CONTEXT.md`**：新增**数据目录**、**备份**、**Schema 版本**、**版本闸门**、**数据迁移**五条词条（各带 `_Avoid_` 行），并修订**附件**词条里指向数据目录的那一句。
- **`app/README.md`**：只改「从首版升级」与「备份」两段——前者改成"启动仍拒绝版本不等的库，正文给出 `--migrate` 与备份指引"，后者补一句迁移前自动备份的落点与"备份失败即拒绝迁移"。「备份单位 = 整个数据目录」的口径不变。

**被否方案与代价**：

- **迁移后 `DROP` 旧表**：不可逆，且与"备份可回退"重复（回退已经由整目录备份承担），代价是回退时还得重新推导旧表内容。
- **迁移期双写**（旧表与新表同时写）：两个正本，未读与预算的口径立刻分裂。
- **只写 ADR、不动 `CONTEXT.md`**：「迁移」「闸门」会变成只在 ADR 里存在的一次性黑话，与「`CONTEXT.md` 是唯一词汇正本」的口径冲突。
- **整段重写 README**：会把 #67 / #37 的既有取证叙述一并抹掉，制造无谓 diff。
- 采纳方案的代价：迁移后的库里**同时躺着两代表**（旧的 `channel_*` 与新的 `target_*`），"这个库长什么样"要读旧表命运这条纪律才知道；且旧表要等到用户自己确认无异后才清理（本仓不提供删除入口）。
