# 自动认领默认开启：只在自主频道生效，存量 Agent 一次性回填

2026-10-20 人定（#195）：频道里新建任务后，编排应当默认替一个可用的 Agent 接手，而不是等人类逐个
打开开关。由此产生三条绑定在一起的裁定——**默认开启**、**只与自主频道合取**、**存量行一次性回填**。

本 ADR 只定配置默认值、生效条件与升级语义；认领的事务内效应、预算与唤醒口径见 ADR-0010 / ADR-0016，
team 模式的拓扑见 ADR-0018 / ADR-0022 / ADR-0025，均不变。

## 决策记录

- **Context**：2026-10-20 自主频道「调查组」里新建的任务停在 `todo`，两名成员 `enabled = 1`、状态
  `online`，但 `auto_claim` 都是 0 且 `created_at = updated_at`（从未改过）。旧默认把「认领」变成
  一个很少有人主动打开的一次性选择，于是自主频道的核心承诺（新建任务会被接手）在最常见的状态
  ——刚建好的 Agent——上不成立。
- **Decision**：`agent_config.auto_claim` 的 DDL 默认值改为 `1`；认领仍要求
  `channel.mode = autonomous` **且** `availability.ok` **且** `auto_claim = 1` 三者合取；升级时把
  存量 `auto_claim = 0` 的行一次性置 1（`19 → 20`，重建表 + 回填，返回真实改动行数）。
- **Consequences**：升级会覆盖此前显式关闭的存量行（见「代价」）；`SCHEMA_VERSION` 19 → 20，迁移
  只前进；team 频道的行为逐字不变；Studio 控件与文案不变，仍可逐 Agent 关闭。

## 一、默认开启

- `agent_config.auto_claim INTEGER NOT NULL DEFAULT 1`。
- 创建 Agent 的写路径**继续依赖列默认值**（`INSERT` 不写这一列）：默认值只有一个正本，不在服务层
  再造第二套缺省。
- 「默认开启」不改变认领的裁决面：候选仍按 `availability` 过滤、仍按创建顺序取第一个、仍每张任务
  至多一次（`claimed_at` 锁不变）。

## 二、只在自主频道生效

生效条件是合取：

```text
channel.mode = autonomous  AND  agent.auto_claim = 1  AND  availability(agent).ok
```

`WakeOrchestrator.claim_new_task` 现有的 `mode != team` 早退已经承担了第一项，本票**不改这段逻辑**，
只用测试锁住「team 频道里即使成员 `auto_claim = 1`，新建任务也不认领」——team 的任务创建只走
「唤醒队长一轮」（ADR-0025），认领不是那条路径的一部分。

DM 恒为 autonomous，因此 DM 里的行为与既有读路径一致；team 的队长/成员唤醒面不变。

## 三、存量行一次性回填与迁移

`19 → 20` 在同一个 `MigrationStep` 里做两件事：

1. 按当前 `SCHEMA` **重建** `agent_config`（既有 `_rebuild_table`）：升级库此后不写该列的直接插入
   也拿到默认 1；
2. `UPDATE agent_config SET auto_claim = 1 WHERE auto_claim = 0`：只改这一列，不动 `updated_at`
   与其它列；返回**实际改动行数**，重复执行是空操作。

**不回溯任务**：本步不扫频道里既有的 `todo` / 未认领任务，不改任何 `task` 行。本票只影响升级之后
新建的任务；升级前已存在的未认领任务保持原状，由人指派或另行处理。

## 四、被否的方案

- **保持默认关闭，只靠文档提醒**：这正是 #195 的现象来源。自主频道的价值主张是「新建任务会被接手」，
  把它留成默认关闭的显式选择，等于要求每个新 Agent 先做一次与直觉相反的配置。
- **切频道模式时联动写成员开关**：`mode` 是频道配置、`auto_claim` 是 Agent 配置，跨对象写会让
  「改频道设置」产生看不见的成员副作用，也让审计难以回答「谁把这个开关打开的」。且它仍不能解决
  「一开始就是自主频道」的默认状态问题。
- **对既有未认领任务做 sweep**：会改写历史任务行、触发批量认领与批量唤醒，把一次配置默认值变更放大
  成一次不可预期的执行风暴；而且违反「只影响之后新建的任务」这条人定边界。

## 五、代价

- **升级会覆盖此前显式关闭的存量行**：`auto_claim = 0` 与「从未配置」在库内是同一个取值，迁移无法
  区分两者。这是把人定规则「存量 Agent 一次性回填」落到数据上的必然代价；升级后仍可逐 Agent 关闭，
  `PATCH /api/agents/{id}` 是唯一写路径。
- **回填不改 `updated_at`**：它是语义迁移而不是一次配置写入；把时间戳改掉会伪造一条「有人改过配置」
  的历史事实。
- **单向门**：schema 迁移 + 存量数据回填 + 默认值语义变更，PR 保留给人工合并。
