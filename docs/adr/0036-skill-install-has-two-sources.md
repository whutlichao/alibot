# 技能安装有两个来源：人自己准备的字节（本机目录 / 上传 zip），以及外部 CLI 的落点（应用不执行 npx）

用户于 2026-10-25 人定（#277）：Agent 技能的安装支持**两个来源**——① 从本机 `~/.agents/skills/`
批量导入；② 用第三方 CLI `npx skills add <owner/repo> -g -a codex -y` 把技能装进
`~/.agents/skills/`，再由本应用导入到成员家目录。**应用不执行 `npx`**：它只读那个落点，把选中的
技能**复制**进 `~/.alibot/agents/<member_id>/skills/<name>/`。

「两个来源」是**取字节的两条路**：人自己准备（本机目录 / 上传 zip），或外部 CLI 装完再由人导入。
按**字节来源**数是三个（见 §一 的表），按**写路径**仍只有一条（`POST /api/skills`）。

本 ADR 只记录这一个决定与它的边界，不记录实施步骤、端点参数与界面措辞。

## 决策记录

- **Context**：技能的字节正本是成员家目录 `~/.alibot/agents/<member_id>/skills/<name>/`，库里只有
  元数据与内容 hash（ADR-0031 §二）。此前安装只接受**本机目录**或**上传 zip**，于是「从公开渠道拿一个
  技能」只能靠人手工找到目录再粘贴绝对路径；而 `~/.agents/skills/` 已经是 codex / cline / pi 等工具
  **共用的全局技能目录**，用户机器上往往已经有一批可用技能。另一方面，`npx` 会**下载并执行**第三方
  npm 包：本仓后端当前零 subprocess、产品无 Node 运行时依赖，出网能力按 ADR-0026 必须**显式开启**。
  把「下载并执行第三方 CLI」塞进后端会同时破掉这三条既有事实。
- **Decision**：把「取技能」与「装技能」**分层**。取技能由人在终端用外部 CLI 完成，落点是
  `~/.agents/skills/`；装技能仍由本应用完成，新增一个**只读**候选端点列出该落点的每个条目
  （名字 / 描述 / 路径 / 是否已安装 / 不可导入的可读原因），导入写路径**复用**既有的
  `POST /api/skills`（`source_path` = 候选目录）。应用不执行 `npx`、不起 subprocess、不下载第三方包，
  也不把 `~/.agents/skills/` 当成第二份字节正本——它只是一个**导入源**。
- **Consequences**：技能的三个字节来源共用同一条校验内核（`SKILL.md` front matter、路径安全、内容 hash、
  大小与数量上界），因此导入与直接安装的失败面一致；坏条目**逐条降级**（不可导入 + 可读原因），
  不整体失败；来源根缺失是**正常状态**（不创建目录、不报错、候选为空）。`~/.agents/skills/` 是
  别人的目录，应用**只读**它：不创建、不改写、不在那里留任何标记；`npx` 的锁文件
  `~/.agents/.skill-lock.json` 不参与判定。新增面只有「读候选」这一条只读 HTTP 路径，**没有**新
  schema、新迁移、新预算类别或新消息 kind。

## 一、三个字节来源共用一条写路径

| 来源 | 谁把字节放到那儿 | 应用做什么 |
| --- | --- | --- |
| 本机目录 | 人（`git clone`、解压、手写） | `POST /api/skills` 校验后**复制**进成员家目录 |
| 上传 zip | 人（上传） | 同上（原始字节走正文） |
| `~/.agents/skills/<name>/` | **外部 CLI**（`npx skills add … -g -a codex -y`） | 只读扫描出候选；人选中后仍走 `POST /api/skills` 复制 |

第三条不是新的写语义：它只是「来源目录恰好是别人写的」。因此**没有**第二个安装器、第二套校验或
第二种落点；`source_path` 指向候选的 `path` 就够。重复导入必然 `409`（同名行已在库里），
成员家目录里已装好的字节**不被覆盖**。

## 二、应用不执行 npx

三条既有事实决定这条边界，逐条对齐：

- **零 subprocess**：后端不 `fork` / `exec` 任何进程（含 `asyncio.create_subprocess_*`）。`npx` 是
  一个会联网下载并执行任意 npm 包的入口，把它请进后端等于把「谁的代码在本机跑」交给一个第三方
  仓库名。
- **无 Node 运行时依赖**：产品只在开发期用 `node --test` 跑前端用例，运行期不依赖 Node / npm。
  要求用户装 Node 才能装技能会把一个可选工具变成硬前提。
- **出网必须显式开启**（ADR-0026）：`npx` 的下载是出网动作。ADR-0026 的口径是「出网是配置事实，
  不是默认能力」，而一个隐式的包下载无法落进那套确认纪律。

因此 Studio **不在界面上展示命令**，也不执行它：执行留给人在终端里做（`npx skills add
<owner/repo> -g -a codex -y` 这类命令仍可用，但它属于**外部 CLI 自己的文档**，不是本产品的一格界面）。
应用这一侧只有「读 `~/.agents/skills` 这个落点」：导入区一个下拉（点一条 = 立即导入）、一个「刷新」
按钮（重扫候选）、一个「全部导入」按钮（对当前可导入且未安装的候选逐个走同一条 `POST /api/skills`）。

事实修正（本票）：本 ADR 原文写「Studio 只展示可复制的命令（`npx skills add …`，ASCII 常量）与一句
说明」，并随后记「刷新候选按钮已删除，改为重新打开详情时自动重扫」——这两句都已被界面演进取代。
`SKILL_INSTALL_COMMAND` 常量、命令块与它的说明、以及「重新打开详情才重扫」的口径**都已删除**：
界面不再教人敲命令（§二的三条边界不变：零 subprocess、无 Node 运行时依赖、出网显式开启），
重扫改为导入区自己的「刷新」按钮（`GET /api/skills/candidates`，只读）。

## 三、与既有 ADR 的关系

- **ADR-0026（Agent 联网是显式开启的出网能力）**：本 ADR **不新增任何出网面**。`GET /api/skills/candidates`
  只读本机文件系统；`POST /api/skills` 只复制本机字节。下载第三方包这一步发生在**应用之外**的终端里，
  由人显式执行——那正是 ADR-0026 要的「显式」。因此本票**不**需要新的 provider 确认档，也**不**给
  后端加网络请求。
- **ADR-0031（Agent 家目录是项目边界之外的全局层）**：本 ADR 只加**导入源**，不改字节正本与装配
  两层。`skill` 表仍是元数据 + 内容 hash；成员家目录仍是唯一正本；装配顺序仍是「成员家目录 >
  全局公共库」；`~/.agents/skills/` **不是**第三层，它不参与装配，只在导入那一刻被读一次。
  路径安全沿用同一条守卫（`resolve_global_read_path`，以来源根自己的 `realpath` 为根），因此
  根外 symlink 祖先与根外目标一律拒绝。
- **ADR-0009（文案分两层）**：候选条目的「不可导入原因」由**后端**按语言偏好渲染
  （`alibot.i18n.render`），界面侧新增文案进前端词条表两份取值。导入区的命令块已随本票删除，
  因此再没有「不进词条的 ASCII 命令常量」这一类取值。
- **ADR-0015（迁移只前进）**：本 ADR **不改 schema**，不新增迁移步骤，`SCHEMA_VERSION` 不动。

## 四、命名

`~/.agents/skills/` 是**外部 CLI 的落点**（import source），不是「市场」「商店」，也不是本应用的
全局层（那是 `~/.alibot`，ADR-0031）。术语沿用 `CONTEXT.md` 的 **Skill** / **成员家目录** /
**全局公共库**；`npx skills` 一律写明是**外部 CLI**。
