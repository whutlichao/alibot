# 旧页面退役：工作台只剩 v2，构建产物改为构建时生成

ADR-0038 用 strangler 方式把前端迁到 Vue，并留下两条刻意的保险：**产物入库**（§一）与
**旧用例族保留**（§四）。阶段 A / B / C 全部合入 `main` 之后，旧页面 `/studio/`
（`app.js` 10,634 行 + `index.html` 880 行）不再承载任何已迁面的退路，它只剩「万一 v2 坏了」这一角色。
本 ADR 记录用户于 2026-10-27 批准的**退役决定**：删掉旧页面与它的 389 条用例，并把产物从入库改成
构建时生成。

本 ADR 只记录决策与边界。删除清单、覆盖映射表与逐条读数在票 #318 的 Answer 与 PR 正文里。

## 决策记录

- **Context**：三条事实让旧页面的收益归零、代价变实。
  ① v2 已覆盖全部已迁面（阶段 A/B/C 合入 `main`），旧页面没有任何「v2 没有而旧页面有」的功能；
  ② 保留它意味着**每次改共享正本都要验两套页面**（`i18n.js` / `markdown.js` / `app.css` /
      `product-tokens.css` 是两版共用的一组正本），而旧页面那套 DOM 用例族（24 文件 / 389 用例）
     是门禁里最长的一段；
  ③ 产物入库让仓库里长期躺着一份生成文件：它的 diff 噪声会掩盖真正的源码改动，而「产物与源码脱节」
     只能靠一条指纹守卫事后发现，不能从构造上消除。
- **Decision**：
  1. **删除** `app/alibot/studio/app.js`、`app/alibot/studio/index.html`、`app/tests/*.test.cjs`（24 个）
     与只被这族消费的 `app/tests/approval_dom_harness.cjs`；
  2. **保留**四个共用正本（`i18n.js` / `markdown.js` / `app.css` / `product-tokens.css`）**一行不动**：
     v2 页面用绝对路径加载它们，删任一个立刻白屏；
  3. 入口统一到 **v2**：`/` 与 `/studio` / `/studio/` 都 redirect 到 `/studio/v2/`；
  4. **产物不入库**：`.gitignore` 忽略 `app/alibot/studio/v2/`，`git rm -r --cached` 让已有的
     产物退出跟踪；
  5. **产物由构建时生成**，三个落点各自兜住自己那条路径（见下一节）。
- **Consequences**：产品形态变了——`python -m alibot` 现在**要求先有产物**。这条必须写进文档，
  否则第一次 `pip install -e app` 就会撞上一张 404 页面而不知道要跑什么。

## 一、被推翻的两条 ADR-0038 决策

| ADR-0038 | 原决策 | 本 ADR |
| --- | --- | --- |
| §一 | 产物**入库**，因为 `pip install -e app` 不跑 npm | **不入库**，改由三个构建落点生成（见 §二） |
| §四 | 旧用例族**保留**，因为旧页面仍是可用入口 | **删除**，覆盖点逐条映射到 Vitest 用例族 |

ADR-0038 的 §二（不用 `innerHTML` / `v-html`）、§三（正本资产不复制）、§五（迁移期间的入口与
「不假装」）、§六（被否的方案）**仍然有效**，本 ADR 不动它们的结论。ADR-0038 §一 / §四 已在原文
做了最小事实修正并指回本文件（历史决策不就地改写）。

## 二、产物为什么不再入库，以及谁负责生成它

`pip install -e app` 确实不跑 npm——ADR-0038 §一 的判断没错，但它的**结论**选了一条最贵的兜底：
把产物塞进仓库，于是每次改源码都要手工重建并提交。换一种兜底更便宜：

- **运行时依旧零 Node**（ADR-0038 §一 的硬约束不变）：v2 页面加载的是静态文件，起服务不需要 Node。
- **构建期允许依赖**，且「谁需要产物，谁就在自己的路径上建」：

| 路径 | 落点 | 判据 |
| --- | --- | --- |
| 本地跑门禁 | `scripts/check.sh` **头部**先 `npm run build` | 门禁不会因为「忘了构建」而红在与改动无关的地方 |
| CI | `.github/workflows/check.yml` 在 `npm ci` 与 `check.sh` 之间显式构建一步 | 构建失败在日志里单独成步，一眼看得出是哪一步红的 |
| 分发（wheel） | `app/hatch_build.py` 的 hatch custom build hook | `pip wheel` / `python -m build` 出来的包**一定**含 `/studio/v2/` |

`app/hatch_build.py` 是本 ADR 唯一新增的产品代码。它缺 node / npm / `node_modules` 时**报错退出**，
不静默打一个 `/studio` 是空的坏包——「装上了但打开 404」是最难定位的一类坏。它只对 wheel 生效：
sdist 是源码分发，产物该由安装者自己建。

## 三、产物新鲜度守卫换了判据

ADR-0038 §四 的守卫守的是「产物与源码不脱节」，因为产物入库时**唯一**的风险是有人改了源码忘了重建。
产物退出跟踪后风险变了，守卫的判据也跟着换（`app/frontend/tests/build-guard.test.js`）：

1. **产物存在**（原先不需要——它总在仓库里）。失败信息直接给修复命令
   `cd app/frontend && env -u NODE_ENV npm run build`，不让人去猜。
2. **产物由当前源码生成**：指纹算法**没变**，仍由 `build-info.js` 的 `sourceDigest()` 写、
   由守卫复算（同一个函数，不是两份实现）。指纹刻意不含时间戳，构建可复现。
3. **接线四条**：`.gitignore` 忽略产物目录、`check.sh` 在门禁前构建、CI 在 `npm ci` 与门禁之间构建、
   `pyproject.toml` 声明 hatch hook 且钩子真的调 `npm run build`。这是「命令清单是缓存、缓存会漂」
   那条既有教训的又一次落地：四个人工步骤变成四条机械判据。

## 四、旧用例族的覆盖去哪了

24 个 `app/tests/*.test.cjs`（389 用例）守的是旧 `app.js` 的 DOM 行为。它们**不是**被判定为无价值
而删除的——删除的前提是「覆盖点有接住者，或行为随页面一起消失」。逐文件映射表在票 #318 的 Answer 里，
每条写明接住它的是哪个 Vitest 文件。

两条**例外**必须单独说，因为它们守的东西**没有**随页面消失：

- **词条表的键集守卫**（原 `i18n_ui.test.cjs` 第 521 / 530 行的「两份语言表同键集、无空值、
  参数位一一对应」）：`i18n.js` 是 v2 唯一的词条正本，删掉这条守卫等于让正本失去唯一的机械判据。
  因此它**迁移**成 `app/frontend/tests/i18n-catalog.test.js`，读的仍是正本（间接 `eval` 装全局），
  不复制任何词条。
- **`app.css` 里没有中文文案**：`app.css` 也仍在服役，这一路跟着一起迁过去。

裸中文扫描的另外两个目标（`index.html` / `app.js`）随文件消失，判据随之作废——它们是**文件级**
判据，不是行为判据。

## 五、没有采用的替代路径

- **保留旧页面但停止维护**：两套页面共用四个正本，任何一次正本改动都要验两遍；「停止维护」在仓库里
  的实际含义是「有一套没人跑的用例 + 一个没人测的入口」，比删掉更贵。
- **产物入库 + `check.sh` 每次构建后比对再自动提交**：门禁不该有写仓库的副作用；而且这会让
  「构建产物」变成 CI 的 commit，把 review 注意力消耗在生成文件上。
- **把产物打进 sdist**：sdist 是源码分发，塞生成物会让「从源码构建」这条路失去意义。
- **在 `api.py` 里做「没有产物就现构建」的懒加载**：把 npm 拉进请求路径，且首次请求会阻塞几十秒。
  缺产物时**启动即报错**（`create_app` 抛一条带修复命令的 RuntimeError）更诚实。
- **保留 `/studio/` 作为「备用入口」指向旧页面**：旧页面已被删除，唯一能指向的就是 v2；
  于是 `/studio/` 做成 redirect——它是被用户记住过的地址，不能变成 404。
