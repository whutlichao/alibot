# 显示名每轮以身份句进 system prompt：内部名不变，空显示名即该段缺席

用户于 2026-10-24 人定：Agent 应当**知道自己的显示名**。此前 `display_name` 只出现在消息作者名
（`_author_name`）与 `TeamAssign` 的工具描述（`member_description`）里，system prompt 里没有一句
说「你叫什么」，模型只能从历史 assistant 消息的 `name` 字段间接推断。本 ADR 只记录「把显示名作为
一句身份说明每轮注入 prompt」这一个决定，不记录实施步骤。

## 决策记录

- **Context**：显示名是成员行的**配置数据**（`member.display_name`，见 `CONTEXT.md` 的**成员**
  与 **Agent 配置**词条）。它进入模型视野的两条既有路径都与「这一轮我是谁」无关：消息作者名是
  **别人**的名字，工具描述是**可选成员**的名字。于是模型对自己名字的认知是间接推断出来的，且
  在空历史的首轮完全不存在。ADR-0031 / ADR-0032 已经把规则与记忆按「全局层 + 项目层」分流，
  但身份本身一直是 prompt 的空白格。
- **Decision**：新增**一句话的身份说明**，由唯一的来源函数从成员行派生，**三处拼装点**每轮都插入
  同一句、同一位置：两段文件规则（全局基座 / 配置 / 项目补充）之后、`你的角色：` 之前。
  三处是单 Agent 轮次（频道 / DM / task / team 队长）、team 成员轮次、SOP 参与者轮次。
- **Consequences**：模型每轮都能稳定自知显示名，不需要从历史里猜；代价是 prompt 多一行，且这句
  只覆盖**显示名**——角色、规则、记忆的职责边界一概不动。

## 一、逐字措辞与单一来源

```text
你在工作台里的名字是「{display_name}」。成员与人类都用这个名字称呼你。
```

- 来源是 `app/alibot/agent_identity.py` 的 `identity_line(member) -> str | None`，**唯一**。三处
  拼装点只调用它，不各写一份字符串；`grep -rn "你在工作台里的名字是" app/alibot` 只命中该模块。
- 硬编码中文，与既有 `你的角色：`、`项目补充：` 等 prompt 文案同口径，**不进 i18n**：这些句子是
  给模型看的行为文案，不是给人切的界面文案。
- 位置固定：身份句是 `你的角色：{role}` **前面独立的一段**，不并入、不改写该行（既有测试与回应
  纪律的措辞全部保持原样）。

## 二、与 D10 的关系：内部名不变、不进 prompt

D10（ADR-0003：Agent 只有结构身份）不变：框架内部名仍是 `m-<member_id>`，它给事件归属与
`TeamAssign` 的成员解析用，是**机器事实**而不是人名。身份句只用显示名，`m-<member_id>` 不出现
在这句里，也不因此进 prompt。

不声明唯一性也是一条既有口径：成员显示名允许重复（`CONTEXT.md` 的**成员**词条），所以措辞是
「别人这样称呼你」，不是「你是唯一的名字持有者」。重名不会让这句变成一条不存在的事实。

## 三、空显示名 = 该段缺席

`display_name` 先 `str(...).strip()`；结果为空串时返回 `None`，**该段缺席**——不写空标题、不写
占位、不写「（未设置）」。这与两段文件规则的既有写法一致（ADR-0031 / ADR-0032：缺失 / 不可读 =
该段缺席，不写空标题）。库里 `create_agent` / `update_agent` 不接受空显示名，因此这条路径只在
配置数据被旁路写入或迁移遗留时生效，属于防御而不是常态。

## 四、与 ADR-0031 / ADR-0032 的关系

本 ADR **不改**家目录布局，也**不改** `AGENTS.md` / `MEMORY.md` 的职责边界：

- `AGENTS.md` 仍是**人定的规则**，由人维护、应用只读；身份句是**代码从配置数据自动派生**的一行，
  与它不同源、不同生命周期——身份句随成员行变化，规则随人改文件变化。
- `MEMORY.md` 仍是模型自己的记忆面；身份句不是记忆，不落库、不写文件。
- **不新增** `SOUL.md` 之类的新文件类型：身份是配置数据的**投影**，不是又一份要人维护的文档。

## 五、被否方案

- **让模型从历史 assistant 消息的 `name` 字段推断**：首轮无历史、名字漂移、沉默轮次不产生
  assistant 消息，都不成立。
- **把显示名并进 `你的角色：` 那一行**（例如 `你是「小明」，角色：工程师`）：改写了既有测试与回应
  纪律依赖的措辞，且把两件不同来源的事实（身份 vs 配置的 role）绑成一行。
- **直接用 `m-<member_id>` 当身份**：那是内部名，人不会这样称呼 Agent，会把机器标识泄漏进正文。
- **新增 `SOUL.md` 供人编辑身份**：多一份要人维护、会与 `member.display_name` 漂移的文件；本决定
  只需要一行投影。
- **只在单 Agent 路径注入**：team 成员与 SOP 参与者同样是「某个 Agent 的一轮」，漏掉它们会让同一个
  Agent 在不同路径下对自己名字的认知不一致。
