# 提醒是后端对象，不用浏览器本地存储

用户于 2026-10-16 把「提醒 reminders」并入本轮。原型把提醒存在浏览器里：`state.reminders` 加一次 `persist()` 就是 localStorage（`alibot-design-system/alibot-app.html:1013-1026`、`:1775`），后端没有任何提醒表或端点。

我们决定**反过来**：提醒落库，后端持有它是唯一正本，人类面提供增删读的端点。依据是本仓既有的那条边界——`CONTEXT.md` **工作台** 明写「业务状态的唯一正本是后端；前端不持正本」，而提醒是**有对象身份、可增删、跨刷新与重启应一致**的对象，不是观感状态。同一条纪律在未读 / 已读位置上已经这样执行过（`target_read` 落库而不是放浏览器），提醒没有理由例外。

被否的方案有两个：一是照原型放 localStorage（刷新后还在、换浏览器就没了，且与同一次交付里的**语言偏好**产生两套持久化规则，而语言偏好因为唤醒编排要在 HTTP 之外产出文案**必须**落库，见 ADR-0009）；二是只做前端内存态。两者都会让「提醒还在不在」这条事实取决于浏览器。

与「不落消息」的边界：提醒的增删**不落消息、不唤醒、不消耗预算**——它不是对话事实，`CONTEXT.md` **系统事件消息** 把「不由对话参与者说出的事实」限定在穿透加入与任务三个来源，提醒不进这张表。提醒与频道的关系是**归属**（提醒属于一个频道），不是 target 作用域：提醒不是消息面，因此不新增 target、不计未读、不参与唤醒。

代价是这一面从「一个弹窗」变成「一张表 + 若干端点 + 一个弹窗」，比原型贵；换来的是「提醒在哪台浏览器打开都还在」和一条与既有纪律一致的边界。具体表名、列名、端点路径与时间类型（原型的 `#rmTime` 只有 `type="time"`、没有日期与重复字段）属于实现细节，记录在 `app/specs/issue-60-spec.md` 的决策账与对应实施票。
