# 频道的归档与删除是两个软删除档位，不是状态机

仓库至今**没有删除或归档频道的入口**——`target` 表 DDL 的注释里明写「本仓没有删除频道的入口，也就没有
删除它的路径」。频道建了就只能留着，左栏只会越来越长。私信已有先例：Agent 被软删除后，对应的私信移进左栏
「已归档」段、只读、历史保留（`CONTEXT.md` 的**已归档私信**）。本 ADR 把同一套形状推广到频道，并补上删除。

用户于 2026-10-30 定下五条：①删除与归档是**两个独立动作**；②归档后的界面是左栏折叠段 + 只读；
③删除时历史**全部保留、不可见**；④归档频道的未读**不计入**左栏总未读；⑤入口位置——归档在频道头工具行
（当场执行），删除在频道设置弹窗底部的「危险区」（需二次确认）。
（**2026-10-30 的事实修正**：#344 按用户新决定把归档入口从频道头工具行移进频道工具 →「设置」页签的
危险区，与删除相邻。归档的语义**不变**：当场执行、可恢复、不弹二次确认；归档态只读、频道头只显示
取消归档。）

本 ADR 只记录决策与边界。逐条读数与覆盖点见票 #342 的 Answer 与 PR 正文。

## 决策记录

- **Context**：三个事实共同决定了形状。①频道的生命周期目前只有「创建」这一端，左栏的单调增长没有出口；
  ②已有 `member.deleted_at` 这条路——软删除、行保留、读路径过滤——它对本仓的**消息 append-only**
  （ADR-0001）是唯一相容的删除形态；③「归档」与「删除」在人类面上做的是两件事：前者是整理（也许过几周
  又要用），后者是丢弃（不可逆）。把两者压成一个动作，要么让「整理」变成不可逆，要么让「丢弃」变成可撤销
  的半吊子。
- **Decision**：`channel` 表加两个可空时间戳列 `archived_at` / `deleted_at`，schema `25 → 26`（纯 `ADD
  COLUMN`，不重建表、不回填）；三个端点 `POST .../archive`（幂等）、`POST .../unarchive`（幂等）、
  `DELETE /api/channels/{id}`（不幂等，二次 404）；归档 = 频道面只读，判定收在一个私有方法里。
- **Consequences**：人类面第一次能「把频道收起来」和「把频道扔掉」。代价是一对同形但语义不同的列需要读路径
  各自解释（列表 / `get_channel` / 总未读 / 全局搜索四处），本 ADR §一 把它们列全。

## 一、两个档位，不是一条状态机

| 列 | 语义 | 可恢复 | 写入口 | 读路径 |
| --- | --- | --- | --- | --- |
| `archived_at` | 移出左栏活跃段，频道面只读 | 是（`/unarchive`） | **五个整体拒绝** | 照常可读，载荷带 `archived_at`；**仍可被搜索**；**不计总未读** |
| `deleted_at` | 终态，频道对人类面「不存在」 | 否 | 全部 404 | 列表 / `get_channel` / 消息 / 配置 / 预算 / 事件流一律 404；**全局搜索过滤它的消息** |

两列**可同时演进**：`archived_at` 非空的频道仍可被删除（删除时顺手清掉 `archived_at`——终态不再需要
「移出活跃段」这个区分）。这不是状态机的三个状态，而是**两个独立的布尔事实**；把它们合并成 `status ∈
{active, archived, deleted}` 会逼出一个谎：已删除的频道在数据里既不是「归档中」也不是「活跃」。

四个读路径的落点：

1. `CHANNEL_SELECT_SQL` 的 `WHERE` 加 `c.deleted_at IS NULL` ⇒ 列表不返回、`get_channel` 自然 404，
   **既有调用点全部继承**（配置 / 预算 / 消息 / 事件流），不需要各自再判一次；
2. `UNREAD_TOTAL_SQL` 外层加 `LEFT JOIN channel c ON c.id = t.id` 与
   `(t.kind <> 'channel' OR (c.archived_at IS NULL AND c.deleted_at IS NULL))`——
   **`UNREAD_WHERE_SQL` 一个字都没改**（未读只有一个 SQL 形状，ADR-0004 决策 7 不变）；
3. 全局搜索的 `SEARCH_ALL_HITS_SQL` 加 `(t.kind <> 'channel' OR c.deleted_at IS NULL)`：
   已删除频道的消息消失，**归档的仍可搜**；
4. `_channel_payload` 恒带两列（列表里 `deleted_at` 恒 `null`，保留它是为了让前端只有一套形状判断）；
5. **任务面**：任务看板（`GET /api/tasks`）与任务搜索命中（`SEARCH_TASK_HITS_SQL`）同样按
   `channel.deleted_at` 过滤。删除是「频道对整个人类面不存在」，而看板卡片与搜索行都带着
   「#频道名」并指向那个频道——不过滤就会出现「一条能点开、但它的频道 404」的行。
   与消息同一条口径：**行不删、按 id 直接读仍可用**（`GET /api/tasks/{id}` 与其线程），
   只是频道层面的两个入口不再列出它。**归档不触发这一条**：归档频道的任务照旧在看板与搜索里。

第 5 条是「合同本身的缺口」在实施中被补上的那一条：票面只列了列表 / `get_channel` / 总未读 / 搜索
消息四个落点，实现时发现任务的两个入口同样会泄漏已删除频道的名字与可点链接。

## 二、归档 = 频道面只读，判定只有一个落点

五个既有写入口改调 `WorkspaceService._require_writable_channel()`：频道消息、频道配置 `PATCH`、回应预算
`PATCH`、加入成员、新建任务。它们各自原本就调 `get_channel()` 做 404 早退，因此这次改动是**把那一次读
换成一次既做 404 又做归档判定的读**——判定不会漂成两份。

**刻意边界**（它们不是缺陷，写在这里以免下一个人「顺手修掉」）：

- **任务面不受影响**：`send_task_message` / `update_task*` / 任务线程的任何写入都**不**调该判定。
  归档的是「频道这个对话面」，而任务的生命周期由任务自己的五态表达；把归档理解成「冻结整个工作区」
  会让归档频道的任务永远卡在一个状态里。
- **在飞轮次不打断**：归档不取消已开始的 Agent 轮次，它自然结束；此后的新唤醒已被写入口拒掉
  （唤醒的唯一入口是人类面写入）。
- **提醒到点不拦**：归属归档频道的提醒到点仍落一条 `system` 消息——那是后端系统事实，不是人类面写入，
  且它不唤醒、不计未读（归档频道也已不计总未读）。
- **标读 / `GET` / SSE 不受影响**：它们只读，归档频道的历史仍可读（这正是归档与删除的分界）。

## 三、删除是终态软删除，一行都不删

`DELETE /api/channels/{id}` 只写 `channel.deleted_at`：`channel` 行、`target` 影子行、消息、`target_member`、
任务、`target_budget`、`round_outcome` 全部保留，读路径按这一列过滤。因此：

- **消息 append-only（ADR-0001）不受影响**：本仓仍然没有任何修改或删除消息的路径；
- 删除**不幂等**：第二次给出「已不存在」的 404，与 `DELETE /api/agents/{id}` 同口径；
- 三个动作都是**配置类写路径**：不落消息、不唤醒、不消耗预算、不开世代。

## 四、被否的方案

- **物理删除整条频道**（连同消息、任务、成员行）。否掉的理由：它要新增一条「删除消息」的路径，直接与
  ADR-0001 冲突；而消息的取证价值恰恰在于「删除之后它还在」。软删除用读路径过滤买到了同一份人类面效果，
  代价只是库里多一行不可见的记录。
- **删除即归档**（一个动作、一个档位，删除就是「不可见的归档」）。否掉的理由：两者的人类意图不同——
  归档是「先收起来，可能还要用」，删除是「不要了」。合并之后，归档态要么被说成不可恢复（人不敢用），
  要么删除被说成可恢复（人被误导）。两个档位让界面上的两句话都能说实话。
- **加一个 `channel.status` 枚举**。否掉的理由：它与 `member.deleted_at` 的既有形态不一致（本仓所有
  软删除都是「一个可空时间戳」），而枚举要读路径在四处各自翻译成布尔；时间戳同时留住了「什么时候做的」
  这个审计事实。
