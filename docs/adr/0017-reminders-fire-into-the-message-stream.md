# 提醒到点落一条 `system` 消息：它不唤醒、不耗预算，但它是「系统事件消息」的第四个来源

用户于 2026-10-17 人定：提醒要新增**到点触发**能力。到点时**后端落一条 `kind='system'` 消息**进归属频道的消息流，
**不唤醒任何人、不消耗预算**。本 ADR 记录这次裁定与它的边界。

## 首段：与 ADR-0012 的逐句取代关系

本 ADR **取代 ADR-0012《提醒是后端对象，不用浏览器本地存储》的三句**，其余全部**仍有效**。
ADR-0012 正文**一字不改、不加 `Status` 行**——沿用本仓既有惯例（ADR-0007「本 ADR 不修订或取代 ADR-0002」；
ADR-0010「**不改 ADR-0005 原文**……就地改写会让『当时为什么这么定』消失」；ADR-0015「ADR-0004 正文**一字不改**」）。
取代关系只在这里、`CONTEXT.md` 的**提醒** / **系统事件消息** / **到点**词条、以及
`app/specs/reminder-trigger-design-notes.md`（设计正本）里声明。

| ADR-0012 的句子 | 处置 |
| --- | --- |
| 「我们决定**反过来**：提醒落库，后端持有它是唯一正本，人类面提供增删读的端点。」 | **仍有效**，并被本 ADR **加强**：到点事实也由后端产生，前端更不持正本 |
| 「被否的方案有两个：一是照原型放 localStorage……；二是只做前端内存态。」 | **仍有效**（那次取舍与被否方案的记账不动） |
| 「提醒的增删**不落消息**」 | **仍有效**：增删仍是人类面配置动作，不产生任何消息 |
| 「不唤醒、不消耗预算」 | **仍有效**：到点落的是 `system` 消息，`system` 本就不唤醒、不耗预算（`orchestration.py:204-206`）——这是**继承**既有口径，本能力**没有**给 `system` 造任何例外 |
| 「**它不是对话事实**」（前半句） | **被取代**：到点产生的是「不由对话参与者说出的事实」，因此它**进系统事件消息表** |
| 「`CONTEXT.md` **系统事件消息** 把「不由对话参与者说出的事实」限定在穿透加入与任务三个来源，提醒不进这张表」（后半句） | **被取代**：提醒的到点事实成为**系统事件消息的第四个来源** |
| 「提醒不是消息面」 | **被取代**：到点产物是一条消息 |
| 「因此**不新增 target**」 | **仍有效**，且本 ADR 用「无归属提醒不落消息」这条边界把它守住（见 §一） |
| 「**不计未读、不参与唤醒**」 | **仍有效**：`system` 消息不计未读（`db.py:536` 的 `UNREAD_WHERE_SQL`）、不唤醒（`orchestration.py:204-206`）、不进搜索命中 |
| 「…端点路径与**时间类型**（原型的 `#rmTime` 只有 `type="time"`、没有日期与重复字段）属于实现细节」中的**时间类型**那半句 | **被取代**：时间语义（一次性「日期 + 钟点」、本机本地时区）从「实现细节」升为**规格级决定**（§二） |

**ADR-0012 的核心决定（提醒是后端对象而不是浏览器存储）没有被任何一条取代。** 本 ADR 只改了「到点发生什么」这一个面。

## 一、到点的产物是一条 `system` 消息，而且它必须落在一个 target 上

到点时，后端为每一条**已到点且未投递过**的提醒落**一条** `kind='system'` 消息。作者恒为 **owner**——提醒是本机用户
给自己设的，不是任何对话参与者说出来的话。人类面**没有**创建 `system` 消息的端点（`api.py:34-35`），这条消息只能由后端投递器写。

**为什么一定是消息、而不是前端算出来的标记。** 唤醒编排的唯一触发点是「消息**成功落库之后**」的 `notify(target_id, from_seq)`
（`orchestration.py:183-206`），而 `notify` 的第一件事就是按 `from_seq` 读库里那条消息；`append_message` 本身也要求一个真实 target
（`db.py:2181-2219`）。这条结构事实的推论是：**「唤醒一个 Agent」必然蕴含「先落一条消息」**。于是「落消息」是「唤醒」的**构造性前置**
——选它保留了以后要不要唤醒的余地，而选「纯前端标记」会把这两条路一起锁死，还让前端时钟变成「到点发生过」这件事的事实来源。

**被否：唤醒归属频道的 Agent 跑一轮。** 它必然包含「先落消息」，额外代价是每一次提醒消耗一次 **agent→agent 跳**
（ADR-0002 的每个**人类世代** 3 跳上界，`db.py:112`）——一次性设 5 条提醒就能吃掉一个世代的全部预算。此外 `channel_id` 为空时
根本没有唤醒面；而且**唤醒是注意力不是命令**（`CONTEXT.md` **唤醒**），「到点提醒我」不需要任何人的反应。

**被否：纯前端提示 / 只在读路径算 `due` 标记。** 两者都让「到点已经发生」取决于有没有人打开浏览器，直接违反 `CONTEXT.md` **工作台**
「业务状态的唯一正本是后端；前端不持正本」。

**必须一起接受的代价：`channel_id` 为空时无处可落。** `reminder.channel_id` 今天**可空**（`db.py:386`），空 = 不归属任何频道
（空工作台 / 私信视图下也设得成提醒），而消息必须有一个 target。本 ADR 的处置是**显式分叉**：
**有归属 ⇒ 落一条 `system` 消息；无归属 ⇒ 到点只写已到点标记、不落消息。** 这条分叉是能力的一部分，不是遗漏。

**被否：把 `channel_id` 改成必填。** 会破坏已发布的写路径契约（「空工作台也能设提醒」是当前合法状态），且存量无归属行没有自然归宿。
**被否：给提醒造一个专用 target 或自动建一个「提醒」频道。** 这推翻 ADR-0012 的「不新增 target」，代价是为一个备忘列表
造出第四种 target 或一个假频道。**被否：就近落到 owner 最近活跃的频道。** 落点取决于运行时状态，「我 9 点的提醒落进了哪个频道」
变成要查才知道的事。

## 二、时间语义是一次性的「日期 + 钟点」，按本机本地时区解释

`reminder.time` 从 `HH:MM` 扩为 **`YYYY-MM-DD HH:MM`**，语义是**一次性**：到点后这条提醒就用完了，**不做重复**。

**为什么不做重复。** 本仓**已经**有一个承载「重复做一件事」的对象——**任务**（可变行 + 状态机，`CONTEXT.md` **任务**）。
给提醒再加一层重复语义，会让「提醒 vs 任务」的边界消失，并立刻要求回答「错过 3 天要不要补 3 次」。**为什么必须带日期。**
不带日期就表达不了用户最自然的请求「明天早上 9 点提醒我」；而且一次性 + 明确日期让「错过」有确定判据（那个时刻已过、且未投递过）。

**时区：到期判定用本机本地时间。** 本仓是**单用户本机进程**，用户写「09:00」时想的就是他墙上的钟；把 UTC 摊给用户是自己造一条换算义务。
**这条差异必须写进规格**：`created_at` 是 **UTC 审计时间戳**（`db.py:756-758` 的 `utc_now()`），到期时刻是**本地时间**，
两者在库里**不做换算比较**——只在需要比较时（精度判据）才换算到同一时区。

**被否：一律 UTC。** 用户要自己换算，且夏令时切换时他的 09:00 会漂。**被否：每条提醒带一列时区标识。** 为单用户本机场景
新增一列 + 一档界面 + 两份词条，收益为零（本仓没有多时区用户）。

**代价**：同一张表里两种时间口径。**跨时区搬数据目录后到期语义会漂**——这条不写清就会变成下一个「为什么 09:00 不响」的事故。

## 三、`fired_at` 是唯一的「已投递」标记；错过在 24 小时窗口内补投一次

新增可空列 **`fired_at`**：`NULL` = 还没到点。到点后行**保留**，写入时刻戳。

**为什么保留行而不删。** 「这条提醒响过没有、什么时候响的」是一条事实，删行就丢了取证面——本仓同族纪律是「状态在行上、历史不可丢」
（`CONTEXT.md` **任务状态** 是行上字段、**消息** append-only）。更直接的理由是：**删行让补投无法实现**——「至多补投一次」
需要一个已投递标记，删了就无法区分「还没投」与「投过了」。

**错过怎么办：补投一次，24 小时窗口。** 本仓是单用户本机进程（`python -m alibot` 才跑，**不常驻**），到点时进程没在运行是**常态**。
启动先扫时：**距到期 ≤ 24 小时**的已过点未投提醒 ⇒ 补投一条 `system` 消息（正文用**补投**措辞）并写 `fired_at`；
**> 24 小时** ⇒ **只写 `fired_at`、不落消息**，人类面标成**已错过**。

**「至多一次」是构造性的**：已写 `fired_at` 的行永不再被任何路径投递——连续触发投递器两次，第二次改动 0 行，可被断言。

**被否：跳过并标 `missed`。** 等于「你关机了所以提醒作废」，而关机是本仓常态不是异常；而且它需要一个第三态状态值。
**被否：不补也不标。** 一次性语义下「下次到点」不可达 ⇒ 提醒永久静默且界面看不出为什么。
**被否：补投但不设窗口。** 关机三个月后开机，消息流被历史噪音淹没。
**被否：三态 `pending` / `fired` / `missed`。** `missed` 在本设计里**不可达**（窗口外也写 `fired_at`）——一个不可达的状态值是死代码，
还会诱导实现去「支持」它。人类面的「已错过」是由 `fired_at` 与到期时刻之差**推导**的呈现，不是第三个状态。

## 四、调度落点是一个可注入的到期投递器 + 进程内轮询

判定「到点」的不是既有编排，也不是 `ThreadScheduler`，而是一个**窄接缝**：输入「当前时刻」，输出「这一批的投递后果（准点 / 补投 / 窗口外 / 已投过 / 无归属）」。
生产实现是进程内后台线程按固定间隔轮询 + **启动先扫一次**；测试注入手动触发，直接喂时刻。

**接缝深度**：接口宽度 = 1 个输入 + 1 个输出；隐藏的实现复杂度 = 轮询节奏、事务边界、`fired_at` 的幂等写、时区换算、
24 小时窗口判定、与 `EventBus` 的发布顺序。判据是「用 3 行的测试替身能否覆盖全部分支」——能，深度就合适。

**精度上界 = 轮询间隔 = 30 秒**，写成可观察判据：对**准点投递**，`system` 消息的 `created_at` 与到期时刻之差 ≤ 30 秒（**补投除外**）。
`POLL_INTERVAL_SECONDS` 是**常量 + 一条单元断言**，轮询间隔**不作为行为测试的对象**——行为测试走注入时刻，一行测试都不真等 30 秒。

**线程生命周期接进既有 shutdown 顺序**（`api.py:331-345`：停事件流 → 停 scheduler → 关库）：新线程必须收口在「停 scheduler」之前，
否则关库之后它还能拿到库句柄。

**被否：复用 `ThreadScheduler`。** 它的语义是「把一轮提交到线程池去跑」（`orchestration.py:70-88`），**没有「何时提交」的能力**——
复用它其实是复用线程池而不是调度，还会让人误以为唤醒编排已经由到点驱动。**被否：`Timer` 睡到最近到期时刻。** 系统休眠 / 时钟变化后
不可靠；「新增一条更早的提醒」必须打断并重排定时器；它把「错过」处理成「睡过头」，与补投语义打架。**被否：读路径顺带算。**
把「到点」变成「有人读才有」，D3 的补投永远无法在无人打开浏览器时发生。**被否：轮询间隔做成可配置项。** 为一个单用户本机场景
新增一档设置面（`CONTEXT.md` **工作区设置** 明写「本轮只有明确列出的三档」），且配错了的表现就是「静默不响」。

## 五、schema 号取 13，还是一次时间语义的一次性收窄

`SCHEMA_VERSION` 12 → **13**，并登记 **`MigrationStep(12, 13, ...)`**（链连续性不变量要求链连续覆盖到本代码版本，`migrate.py:664-682`）。

**取 13 的依据**：号段的判据是「**必须高于当前 main**」（`db.py:44-58` 的记账正本，`9 → 11 → 12` 那次争号得出的结论），
不是「任意取个更大的数」。`main` 是 12、全部分支最大也是 12、`git log -S"SCHEMA_VERSION = 13"` 零命中 ⇒ 13 是满足判据的最小号。
（取 14 只会让后续票少一个号且没有任何收益。）

**列改动**：`time` 形状改为 `YYYY-MM-DD HH:MM`；新增 `fired_at TEXT`（可空）。**存量 `HH:MM` 行统一解释成「迁移执行当日」的该钟点**，
`fired_at` 补 `NULL`。

**为什么是「迁移执行当日」而不是「下一个该钟点」。** 后者让结果**依赖迁移执行的时刻**——同一份备份在 08:00 迁与 16:00 迁会得到
两个不同的到期日，不可复现、难以写测试；前者是**唯一不依赖运行时状态**的解释口径。

**必须一起接受的代价（本 ADR 的记账栏）**：这是**时间语义的一次性收窄**——用户原来的「每天 9 点」在迁移后变成「迁移那天 9 点」。
它不丢数据行，但**改变了行的含义**。因此迁移报告必须给出**被改写的行数**。

**被否：加 `due_date` 列而不改 `time` 形状。** 两个列表达一个事实（`time` 永远 `HH:MM`、`due_date` 永远日期），读写都必须双列同步。
**被否：不 bump 版本、把新列塞进既有的 `_step_7_to_8`。** 这是**不 bump 版本却改 DDL**：已迁到 13 之前的库与新建库的 `reminder` 形状
会不一致，而**版本闸门只比版本号看不出来**——正是 ADR-0015 要消灭的那类事故。

## 六、人类面：两个原生输入、状态后缀、指示点只表示「还有事等着」

1. **新增控件 = `<input type="date">`（默认今天）+ 既有 `<input type="time">`**，提交时后端起拼成一个到期时刻。
   **这是对原型的显式偏离**：原型与产物现在都只有 `type="time"`（`alibot-design-system/alibot-app.html:1579`、`app/alibot/studio/index.html:662`）。
   被否：`type="datetime-local"` 单控件（一个控件塞两个语义、跨浏览器日历弹层形态不一、无法分字段校验）；
   保持只有 `type="time"`（本 ADR §二 的裁定无法表达）。
2. **列表行加状态后缀**：待响 = 到期时刻；已到点 = 「已提醒」；已错过（超 24 小时）= 「已错过」。**只用既有档位 token，不加新色位**
   ——**视觉契约**的 token 名集合是承诺，且已到点**不是错误**、不该用 `--error`。**到点不计未读**：`system` 消息既有的「不计未读」
   口径不为本能力开口子（未读是 owner 的「有多少话要对我说」的读数，一条系统事实混进去会让这个读数失真）。
3. **rail 指示点判据改为「有未到点的提醒」**：`state.reminders.length === 0`（`studio/app.js:789-793`）→
   `state.reminders.some(r => !r.fired_at)`。指示点的语义是「有一件事还等着发生」；保持旧判据会让提醒响过之后圆点永远亮着，
   变成一个「历史计数器」。

**用户可见文案的两层归属（ADR-0009，不许有第三层）**：

| 文案 | 层 | 载体 | 为什么在这一层 |
| --- | --- | --- | --- |
| `system.reminder.fired`（准点投递） | 后端第二层 | `app/alibot/i18n.py` 两份词条 | 它是**落库的 `system` 消息正文**，由投递器在 HTTP 请求之外写入，**没有请求头可读** ⇒ 只能按库内语言偏好渲染（ADR-0009 的决定性理由）；落库后是 append-only 取证面，**历史不回溯** |
| `system.reminder.fired_late`（补投） | 后端第二层 | 同上 | 同上；且准点与补投是两个落库路径 ⇒ **必须是两个键**，不能靠参数区分 |
| `reminder.dateLabel`（日期输入的可访问名） | 前端第一层 | `app/alibot/studio/i18n.js` 两份词条 | 界面静态文案，只出现在浏览器里、随语言偏好即时重渲染 |
| `reminder.stateFired` / `reminder.stateMissed`（行状态后缀） | 前端第一层 | 同上 | 它是**呈现**不是落库内容；同一个 `fired_at` 在不同语言下应显示不同说法 |

**同一条文案不许两边都登记。** 被否：后端返回文案键 + 前端渲染（库里的 `system` 行不再人类可读，丢可搜索性与取证面，ADR-0009 已否）；
前端自己拼「已提醒」并存进消息正文（落库正文取决于写入时浏览器语言，与「语言偏好读库」冲突）；
两层都登记同一条文案（第三层，明确违反 ADR-0009）。
