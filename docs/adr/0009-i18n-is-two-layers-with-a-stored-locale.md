# 双语机制分两层，语言偏好落库而不是放在浏览器里

用户于 2026-10-16 人定：「语言切换」是完整 i18n、全量双语（简体中文 / English），而且**后端生成的用户可见文案也要双语**（任务线程 `system` 消息、远端数据流告知、HTTP 错误文案）；机制（后端按语言返回 vs 返回文案键由前端渲染）由实施方取证后定。本 ADR 就是那次取证后的决定。

**一、文案分两层，不许有第三层。**

- **结构化状态词**（`round_outcome.status` 的五个词、四态**状态点**、任务状态、结果摘要）：后端只给**词**，前端按**词条**渲染。今天已经是这样（Studio 的 `OUTCOME_SUMMARY` / `SUMMARY_STATUSES` / `TASK_STATUS_LABEL`），本轮不动这条。
- **后端生成的自然语言**（HTTP 错误的 `message` 与 `fields`、落库的 `system` 消息正文、`round_outcome.reason`、Agent 的 `enabled_reason`、远端数据流告知文案）：**后端按当前语言偏好渲染**。

被否的替代方案是「后端返回文案键 + 参数，前端渲染」。理由：这些文案的落点本身就是**文本正本**——`system` 消息一落库就是 append-only 的取证面（搜索、审计、历史回看都读它），HTTP 错误今天也带人类可读的 `message`（机器判别另有 `code` 与 `fields`）。改成「键 + 参数」会让库里的记录不再是人类可读文本，并把措辞权在前后端边界上搬来搬去；这与 #35 用同一个理由否掉「把语义塞进 `reason` 自由文本」是同一类取舍——两处都不造半结构化协议。

**二、语言偏好落库，不放浏览器。** 它是工作区级的**配置类**取值，人类面可写、后端可读（与 ADR-0007 同族：人类面可以写配置，不得写用量类事实）。决定性理由不是一致性偏好，而是**可用性**：写 `system` 消息与 `round_outcome.reason` 的是**唤醒编排**，它跑在 HTTP 请求之外（后台线程 / 测试的手动调度器），**没有请求头可读**。偏好若只存在浏览器里，后端在这些产出点根本无法确定该用哪种语言——只能猜或退回源语言，那正是「全量双语」要求排除的。前端启动时读该偏好并按它渲染，切换语言时写回。

**三、历史不回溯。** 已落库的 `system` 消息保持写入时的语言：**不回填、不编辑、不迁移**（ADR-0001 的 append-only）。已知代价是切换语言后旧系统消息仍是原语言；要「历史随语言重渲染」就得把历史正文结构化并回填，那是另一个决策，本轮明确不做。

**四、源语言是简体中文。** 设计系统包自己声明 UI locale 为英文以外的唯一语言（`alibot-design-system/SKILL.md:145`、`DESIGN.md:269`）。本轮把该声明读作「**源文案**的语言与语气规范」：简体中文仍是源语言，英文是同一集合的第二语言取值，品牌名 / 代码 / 模型标识 / 标识符按包内规则保持原样。包内那句话需要一次**包内修订**（设计系统包有自己的写面与编号空间），本仓的 app 层不静默改写它——这处冲突与处置已登记在 `app/specs/issue-60-spec.md` 的 Out of Scope。
