# 附件是独立对象，字节落本机数据目录、库里只存元数据

用户于 2026-10-16 人定：composer 的附件按钮**做真上传**（新增附件存储 + 消息附件关联 + 渲染），而不是像原型那样只弹一句「附件原型占位」。原型的附件按钮本身没有任何数据面（`alibot-design-system/alibot-app.html:1799`），因此这是一次能力新建，必须先定存储契约。

我们决定：

- **附件是独立对象**，落一张新表（元数据：原文件名、大小、MIME、相对路径、创建时间、以及可空的 `message_id`）。字节**不进** SQLite：单文件库是这个仓的业务正本与备份单位，把二进制塞进去会让库体积、备份与损坏半径一起失控。字节落**本机数据目录**（`app/alibot/db.py:44-46/487-492`：`ALIBOT_DATA_DIR` 可覆盖，默认 `~/Alibot`）下的独立子目录，库里只存**相对路径**，于是整目录可整体搬迁。
- **两步上传**：人类面先上传拿到附件标识，再随消息提交时绑定，绑定与消息落库**同一事务**。理由是本仓的消息**append-only**（`CONTEXT.md` **消息**、库级触发器兜底）——消息一旦落库就不能再挂东西，附件必须在创建那一刻就绑定好。被否的替代方案是「在发送请求里内联 multipart 一次性完成」：它让消息写入路径与文件写入路径在同一事务里互相等待，且一旦文件写入成功而消息落库失败，就留下一个无人知晓的字节垃圾。
- **未绑定的附件 = 未发送的草稿**，允许存在，读取面只暴露**已绑定**的附件。因此不需要后台清理器，也不需要「上传即消息」的伪事务。
- 附件**不可变**：上传后不改内容、不改名、不提供覆盖；删除跟随消息的 append-only 纪律——**没有**删除附件的端点（与消息同口径：本仓没有删除消息的路径）。附件也**不进搜索**（`CONTEXT.md` **搜索命中** 的命中本体仍是文本），并且**不进成员面**（ADR-0003：Agent 的动作不经 HTTP；本轮不把附件内容加进 seam 的输入，那是另一个决策）。
- 大小与类型上限在**人类面**拒绝（可读原因），与既有 HTTP 面同口径：本机单用户、无鉴权。工具行只出现在**主 composer**（频道与 DM）——原型的任务线程回复框只有提示与发送键（`alibot-app.html:775-780`），本轮不替它新增按钮。

具体表名、列名、端点路径、上限数值与文件名策略属于实现细节，记录在 `app/specs/issue-60-spec.md` 的决策账与对应实施票。
