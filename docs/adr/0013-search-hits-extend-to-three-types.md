# 搜索命中扩为三类，判定仍唯一落在后端

`CONTEXT.md` **搜索命中** 目前把「命中」定死为**一条消息**加它的 target 与高亮区间，`GET /api/search` 也如实只查 `message`（排除 `kind='system'`）。但设计系统原型的搜索面有四档 facet（全部 / 消息 / 任务 / Agent）与三类结果行，用户本轮点名要对齐这一面。

我们决定**扩展后端**而不是让前端聚合：`GET /api/search` 的命中来源扩为三类——消息（正文子串）、任务（标题）、Agent（显示名与角色），facets 作为后端的**过滤参数**；前端继续只做呈现与高亮包装。

被否的方案是「后端不动，前端拿三份数据自己过滤」：`CONTEXT.md` **搜索命中** 与 **高亮区间** 两条词条已经把「命中判定在后端、前端不判定」写成硬纪律（同一条纪律也写在 **补全** 词条里：「前端**不解析**提及」），前端聚合会在同一能力上重建第二个判定落点，此后两处的匹配规则必然漂移。

代价是三类的证据强弱不对称：消息命中带**高亮区间**，任务与 Agent 的命中本体是标题 / 名字，前端只能整段呈现（或按同一个后端给出的区间包装）。因此返回形状必须统一携带「命中类型 + 所属 target 或对象标识 + 可呈现文本 + 可选高亮区间」，缺失区间时前端退化为不包 `<mark>`，**不得**自行在文本里找位置——那正是被否的第二个落点。原型的 `mark()` 只包裹第一处命中，本仓既有契约更强（标出全部命中），这一处**沿用仓库契约**而非降级对齐原型。
