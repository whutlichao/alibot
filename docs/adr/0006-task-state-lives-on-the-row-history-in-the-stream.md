# 任务的当前态在行上，变更史在消息流里

任务有标题、状态、指派者三个字段，它们在原型的交互里都能改（拖拽改状态、点选改指派）。这与 **ADR-0001
（消息 append-only）** 迎面撞上：任务的历史到底算什么？

我们决定**两者分开、各自用对的形态**：`task` 行是**可变的**（当前态的读写面，看板一次渲染几十张卡片时
只读它），而**每一次变更都追加一条 `kind='system'` 消息进该任务 target 的消息流**——历史就是消息流本身。
消息仍然 append-only，ADR-0001 一个字不改，本 ADR 要写清的是那个容易含混的边界：**task 行的 UPDATE 不是
消息的 UPDATE**。它们作用在两个不同的表上，前者改"现在是什么"，后者只记录"曾经变成过什么"。

否掉的两条路：**任务完全 append-only**（状态与指派都是新消息、看板卡片由重放算出）会让"当前态"这个最热的
读路径变成一次按 seq 的聚合，看板要为此付几十次重放的代价；**行可变 + 另存一张 `task_event` 表**则违背
"变更的可解释来源只有一处"——本仓已经用**消息**承载过"为什么它没说话"（轮次结果），历史落在消息流里是同一个
形状，不需要第二张历史表。

代价明确：任务 target 的消息流会比频道流"话多"（一次改状态就是一条 system 消息）。这由两条既定的口径吸收：
任务线程的消息**不在**频道 target 里，因此**不计入频道未读**；而**未读计数**的口径一如既往只算
`human` / `agent` 正文、**不计 system**，所以任务自己的 system 消息也不会虚增任何徽标。任务线程的未读是
`target_read(member, task_target_id)` 这一行自己的事实。
