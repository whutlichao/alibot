## Problem Statement

今天「回应预算」的上界是一个**写死在源码里的常量**：`BUDGET_LIMIT = 3`（`app/alibot/db.py:48`）。它没有环境
变量、没有配置文件、也没有任何人类面写入端点 —— 三个面都是硬的：

- 人类面只有一条只读端点 `GET /api/channels/{id}/budget`（`app/alibot/api.py:272`），注释自己写着「只读，无 UI」；
- `PUT / PATCH / DELETE / POST /api/channels/{id}/budget` 一律 404（`app/alibot/api.py:397`），话术是
  「回应预算只读：人类面不存在写入它的端点」；
- 编排侧直接 import 这个常量来裁决（`app/alibot/orchestration.py:50` 的
  `from .db import BUDGET_LIMIT, Database, utc_now`，判定在 `:249-250`，耗尽文案在 `:262-265`）。

于是本机用户面对的是一个**不可调、也说不清理由**的旋钮。想让它更宽一点（例如在自己的频道里跑一次更长的
Agent 接力），用户没有任何合法路径：改源码常量不是配置，而库里也没有可改的行。想让它更紧一点（例如在花钱
的 provider 上），同样做不到。

而「为什么是 3」这个问题，仓库里**没有算出来的依据**。它的来源是一条拍板：`gh issue view 1` 的
「用户已确认的边界」第 2 条原文是

> **有界响应策略**：每条人类消息重置预算，Agent 之间最多 **3 轮**连续往返；超出预算后消息**仍然落库**，
> 但**不再唤醒任何 agent**。

这条策略参数随后被固化为 `docs/adr/0002-response-budget-caps-relay-at-three.md`（标题即结论
「回应预算 ≤ 3 是有界响应的手段」）与 `CONTEXT.md` 的**五条**词条（**人类世代** / **回应预算** / **跳** /
**预算耗尽** / **预算表**，`CONTEXT.md:138-167`）。ADR-0002 给出的理由是一句动机而不是一次测量：
「若不设上界，两个 Agent 会互相唤醒到把 token 烧光」。仓库里**没有任何成本模型、没有对比实验、没有
token / 时延 / 金额读数**支持「3」这个具体数值 —— 它是一条被确认的**策略参数**，不是一个被算出来的结果。
这两件事在本票里必须分开说：**「必须有上界」与「上界实现成零投递」是有依据的决策，而「上界取 3」是拍的。**

## Solution

把这一条策略参数从「一个写死的常量」变成**三层都有明确落点、由用户在页面上改、并且改数要留下权衡记录**的配置：

1. **预算可配置**：给出配置落点的候选与比较（进程环境变量 / 库内逐频道配置 / 成员或工作区级配置），
   并逐条说清它对两条既有语义的影响 ——「**跳数的正本是 `channel_budget.used`**」与
   「**人类消息落库即重置**」。
2. **在页面上交给用户**：配置必须能由用户本人在浏览器界面里调整，而不是只能改环境变量或改库。本规格正面
   处理它与既有纪律的冲突（人类面刻意没有写入预算的端点），把「新增的写入口落在哪」写成**显式待决的决策点**。
3. **重新定档位**：不只是把 3 搬成配置项，还要按频道规模 / 成员数 / 成本估算重新审视**默认值本身**，
   给出档位候选（固定档位 / 按成员数推导 / 按估算成本推导）与各自的代价，并写清默认值本票改不改、为什么。
4. **补齐 ADR 依据**：把「为什么是 3」补上实测依据（token 消耗、往返时延、花钱成本），实测方法写进
   Testing Decisions。
5. **调查结论**：把 3 的来源如实记下来（#1 拍板的策略参数），并写明仓库里没有任何成本模型或对比实验。

用户能感到的变化是：**这个旋钮看得见、说得清、改得动** —— 而「改成几」这件事有了实测方法与 ADR 记录做底，
不再是一句动机。

## User Stories

**A. 看见这个旋钮**

1. 作为本机用户，我想在界面上看到某个频道当前人类世代的回应预算（已用 / 剩余），这样我知道自己还剩几次
   Agent 往返，而不是等 Agent 突然不说话才发现。
2. 作为本机用户，我想看到这个上界**是几**、以及它是从哪一层配置来的（本机默认 / 频道覆盖 / 没配过），
   这样我改之前就知道自己改的是哪一层。
3. 作为本机用户，我想在预算耗尽导致某条 Agent 消息没唤醒任何人时，一眼看到「预算用尽」而不是猜，
   这样「它没说话」不会被我误读成「它坏了」。
4. 作为本机用户，我想在界面上看到这个上界的**理由**（一条人类发言允许引发多少 Agent 往返、代价是什么），
   这样我不是在调一个没有含义的数字。

**B. 调这个旋钮**

5. 作为本机用户，我想在页面上把这个上界调大，这样我可以在一个频道里跑更长的 Agent 接力，而不用改源码。
6. 作为本机用户，我想在页面上把这个上界调小（乃至调到 0 或 1），这样在花钱的 provider 上我能更早刹住。
7. 作为本机用户，我想让改动**只影响我改的那个频道**（或明确知道它影响整个工作区），这样我不会因为调一个
   频道而悄悄改变另一个频道的循环上界。
8. 作为本机用户，我想在改动**下一个世代生效**（而不是把当前世代已经用掉的额度回溯改写），这样「这个世代
   还剩几次」不会在我改配置的瞬间忽然变多或变少。
9. 作为本机用户，我想在填了不合法值（负数、零、非整数、超大值）时得到明确报错、且**配置不被写成半成品**，
   这样我不会得到一个坏掉的频道。
10. 作为本机用户，我想让新上界在后端重启后仍然生效，这样我的配置不是活在某个进程内存里的东西。
11. 作为本机用户，我想让「上界」与「当前人类世代已经用掉的跳数」这两件事在界面上**分开呈现**，这样我不会
    把「我用完了」误读成「这个频道的上界变了」。
12. 作为本机用户，我想在改完上界之后，那条新的上界能立刻在同一个界面上被读回来（不是"看起来改了，其实
    没写进去"），这样我对这个控件有信任。

**C. 上界仍是有界响应**

13. 作为本机用户，我想无论我把上界配成几，**一个人类世代内的 agent→agent 跳数都不会超过它**，这样"有界"
    仍然是构造性保证而不是事后统计。
14. 作为本机用户，我想让「上界配成 0」成为一个有意义的状态（这个频道的 Agent 消息永不唤醒任何人），而不是
    一个非法输入或被当成"用默认值"的静默兜底。
15. 作为本机用户，我想让「人类消息落库即重置为满额」这条纪律在配置化之后逐字不变 —— 重置成的是**当前生效
    的上界**，不是那个写死的 3。
16. 作为本机用户，我想让「预算耗尽 = 零投递 + 为每个被压制的成员各记一条轮次结果」这条纪律逐字不变，
    因为它是我事后解释「它为什么没说话」的取证面。
17. 作为本机用户，我想让「跳数的正本仍是 `used`、不是轮次结果的行数」这条纪律逐字不变，这样我拿到的读数
    不会被成员数干扰。
18. 作为本机用户，我想让并发到达的两条 Agent 消息不可能同时读到「还剩 1」而各投一次，这样上界在配置化之后
    仍然不被竞态突破。
19. 作为本机用户，我想让不同频道的预算各自独立（一个频道烧完不锁死另一个），这条既有语义在加配置层之后
    不被破坏。
20. 作为要改这套系统的开发者，我想让「零投递不算一次跳」「被合并的唤醒不额外计数」这些既有判据逐字保留，
    这样配置化不是一次语义重写。

**D. 改数的依据**

21. 作为本机用户，我想知道**为什么**默认值是现在这个数，依据是 token 消耗、往返时延还是花钱成本，这样我
    改它的时候有参照而不是凭感觉。
22. 作为要改这套系统的开发者，我想拿到一组实测方法（在隔离数据目录、用可控模型替身与至少两种真实模型怎么
    量），这样"为什么是 N"这件事可以重复测，而不是只有一句动机。
23. 作为本机用户，我想看到一条人类发言在**最坏情况**（上界被跑满）下的代价读数，这样我能判断这个上界对我
    的钱包意味着什么。
24. 作为本机用户，我想让成本相关的依据**按 provider 分开**，因为本机 Ollama 与远端付费模型差几个数量级，
    同一个数字在两者身上含义完全不同。
25. 作为要改这套系统的开发者，我想在默认值真的要从 3 改掉时，有一条**必须走新 ADR**的纪律（因为
    ADR-0002 的标题即结论），这样这个数字不会某天被静默改掉。

**E. 与既有决定的关系**

26. 作为要改这套系统的开发者，我想让本规格明写「改默认值或改上界语义会推翻 ADR-0002」，并列出新 ADR 应当
    记录的取舍，这样推翻是有记录的动作而不是漂移。
27. 作为要改这套系统的开发者，我想知道 `CONTEXT.md` 的五条词条（`CONTEXT.md:138-167`）把 3 写死了，改数时
    要一并处置，这样文档不会与实现分叉。
28. 作为要改这套系统的开发者，我想知道既有测试里有把 3 当硬断言/写进测试名的用例，改默认值时必须一并处置，
    这样「改了默认值但测试还写着 3」不会变成一个哑火的回归网。
29. 作为要改这套系统的开发者，我想知道 #23 的决策 G2 把 `target_budget` 的机制写成"逐字不变（≤3）"，改数会
    让那份规格的措辞与实现分叉，需要同步，这样两个规格不会互相打架。
30. 作为本机用户，我想让「预算可配置」这件事**不改变**我当下看到的行为（本票不改默认值），这样这份规格落地
    前后我没有感知上的突变。

## Implementation Decisions

### 1. 事实基线（本规格全部论述的依据，已只读核实）

| # | 事实 | 出处 |
| --- | --- | --- |
| F1 | 上界是源码常量 `BUDGET_LIMIT = 3`，三个面都不可配置（无 env、无配置文件、无人类面写入端点） | `app/alibot/db.py:48`、`app/alibot/orchestration.py:50`、`app/alibot/api.py:397` |
| F2 | 口径是 **agent→agent 跳**，不是「每个 bot 3 条」：一条 Agent 消息投递至少一个唤醒 = 1 跳；跳数的唯一正本是 `channel_budget.used`（建表在 `app/alibot/db.py:109-114`），唯一写点是 `_spend_jump`（`app/alibot/orchestration.py:234`，判定 `:249-250`、扣款 `:253`） | `app/alibot/orchestration.py:234`、`app/alibot/db.py:109-114` |
| F3 | **人类世代** = 该频道最近一条人类消息的 `seq`（`db.human_epoch_seq`），人类消息**落库即重置**为满额 | `app/alibot/db.py:802`、`app/alibot/db.py:728-736`（`append_message` 内） |
| F4 | 预算耗尽时**零投递**，且为每个被压制（本应被唤醒）的成员**各记一条 `budget-exhausted` 轮次结果**；状态点不因此变 `error` | `app/alibot/orchestration.py:256`（reason 文案 `:262-265`） |
| F5 | 把 3 当硬断言的既有用例在 `app/tests/test_bounded_relay.py`（`used == 3`、整块 dict 里限 `limit: 3`、`remaining == 3`），并有测试名把 3 写进去 | `app/tests/test_bounded_relay.py:194`、`:285-290`、`:331`、`:336`、`:488`、`:499`；测试名 `:258` |
| F6 | 来源是 #1 拍板的策略参数，固化为 `docs/adr/0002-response-budget-caps-relay-at-three.md` 与 `CONTEXT.md` 的五条词条（**人类世代** / **回应预算** / **跳** / **预算耗尽** / **预算表**） | `gh issue view 1`「用户已确认的边界」第 2 条；`docs/adr/0002-response-budget-caps-relay-at-three.md`；`CONTEXT.md:138-167` |

**必须逐字保留的两条既有语义**（改配置不得削弱它们）：

- **跳数的正本是 `channel_budget.used`**，不是轮次结果的行数 —— `round_outcome.consumed_budget` 只是**行级**
  标记，一次跳投递 N 个成员就有 N 条为真的行（`app/alibot/db.py:470-480` 的 docstring 原话）。
- **人类消息落库即重置满额** —— 重置发生在落库那一刻（`app/alibot/db.py:728-736`），而不是等下一位调用者
  惰性重置；预算只读端点与压制行为必须同时看到这件事。

### 2. 决策：配置的**落点**（三候选，附对两条既有语义的影响）

以下三个落点都可行，取舍在**「谁改得动」「重启后是不是同一条事实」「重置成哪个数」**这三问上分岔。
**本规格要求实现票在这三者中选一个并写明理由**；本票只把代价摊开，不替实现票拍板。

**候选 L1 —— 进程环境变量（例如一条新 env 承载默认上界）**

- 形状：进程启动时读一次，作为**本机默认上界**；库里不新增列。
- 好处：改动最小，与既有「凭证只从进程环境变量读」的窄 seam 同构（`app/alibot/agent_seam.py:152-169`），
  也不新增任何人类面写入口（于是与 F1 的"没有写入端点"不冲突）。
- 代价：**它不满足本票的"在页面上交给用户"**（用户本轮的原话），只能当作兜底层。
- 对既有语义的影响：`used` 仍是正本，但 `remaining` 变成**进程相关**的读数 —— 同一个世代里重启后端并改
  env，`used` 不变而 `remaining` 变了。这与 #4 的验收读数「重启后**预算状态**仍是同一条事实」直接冲突：
  重启持久性测试对比的是整块 dict（`app/tests/test_bounded_relay.py:471`），而其中 `limit` 会漂移。
  选 L1 就必须把该验收项重新表述为「`used` 与 `epoch_seq` 持久，`limit` 属于进程配置」。

**候选 L2 —— 库内逐频道配置（推荐作为主落点）**

- 形状：在预算正本所在的那一行（`channel_budget(epoch_seq, used)`，`app/alibot/db.py:109-114`）旁新增上界，
  或另立一张频道级配置行。上界与 `used` **同在库里**。
- 好处：满足「页面上交给用户」；与「预算是每频道一份」的既有边界同构；重启后上界与 `used` 一起恢复，
  第 1 节那条既有语义不受影响。
- 代价（必须在实现票里定清，本票列为待决）：**世代中途改上界要不要回溯生效？** 若立刻生效，当前世代
  「还剩几次」会在改配置的瞬间跳变（`used` 已 3、上界从 3 改成 5 ⇒ 那一刻又"多出两次"）；若下一世代生效，
  用户改完看不到立即变化，需要一个明确的呈现话术。这是配置化**新引入**的语义歧义，既有设计里不存在
  （上界是常量，没有"改"这个动作）。
- 对既有语义的影响：「人类消息落库即重置」要明确重置成**当前生效的上界**而不是常量 3 —— 重置路径在
  `app/alibot/db.py:728-736`，它今天写的是 `used = 0`（不写 limit），所以配置化后这条路径本身不必改，
  但**读上界的唯一落点**必须收敛到一处（否则裁决点 `app/alibot/orchestration.py:249-250` 与只读端点
  `app/alibot/service.py:146-151` 可能读到两个数）。

**候选 L3 —— 工作区级 / 成员级配置**

- 形状：一张工作区级默认上界 + 可选的成员级覆盖。
- 好处：一次改动能覆盖全工作区的频道，适合"我想整体收紧"的诉求。
- 代价：引入**第二个作用域的配置来源**，而预算的正本是 per target / per channel 的。需要额外定清优先级
  （成员级 > 频道级 > 工作区级？）与"哪一层允许被页面上改"，落地成本最高；成员级覆盖还有一个语义可疑点：
  跳是**一条消息投递的唤醒数**，与"哪个成员"无关，按成员配一个"跳的额度"会让同一跳在不同成员的预算上
  各记一次，与 F2 的口径相冲。
- 对既有语义的影响：若引入优先级链，`used` 仍是唯一正本，但"上界"变成读三层后计算出来的值 —— 裁决点与只读
  端点的读取必须共用同一个解析函数，且要能回答"这个数是从哪一层来的"（User Story 2）。

### 3. 显式待决决策点 ①：**人类面新增的写入口落在哪**（本票最大未决项）

**冲突的正面陈述**：需求说「预算可配置应该在页面上交给用户」，而仓库当前有一条**刻意的**纪律 ——
「预算只由后端在『人类消息重置 / 一次跳投递』时推进：人类面不能直接改它」（`app/alibot/api.py:397-404`，
`PUT/PATCH/DELETE/POST /budget` 一律 404）。也就是说：今天"人类面不能改预算"不是遗漏，是设计。
本规格**不自行拍板**这条纪律该不该被打开，而是把候选与代价写清，等用户裁定。

**候选 W1 —— 频道设置里的「回应预算」数字输入，新增 `PATCH /api/channels/{id}/budget`**

- 形状：把 404 兜底改成真实的写端点，落在频道的设置面（配置项与"发消息"是两个动作）。
- 代价：需要把"配置"与"用量"分开陈述 —— 写入口改的是**上界**，而 `used` 仍然只能由后端推进，因此同一个
  资源上的"可写字段 / 只读字段"要在契约里说清（否则用户会以为能直接抹掉已用的次数）。
- 与既有纪律的关系：纪律从「人类面不能写预算」变成「人类面**只能写上界，不能写用量**」。这不是削弱：
  压制行为仍由后端按 `used` 与上界裁决，跳数正本未变。需要一条新 ADR 记录这次收窄的边界。

**候选 W2 —— 只在「新建频道」时选定（创建期配置，创建后不可改）**

- 形状：把上界列进 `POST /api/channels` 的字段，不新增任何写端点。
- 好处：完全不碰「人类面没有写入预算的端点」这条纪律；与「创建时勾选初始成员」的既有创建面同构。
- 代价：**改不了** —— 想收紧一个已经建好的频道，只能新建频道。对"我这次想让它多跑两轮"这种临时诉求
  基本无用。

**候选 W3 —— 工作区设置页（`PATCH /api/workspace` 上的一个字段）**

- 形状：一个全局默认，频道可选覆盖（覆盖需要 W1）。
- 好处：一次收紧全部频道，符合"我在花钱的 provider 上"的诉求。
- 代价：与"不能因为调一个频道而悄悄改变另一个频道"（User Story 7）的直觉相反，需要呈现在哪里改的读数；
  且仍然要回答"频道级覆盖算不算人类面写预算"。

**候选 W4 —— 不新增写入口，用「人类发言」承载配置**

- 形状：不改端点，用一条人类消息里的约定指令改变上界。
- 代价：把配置混进对话内容，与「消息 append-only、正文不可编辑」（ADR-0001）相冲（改错了只能再发一条），
  并要新增一套指令解析器 —— 而规格 #1 §5 明确「唤醒是注意力信号，不是命令」，反过来也成立：配置不该是一条
  发言。**本规格倾向否决 W4**，列为候选只为把代价摊在明面上。

**本票要求**：无论最终选哪个，规格必须写清**端点、界面位置、以及它与「预算只由后端推进」的关系**三件事，
并用一条新 ADR 记录这次边界变化（新写入口的收窄/放开都是"难逆 + 无上下文会困惑 + 真取舍"的决定）。

### 4. 显式待决决策点 ②：**新默认值怎么定**

**本票的立场（写清、不回避）**：**本票不改默认值，3 保持不变。** 理由是硬性的：ADR-0002 的标题即结论
（`docs/adr/0002-response-budget-caps-relay-at-three.md` 的 `at three`），改默认值**就是**推翻它；而推翻它需要
**实测依据**（第 5 节的方法），今天一条都没有。在没有依据的情况下换一个数，等于用一个拍板替换另一个拍板。
因此顺序是：**先落配置化（让这个数可改、可见）→ 再按实测补依据 → 再决定默认档位**；后两步各需自己的票。

档位候选与代价（供后续票裁定）：

**候选 T1 —— 保持固定档位（默认 3，只有一个数）**

- 好处：与今天行为完全一致；ADR-0002 的「≤3」措辞只需泛化为「≤ 当前上界」。
- 代价：与频道规模无关。一个 2 人 DM 式的频道和一个 8 个 Agent 的频道拿同一个上界。

**候选 T2 —— 按成员数推导（例如随 Agent 成员数增长）**

- 好处：看起来"更聪明"，大频道额度更大。
- 代价（重要，规格要写明）：**跳数与成员数几乎无关** —— 一条消息即使唤醒 N 个成员也只消耗 1 跳（F2）。
  成员数影响的是"一次跳的唤醒面"，不是跳数。按成员数推导会引入一个**与正本口径不成比例的旋钮**：同样的
  接力长度，在 8 人频道里上界更大、在 2 人频道里更小，而这个差异没有任何成本依据支撑。

**候选 T3 —— 按估算成本推导（用实测的 token / 时延 / 金额反推）**

- 好处：唯一一个把"为什么要设上界"的原始动机（token 会烧光）直接接进数值的候选。
- 代价：依赖第 5 节的实测，且成本**随 provider 与模型变化几个数量级**（本机 Ollama 与远端付费模型不可比），
  于是同一个数字在不同 provider 下含义不同 —— 要么按 provider 分别推导（配置面变大），要么承认这个数字只是
  一个"以最贵场景为准"的保守值。另外 `agent_config.model_id` 是按成员的，一个频道里可以混用 provider。

**候选 T4 —— 按频道用途预设档位（例如「单人问答 / 双人接力 / 多人协作」三档语义名）**

- 好处：用户不需要理解"跳"，只需要选一个用途。
- 代价：引入"频道用途"这个新词与新的选择面（`CONTEXT.md` 里没有它），并且要定清"用途"是一个可改的字段
  还是创建期的属性；把用户从"调一个数"推向"选一个语义"，而语义档的背后仍然是一个数。

### 5. 改数**必须**有新 ADR（纪律，不得静默）

- 改**默认值**（3 → 其它）：直接推翻 ADR-0002（标题即结论）。**必须**新增一条 ADR 显式推翻，并在其中记录：
  ① 实测依据（token / 时延 / 成本读数，含测量环境与模型）；② 为什么旧值不够 / 过多；③ 新的默认档位与推导
  方式（T1–T4 中的哪一个）；④ 代价（放宽后一次人类发言最坏情况的成本上界变大）。
- 改**上界语义**（例如把"零投递"换成"投递后刹住"、或允许人类面直接改 `used`）：同样推翻 ADR-0002 的关键
  取舍段（它写明了为什么选"零投递"）。同样需要新 ADR。
- **只是把常量搬成配置项、默认值不动、上界语义不动**：不推翻 ADR-0002 的取舍，但**新增人类面写入口**这件事
  本身改变了一条既有边界（`app/alibot/api.py:397-404`），需要一条**新 ADR 记录这次边界变化**（见决策点 ①）。
- 任何情况下都**不得**静默改常量：`BUDGET_LIMIT` 是书面结论的落点，改它而不动文档就是让文档与实现分叉。

### 6. 文档与词汇表要一并处置的落点

- `CONTEXT.md` 的五条词条把 3 写死（`CONTEXT.md:138-167`：**人类世代** 的"重置为 3"、**回应预算** 的"最多 3 次"、
  **预算耗尽** 的"已用满 3 次跳之后"）：**改数或改成配置项都要一并处置**，否则词汇表与实现分叉。
  本规格要求措辞改为"当前生效的上界"这一类说法，而**不**在这五条词条里写死任何具体数值。
- `docs/adr/0002-response-budget-caps-relay-at-three.md` 不修改、不删除；它的失效只能由一条**新** ADR 声明。
- #23 的决策 G2（`target_budget` 逐字不变、≤3）与正文「跳数上界 ≤ 3」措辞会在本规格落地时与实现分叉，需要
  同步（本票不授权对 #1 / #23 做任何写操作，见 Further Notes）。

### 7. 接口与读数（决策级，不含代码）

- 预算的读数形状不变：`{channel_id, epoch_seq, limit, used, remaining}`（今天的 `db.budget_state`，
  `app/alibot/db.py:781`，经 `service.channel_budget` `app/alibot/service.py:146-151` 出现在
  `GET /api/channels/{id}/budget`）。配置化后 `limit` 的含义从"常量"变成"当前生效的上界"，字段名不变。
- **上界的读取必须收敛到唯一落点**：裁决点（`app/alibot/orchestration.py:249-250`）与只读端点读到的必须是
  同一个数，"这个数从哪一层来的"要能一并读到（User Story 2）。
- **零投递判据逐字不变**：目标全部 in-flight ⇒ 不算一次跳、不消耗（`app/alibot/orchestration.py:246-248`）；
  耗尽 ⇒ 零投递 + 每个被压制成员各一条 `budget-exhausted`（F4）。

## Testing Decisions

**什么算好测试**：只断言**外部可观察行为** —— 经 HTTP 面读到的 `limit` / `used` / `remaining`、压制行为、
轮次结果与消息落库事实。不断言常量本身、不断言私有结构、不把 `3` 写进断言或测试名。一条测试不应因为上界
被配成别的数而失败（除非它显式配了那个数）。

**既有把 3 当硬断言的用例必须一并处置**（改默认值的那一票的责任，F5）：

- `app/tests/test_bounded_relay.py:194`（`used == 3`）、`:285-290`（整块 dict 含 `limit: 3`）、
  `:331`、`:336`（`used == 0 and remaining == 3`）、`:488`、`:499`，以及测试名
  `test_agent_to_agent_relay_is_bounded_by_three_jumps_per_human_epoch`（`:258`）与
  `test_a_new_human_message_resets_the_budget_and_the_relay_works_again`（`:314`）内的读数。
- 处置方式（实现票选一个并写明）：① 先读 `/budget` 的 `limit`，再断言 `used == limit` / `remaining == 0`
  —— 表达力不变、不写死数字；② 在测试里显式配置上界，再断言那个数 —— 配置化之后更有表达力，且顺带覆盖
  "配置生效"这条新行为；③ 把断言改写成"不存在第 limit+1 次投递"这类构造性断言。**无论选哪个，不得留下
  写死 3 的断言**，也不得把测试删掉来"让它过"。
- 另需新增的行为测试（实现票）：上界配成 0 时有意义（Agent 消息零唤醒）、配成 1 时上界恰好为 1、
  非法值被拒且不留半成品、改动在后端重启后仍生效、不同频道的上界互不影响、上界与 `used` 的呈现不互相污染。

**Prior art**：`app/tests/test_bounded_relay.py` 是既有的范式 —— HTTP 黑盒 + 手动调度器 + 脚本化替身
（`app/alibot/api.py:145-157` 的 `scheduler`/`seam` 注入点），以及重启持久性读数
（`app/tests/test_bounded_relay.py:471`）。新测试沿用同一范式，不新开接缝。

**补齐 ADR 依据的实测方法（本票只写方法，不实施 —— 这是「为什么是 3」缺的那一半）**

1. **环境**：隔离数据目录（`default_data_dir()` 支持环境变量 override，`app/alibot/db.py:238-243`），
   不触碰用户真实数据目录；任何"红证据"在隔离副本或基线 worktree 上取得。
2. **量三样东西**：
   - **token 消耗**：从框架侧的 `Msg.usage` 取（`app/alibot/agent_seam.py:179-180` 已写明 `usage` /
     `finished_reason` 只影响本轮结论、不构成消息正本，因此读取它是安全的取证动作）。
   - **往返时延**：一轮的 wall time，来源是 `round_outcome` 的 `started_at` / `finished_at`
     （表定义 `app/alibot/db.py:138`，写入在 `append_round_outcome`，`app/alibot/db.py:461`）。
   - **花钱成本**：按 provider 的定价 × token 折算；注意**库里不存密钥**、也不存定价，定价与模型标识都是外部
     输入，实测脚本需要自带一张"模型 → 单价"表（放在测试侧，不入库）。
3. **关键实验（最坏情况外推）**：构造两个互相 `@` 的 Agent，跑满一个人类世代（现行 3 跳），量出**一条人类
   发言在最坏情况下的代价**；再按 N 跳外推，得到"上界 = N 时一次发言最多花多少"。这正是 ADR-0002 缺失的
   那句依据。
4. **样本要求**：**至少两种模型**，且必须包含**一个远端付费 provider 与一个本机 provider** —— 两者成本量级
   差几个数量级（`agent_seam.py:29-31` 写明换成本机 Ollama 时无需任何凭证）。只测一种得出的数字不能支撑
   一个跨 provider 的默认值。
5. **可复现性纪律**：脚本化替身跑出来的 token 数恒为 0（`app/alibot/agent_seam.py:10-12` 的"不联网、零成本"），
   因此**成本实验不能只用替身** —— 必须有一条或一组"真实模型、默认跳过、本机手动运行"的成本用例（沿用
   #1 §Testing 的既有做法：真模型连通性本就是默认跳过的冒烟测试）。替身仍用于行为测试，两者分工不能混。
6. **交付形状**：实测读数与折算说明写进新 ADR（推翻 ADR-0002 的那一条）与实现票的验收取证文件；不在本票。
