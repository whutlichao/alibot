### 0.3 `repair.py` 的现状与它的版本门

- `repair.py:303` 用 `Database.open_without_initializing(data_dir)`：它**复用同一道闸门**，因此要求库里的版本**恰好等于**当前 `SCHEMA_VERSION`（`db.py:757-770` 的 docstring 明说"版本不等时**连看都不让看**"）。
- 于是今天的实际能力边界是：**一个 `schema_version` 已是 4、channel 型作用域数据还没搬的半改名库（#37 那次事故的产物），今天两条路径（启动 / `--repair-targets`）都打不开**——它会在闸门处被拒绝。这不是缺陷，是"当前版本库的补齐入口"这个自我定位的直接推论；但它是本票附加约束必须处置的那一格（§1 的 E1）。
- `repair.py` 的补齐是**四条 `INSERT OR IGNORE` + 双向自校验 + 单事务**（幂等、可自校验；`repair.py:273-353`）。这套结构**正好就是**本设计里"形态步骤"要的形状，所以第五节选"吸收"而不是"另起一套"。

### 0.4 CLI 习惯与 ADR 体例（用于命名与落点）

- CLI 是**单 argparse 入口 + 布尔旗标**：`--host` / `--port` / `--data-dir` / `--repair-targets`（`__main__.py:37-54`），**没有子命令**。
- `docs/adr/` 现有 14 条（`0001`–`0014`），**没有一条用 `Status` frontmatter**；处置旧口径的既有惯例是**不改旧 ADR 原文**（ADR-0007：「本 ADR 不修订或取代 ADR-0002」；ADR-0010：「**不改 ADR-0005 原文**……就地改写会让『当时为什么这么定』消失」）。
- `docs/agents/domain.md` 的纪律：与既有 ADR 冲突要**显式写出**，不得静默覆盖。

## 2. 被否方案与代价（逐条）

| 决策点 | 被否方案 | 代价（为什么否掉） |
| --- | --- | --- |
| Q1 预演 | **只读判定、不跑步骤**（同一连接上只规划、绝不执行写语句） | 更便宜、也不需要临时空间，但**证明不了"步骤真能跑通"**——用户仍要拿真库赌一次，而预演的全部价值正是免掉这一赌 |
| Q1 预演 | **不做预演** | 用户对一次不可逆操作零信息 |
| Q1 退出码 | **"部分完成"独立退出码** | 迁移在单事务里收口，该状态**不可达**；一个不可达的码是死代码，还会诱导实现去"支持"它 |
| Q2 范围 | **只支持 N-1** | 本仓必须**每次发布都留一棵 N-1 的代码树**，而中间版本的用户被逼向手工逐版升级——正是"显式命令"想消除的体力活 |
| Q2 范围 | **把起点抬高到 7**（"更早的号没有真实用户"） | 丢掉 3–6 的唯一迁移路径，而那段步骤在 git 里可复现，成本只是几步注册项 |
| Q3 组织 | **纯"按目标 `SCHEMA` 结构对齐"** | 回答不了"**这一步该搬哪些行**"——对齐只能造出结构，数据搬迁的判据本来就是"上一代形态里它在哪"；对未来版本也给不出判据（没有版本链，就没有"我只认得 ≤ 我的号"这句话） |
| Q3 组织 | **纯逐版步骤、不加连续性检查** | 撞号与落后号**静默通过**，错了要等用户库上报才发现（`9 → 11 → 12` 就是近例） |
| Q4 备份 | **不自动备份**（正文给指引、让用户自己备份） | 把不可逆风险留给用户，报错正文那句「请先备份该数据目录」变成**空话** |
| Q4 备份 | **自动备份但失败仍放行** | 等于没有备份保证，只多一个"备份过了"的错觉 |
| Q4 备份 | **只备份 `alibot.db`** | 与「备份单位是整个数据目录」冲突（`README:83-84`），会丢 `attachments/` 的字节，恢复出来是半份库 |
| Q5 入口 | **并存两套入口**（repair 独立管"当前版本的半改名库"，migrate 管跨版本） | 长期分裂成「同一个库、两个答复、两套语义」，而两者处置的其实是同一批行 |
| Q5 入口 | **直接删除 `--repair-targets`** | 存量文档与脚本的引用当场断，且丢掉 #37 的历史处置能力 |
| Q5 ADR | **就地改写 ADR-0004 那句话** | 抹掉那次取舍的**被否方案记录**（"不做迁移"是 ADR-0004 登记的代价栏） |
| Q6 旧表 | **迁移后 `DROP` 旧表** | 不可逆，且与"备份可回退"重复——回退已由整目录备份承担，代价是回退时还要重新推导旧表内容 |

| Q6 文档 | **只写 ADR、不动 `CONTEXT.md`** | "迁移 / 闸门"会变成只在 ADR 里存在的一次性黑话，与「`CONTEXT.md` 是唯一词汇正本」的口径冲突 |
| Q6 文档 | **整段重写 README** | 抹掉 #67 / #37 的既有取证叙述，制造无谓 diff |

## 3. 给 to-spec 的规格输入清单（逐条可验收）

每条给【契约】与【可观察验收判据】两半。**不含实现细节缺口**：表的列名、SQL 文本、副本获取的具体机制可以留给实施票，但下面每条的**行为**都必须是规格正文里可判定的句子。

| # | 契约（规格必须写清的） | 可观察验收判据 |
| --- | --- | --- |
| S1 | 迁移入口是 **`python -m alibot --migrate [--data-dir <路径>]`**：布尔旗标，与 `--repair-targets` / `--data-dir` 同族，**不引入子命令**；它是**唯一**迁移入口，任何启动路径都不自动迁移 | `--help` 里列出该旗标；`--migrate` 跑完不监听端口、进程直接退出 |
| S2 | **退出码**：`0` 成功 / 库里已是目标版本；`3` 拒绝（复用 `DATA_NOT_ACCEPTED_EXIT_CODE`）；`5` 迁移失败已回滚（**新常量**，与 repair 的 `4` 区分）；**不设"部分完成"码** | 三类库分别得到 0（当前版）/ 3（未来版）/ 0（可迁的旧版）；在一步搬迁中注入失败 ⇒ `5` |
| S3 | **拒绝正文**：库路径 + 库里版本 + 本代码需要的版本 + `--migrate` 命令 + 备份指引；**不再出现「本版不做数据迁移」** | stderr 含 `--migrate` 与备份指引、不含旧句；退出码 `3`；**库文件 sha256 前后一致** |
| S4 | **启动路径**：普通 `python -m alibot` 仍**拒绝**版本不等的库、退出码 `3`，正文改为给迁移命令与备份指引 | 造一个 `stored=11` 的库 ⇒ 启动退出 `3` 且正文含 `--migrate`；「非 loopback ⇒ 2」不变 |
| S5 | **只读预演** `--migrate --dry-run`：在**数据目录内的临时副本**（`alibot.db` + `-wal`/`-shm`）上跑**完整迁移链**，打印将执行的步骤与每步将改动的行数，报告打**原库 sha256 的前后两个读数**，随后删除副本 | 预演后原库 sha256 与预演前一致；数据目录里不留临时副本；报告含步骤清单与逐步行数 |
| S6 | **备份落点与命名**：迁移前自动整目录复制（含 `attachments/`）到**同级** `<数据目录>-backup-<from>-to-<to>-<UTC 时间戳>` | 迁移成功后该备份目录存在，且其中同时有 `alibot.db` 与 `attachments/` |
| S7 | **备份失败即拒绝迁移**（退出码 `5`），不退化成"放行 + 警告" | 让备份目标不可写 ⇒ 退出码 `5`、原库 sha256 不变、无任何半迁移痕迹 |
| S8 | **单事务**：DDL 与数据搬迁在同一个 `BEGIN IMMEDIATE` … `COMMIT` 内；任何中断 ⇒ 回滚、库**停在原版本**且仍可被原版本代码打开 | 在提交前杀掉进程 ⇒ 库版本仍是原值、旧代码仍能打开、不存在"新表建了但数据没搬"的中间态 |
| S9 | **迁移审计**：每次**真正执行**的迁移写一条 **append-only** 记录（from、to、起止时间、结果、备份路径）；**人类面没有任何写入口** | 迁移成功后库里能查到该条记录；HTTP 面不存在可写它的端点 |
| S10 | **幂等 / 无事可做**：已是目标版本再跑 ⇒ 改动 0 行、退出 `0`、**不新建备份**；空目录（没有库文件）上跑 ⇒ 退出 `0` 且**不凭空创建库**（与 repair 既有口径一致） | 连跑两次：第二次报告"改动 0 行"、退出 `0`、备份目录数不增；空目录跑完目录里仍没有 `alibot.db` |
| S11 | **版本链**：注册表覆盖 `3..SCHEMA_VERSION`，每步 `from→to` **严格 +1、唯一、连续**，执行器**不跳步**；**一条源码测试**断言链连续性 | 该测试绿；人为把某步的 `from` 改成落后号（模拟 `9 → 11` 那种落后号）⇒ 该测试**红** |

| S13 | **弃用别名**：`--repair-targets` 与 `--migrate` 同入口、**行为逐字相同**（先跑形态步骤，再走同一条逐版链）、同退出码，先打印一句「请改用 `--migrate`」；它的版本门**同为 `[3, SCHEMA_VERSION]`** | 对同一个半改名库分别调用两条路径 ⇒ 同一结果、同一退出码；输出含弃用提示；`--migrate` 与别名的退出码语义逐条一致 |

| S15 | **旧表与读路径**：迁移后 `channel_member` / `channel_read` / `channel_budget` **原样保留**；当前读路径只读 `target_*`；既有端点的读口径一字不改 | 一条测试断言旧表名**不出现在读路径的 SQL 常量里**（只允许出现在迁移 / 修复模块与测试）；迁移后未读 / 预算 / 成员面的读数与迁移前一致 |
