## Problem Statement

今天，一个 `schema_meta.schema_version` 与本代码常量不等的库是一处**死路**。`python -m alibot` 会在组装应用之前拒绝它，退出码 `3`，正文只有一句出路：「本版不做数据迁移：请先备份该数据目录，再换一个数据目录启动」（`app/alibot/db.py:681-694`、`app/alibot/__main__.py:103-113`）。用户手里那本承载着频道、消息、成员、任务、附件元数据的 `alibot.db` **没有任何入口能被推进到当前形态**：

1. **没有任何迁移路径。** 所有 DDL 都是 `CREATE TABLE/INDEX/TRIGGER IF NOT EXISTS`，对既有库重跑 `SCHEMA` 是 no-op（`app/alibot/db.py` 的 `SCHEMA`），而 `_assert_schema_compatible()`（`db.py:830-848`）在**任何 schema 变更之前**就把不等版本的库拒掉了。ADR-0004 与第二版规格决策 8 明确「不做旧数据迁移」，于是这条能力从来不存在。
2. **唯一的显式入口只处置一种形态。** `python -m alibot --repair-targets`（`app/alibot/repair.py`）只在库版本**恰好等于**当前常量时可用（`repair.py:303` 复用同一道闸门）。#37 那次事故留下的库是「`schema_version` 已是 4、channel 型作用域数据还留在旧表名里」——按版本号它已经是 v4，今天**两条路径都打不开**（`app/specs/issue-37-acceptance.md` 记录了该形态的实测读数）。
3. **升级的号段历史已经证明「靠人记得」不成立。** `SCHEMA_VERSION` 是**跨在途票的号段分配**而不是「每次 +1」：main 上实际出现过的读数序列是 `3 → 4 → 5 → 6 → 7 → 10 → 10 → 11 → 12`，`8` 与 `9` 从未作为 main 的读数存在过（它们是分支局部值），而 `9 → 11 → 12` 那次争号的判据最终收在「**必须高于当前 main**」（`app/alibot/db.py:44-56` 的注释就是这段记账）。今天没有任何 CI 检查守这条纪律。
4. **备份是口头请求，不是前置条件。** README 与拒绝正文都请用户「先备份该数据目录」，但备份单位是**整个数据目录**（`alibot.db` + `attachments/` 字节，`app/README.md`），没有任何机制在改动前真正做这件事。

后果对用户是具体的：改名 worksplice → alibot 之后，**`3` 是唯一同时存在于新旧数据目录的号**（`app/README.md` 已明写改名不保留兼容）；一个从 3 升上来的用户今天只有「丢掉这本库、换一个数据目录重来」这一条路。

## Solution

给用户一条**显式、可预演、可回退、幂等**的升级命令，同时保持「启动不猜、不自动改库」这条既有纪律：

- **迁移要用户显式执行**：`python -m alibot --migrate --data-dir <数据目录>`（布尔旗标，与 `--repair-targets` / `--data-dir` 同族，不引入子命令）。它是**唯一**的迁移入口；任何启动路径都不会自动迁移。
- **拒绝变成可操作的指引**：普通 `python -m alibot` 仍然拒绝版本不等的库、退出码仍是 `3`，但正文改为给出 `--migrate` 命令与备份指引——**与迁移入口、`--repair-targets` 对同一个库给同一个答复**。
- **先备份，再动手**：迁移前自动把**整个数据目录**（含 `attachments/`）复制成同级 `<数据目录>-backup-<from>-to-<to>-<UTC 时间戳>`；**备份失败即拒绝迁移**，不退化成「放行 + 一句警告」。
- **形态步骤 + 逐版步骤链**：链前先跑一个**不依赖版本号**的形态步骤（处置「号已是新一代、数据还停在旧一代」的半改名库），然后按**逐版注册表**从库里版本逐步推进到 `SCHEMA_VERSION`（每步严格 +1、连续、不跳步）。
- **单事务收口**：DDL 与数据搬迁在同一个事务里；中断 ⇒ 回滚、库停在原版本、仍可被原版本代码打开。**没有「部分完成」这种状态。**
- **可预演**：`--migrate --dry-run` 在数据目录内的临时副本上跑**完整链**，打印将执行的步骤与每步将改动的行数，并打出**原库 sha256 的前后两个读数**作证，随后删除副本；原库与数据目录零残留。
- **兼容面不回退**：迁移后 `channel_member` / `channel_read` / `channel_budget` 三张旧表**原样保留**作回退面；既有读路径继续只读 `target_*`，未读、预算、成员面的读数与迁移前一致。
- **不降级**：库版本高于代码版本（**未来版本**）一律拒绝，三条路径一致——本仓没有降级步骤，「旧代码改写新版库」是数据损坏的唯一来源。
- **形态不对的库另有答复**：版本已等于本版本、却缺当前 `SCHEMA` 声明的对象**且**有业务数据的库，得到退出码 `4`（「不被本入口处置」），而不是被静默当成「无事可做」的 `0`；它发生在任何写入之前（不改库一个字节、不建备份）。

## User Stories

**A. 跑一次迁移**

1. 作为本机用户，我想用一条布尔旗标 `--migrate` 显式触发迁移（而不是记一串子命令），这样我能沿用已经熟悉的 `--data-dir`、`--repair-targets` 用法。
2. 作为本机用户，我想在 `--help` 里看到 `--migrate` 与它的说明，这样我不用读源码就知道入口存在。
3. 作为本机用户，我想让 `--migrate` 跑完就退出、不监听任何端口，这样迁移是一次批处理，不会顺带起一个服务。
4. 作为本机用户，我想在迁移成功时拿到退出码 `0`，并在库里读到 `schema_version = SCHEMA_VERSION`，这样脚本化调用有明确判据。
5. 作为本机用户，我想让迁移报告打出实际执行的步骤清单与每步改动的行数，这样我能核对它到底做了什么。
6. 作为本机用户，我想让报告打出本次备份的落点路径，这样我知道回退时该复制哪个目录。

**B. 被拒绝时知道下一步**

7. 作为本机用户，我想在库版本低于 3 时被明确拒绝、退出码 `3`，并被告知本版支持的源版本范围，这样我不会以为命令坏了。
8. 作为本机用户，我想在库版本号**缺失但库里有业务数据**时被拒绝、退出码 `3`，这样来源不明的库不会被静默当成空库初始化。
9. 作为本机用户，我想在库版本号是认不出的垃圾值时被拒绝、退出码 `3`，这样坏库不会被猜着改。
10. 作为本机用户，我想在库版本**高于**本代码版本时被拒绝、退出码 `3`，这样本仓永远不会出现「旧代码改写新版库」这条数据损坏路径。
11. 作为本机用户，我想让启动路径、`--migrate`、`--repair-targets` 对同一个库给出**同一个答复与同一个退出码**，这样「同一个库、两个说法」不会发生。
12. 作为本机用户，我想让所有拒绝路径**不改库文件一个字节**（校验文件 sha256 前后一致），这样被拒绝之后那本库仍可原样备份。
13. 作为本机用户，我想在拒绝正文里看到库路径、库里的版本、本代码需要的版本、`--migrate` 命令与备份指引，这样我能照着做。
14. 作为本机用户，我想让拒绝正文**不再出现「本版不做数据迁移」**这句话，这样正文不会与新的迁移能力自相矛盾。
15. 作为本机用户，我想让普通启动路径的「非 loopback ⇒ 退出码 2」这条既有拒绝语义不变，这样迁移能力不会顺手改掉无关契约。

**C. 迁移到底做什么（逐版行为）**

16. 作为本机用户，我想让迁移链覆盖 `3..SCHEMA_VERSION` 的每一条边、每步 `from → to` 严格 +1 且唯一、执行器不跳步，这样我不会得到一个「跳过了某代」的库。
17. 作为本机用户，我想让迁移在按版本号走链**之前**先跑形态步骤，这样「号已是新一代、数据还停在旧一代」的半改名库不会因为链跳过那一步而漏搬数据。
18. 作为本机用户，我想让形态步骤**不依赖版本号**、只看库的形态：`channel` 行在、而 channel 型的影子行 / 成员 / 已读 / 预算有缺，就执行搬迁，这样 #37 那类事故形态有确定处置。
19. 作为本机用户，我想让形态步骤一次补齐**四张**表（影子行、成员、已读、**预算**），这样不会出现「补齐了三张、预算面从 404 变成 200 且 `used` 归零」这种沉默抹掉已耗尽预算的假象。
20. 作为本机用户，我想让形态步骤与每一步迁移都是幂等的（重复跑改动 0 行），这样中断后重跑不需要人工判断从哪继续。
21. 作为本机用户，我想让 `3 → 4` 那一步把每个既有 channel 搬成一行 `kind='channel'` 的影子 target、并把三张旧表的行按 `channel_id → target_id` 逐列改名搬进新表，这样 v3 时代的成员 / 已读 / 预算数据在升级后仍然在。
22. 作为本机用户，我想让影子行**最先**落、新表在其后，这样引用约束不会让搬迁顺序变成隐形的失败条件。
23. 作为本机用户，我想让 `4 → 5`（任务表与线程）、`5 → 6`（DM 一对一唯一）、`6 → 7`（工作区设置面）、`7 → 8`（提醒）、`8 → 9`（附件）、`9 → 10`（主题三档）、`10 → 11`（附件触发器改写）、`11 → 12`（认领与 `claimed_at`）各步把库对齐到目标形态，这样每个号的库都能继续往前走。
24. 作为本机用户，我想让 `8 → 9` 这两步虽然从未作为 main 的读数存在、也必须作为链上的一环存在，这样分支局部号段的库不会被链的断点卡住。
25. 作为本机用户，我想让迁移的**终态**是「`schema_version = SCHEMA_VERSION`，且当前 `SCHEMA` 声明的表 / 列 / 索引 / 触发器在库级解析形态上齐备」，这样终态有唯一判据、不靠「看起来差不多」。
26. 作为本机用户，我想让老库里**读数 10 对应两棵树**（带 `reminder` 与不带 `reminder`）这种歧义被终态判据吸收，这样缺表的 v10 库也能迁到正确终态。
27. 作为本机用户，我想让**新增带默认值的列**按目标 `SCHEMA` 的默认值落到存量行（`workspace_settings.theme = 'system'`、`agent_config.auto_claim = 0`），这样升级不会偷偷改变设置与编排行为。
28. 作为本机用户，我想让 `task.claimed_at` 的存量行保持 `NULL`（= 从未被认领过），这样升级后的存量任务仍可被认领一次、认领仍会开一次世代，而不是被当成「已经认领过」而静默失去这条路。
29. 作为本机用户，我想让迁移不改任何既存列的类型 / `NOT NULL` / 默认值、不删任何既存列，这样迁移只做「加」与「搬」，不做破坏性改写。
30. 作为本机用户，我想让迁移保真数据：迁移后各业务表的行数与迁移前一致（除新表与按目标形态补齐的默认行），这样数据搬迁是可核对的行数事实。
31. 作为本机用户，我想让新插入的触发器语义（如附件不可变的两条细分触发器）在迁移后**替换**掉旧触发器而不是并存，这样约束不会出现「新旧两套同时生效」。
32. 作为本机用户，我想让附件相关的库级迁移**不假装搬了字节**：附件字节在数据目录的 `attachments/` 下、不进单文件库，备份因此以整个数据目录为单位，这样恢复出来不会是「有元数据、没字节」的半份。
33. 作为本机用户，我想让 `5 → 6` 这种**唯一性收紧**在遇到存量冲突行时明确拒绝而不是静默跳过，这样新约束不会变成「建不上就算了」。

**D. 自动备份与失败恢复**

34. 作为本机用户，我想让迁移在动手**之前**自动备份整个数据目录（含 `attachments/`），这样我不必靠自觉去复制目录。
35. 作为本机用户，我想让备份落在数据目录**同级**、命名为 `<数据目录>-backup-<from>-to-<to>-<UTC 时间戳>`，这样副本不落进被迁移的目录、命名自带方向与时间。
36. 作为本机用户，我想让备份失败就**拒绝迁移**（退出码 `5`）、库一个字节不动，这样「先备份」是执行器的前置条件而不是一句请求。
37. 作为本机用户，我想让 DDL 与数据搬迁在**同一个事务**里提交，这样进程被杀 / 断电 / 磁盘满都落在回滚那一侧。
38. 作为本机用户，我想在提交前中断后，库仍停在**原版本**、且仍能被原版本代码打开，这样失败是可恢复的而不是「新表建了、数据没搬」的中间态。
39. 作为本机用户，我想让迁移失败时得到退出码 `5`（已回滚）而不是与别的拒绝混在一起，这样脚本能区分「库不被接受」与「迁移没做成」。
40. 作为本机用户，我想让每次**真正执行**的迁移写一条 **append-only** 审计记录（from、to、起止时间、结果、备份路径），这样升级历史可追溯。
41. 作为本机用户，我想让审计记录**在人类面没有任何写入口**（HTTP 面不能改它），这样审计不会被应用路径污染。

**E. 幂等、无事可做与空目录**

42. 作为本机用户，我想让「库已是目标版本」再跑 `--migrate` 时改动 0 行、退出 `0`、**不新建备份**，这样重复执行安全且不留垃圾。
43. 作为本机用户，我想让空数据目录（没有库文件）上跑 `--migrate` 时退出 `0` 且**不凭空创建库**，这样迁移入口不会在空目录里造出一个库来。
44. 作为本机用户，我想让「无事可做」与「成功迁移」都走退出码 `0`，这样幂等调用不需要分支判断。

**F. 预演**

45. 作为本机用户，我想在真跑之前用 `--migrate --dry-run` 试一遍，这样我对一次不可逆操作有信息而不是零信息。
46. 作为本机用户，我想让预演在**数据目录内的临时副本**（`alibot.db` 与旁边的 `-wal` / `-shm` 一并复制）上跑**完整迁移链**，这样它证明的是「这条链在这个库上能跑通」，不是「大概齐」。
47. 作为本机用户，我想让预演报告打出将执行的步骤清单与每步将改动的行数，这样我能预判改动面。
48. 作为本机用户，我想让预演报告打出**原库 sha256 的前后两个读数**并保持一致，这样「预演没碰原库」是可验证的。
49. 作为本机用户，我想让预演结束后数据目录里**不留**临时副本，这样预演不污染数据目录。

**G. 弃用别名**

50. 作为本机用户，我想让 `--repair-targets` 继续可用但在输出里打印一句「请改用 `--migrate`」，这样存量脚本不当场断、同时被告知新名字。
51. 作为本机用户，我想让别名的版本门放宽为 `[3, SCHEMA_VERSION]`（不再要求「恰好等于当前版本」），这样半改名库不再被它拒之门外。
52. 作为本机用户，我想让别名与迁移入口在同一个库上给出**同一退出码**，这样我换名字不会换语义。
53. 作为本机用户，我想让别名**放宽的是「离目标有多远」，不是「方向」**——未来版本一个都不碰，这样别名不会成为绕过闸门的后门。
54. 作为本机用户，我想让 README 的指引改指 `--migrate`、并说明别名还能处置哪种半改名形态，这样文档不会把人引向一条下个版本周期就要删的路。

**H. 兼容面与读路径**

55. 作为本机用户，我想在迁移后看到 `channel_member` / `channel_read` / `channel_budget` **原样保留**，这样我有一条回退面。
56. 作为本机用户，我想让当前代码的**读路径只读 `target_*`**、既有端点的读口径一个字不改，这样旧表里的值不会被读成第二正本。

## Implementation Decisions

> 本规格可引用 `file:line` 作**判据落点**；实施票按此落地。术语一律用 `CONTEXT.md` 的**数据目录** / **版本闸门** / **Schema 版本** / **数据迁移** / **备份**。

### D0. 决策归属

本规格里有四件事由 `orca orchestration ask` 提交本票 coordinator **人定**后才落盘（回信原文逐字见 N3）：

| 项 | 裁定 | 落到本规格 |
| --- | --- | --- |
| 测试接缝 | **唯一接缝 = CLI 进程入口**（A） | T2 |
| 弃用别名语义 | **真别名：与 `--migrate` 行为逐字相同**（A） | D11、S13 |
| 沿革清单要求显式落定的默认值口径 | 三列取目标 `SCHEMA` 的 DDL 默认值（`theme='system'` / `auto_claim=0` / `claimed_at=NULL`） | D6、D7 |
| 退出码 `4` 在新路径下的去向 | **保留现状语义并让它继续可达**：迁移入口与别名在「版本已等于目标版本、但形态不是当前 `SCHEMA` 形态、且有业务数据」时返回 `4` | D2、S2、User Stories K |

S1–S18 的行为契约与 ADR-0015 的决策来自上一张票（设计票），本规格不改其决策内容。本票 ask 另行授权的**最小措辞对齐**（ADR-0015 §1 退出码表补一行、§5 的「只跑形态步骤」一句；设计笔记 §1.2 E1 行与 §3 S13 行）见 D11、D14 与 N3；`app/specs/schema-migration-inventory.md` 一字不改。

### D1. 命令面

- 迁移入口是 `python -m alibot --migrate [--data-dir <数据目录>]`：**布尔旗标**，与 `--repair-targets` / `--data-dir` 同族；**不引入子命令**（本仓 CLI 是单 argparse 入口，`app/alibot/__main__.py:37-54`）。
- `--migrate` 是**唯一**迁移入口。任何启动路径（无旗标）都不自动迁移——`create_app` 之前收口，不起监听、不跑 uvicorn。
- `--help` 列出该旗标及其说明。

### D2. 退出码

迁移入口与别名的**答复集合是 `{0, 3, 4, 5}`**；S2 的三类语义（`0` / `3` / `5`）不变，`4` 是把既有的「库形态不对」答复纳入同一集合（本票 ask 追加裁定，见 D0 / N3）。

| 码 | 判据 | 可观察验收 |
| --- | --- | --- |
| `0` | 迁移成功；或库里版本已是目标版本**且形态完好**（无事可做）；或没有库文件的空目录 | 进程退出 `0`；迁移成功时库的 `schema_version` = `SCHEMA_VERSION` 且报告给出步骤与行数 |
| `3` | 库不被本代码接受：版本低于 3 / 版本号缺失但有业务数据 / 认不出的号 / **未来版本** | stderr 含新拒绝正文（库路径 + 两个版本 + `--migrate` + 备份指引）；库文件 sha256 前后一致；三条路径同一个答复 |
| `4` | 库**不被本入口处置**（形态不对）：版本已**等于**本代码版本，但缺当前 `SCHEMA` 声明的对象（复用既有的 `_CURRENT_REQUIRED_TABLES`，`app/alibot/repair.py:97`——以实施票读取的既有常量为准），**且**库里有业务数据 | 退出 `4`；**不做任何写入、不建备份**：库文件 sha256 前后一致、数据目录里不出现新的备份副本。与 `5` 的区分：`4` 是「还没动手」，`5` 是「已经动手、失败并已回滚」 |
| `5` | 迁移失败，**已回滚**（含备份失败） | 退出 `5`；原库 sha256 不变；不存在半迁移痕迹（无「新表建了但数据没搬」的中间态） |

区分口径（必须可观察）：`3` 与 `4` 都发生在**任何写入之前**，区别是「库不被本代码接受（版本问题）」与「版本匹配但形态不是本入口能处置的」；`5` 发生在**动手之后**且已回滚。**不设「部分完成」退出码**：单事务下该状态不可达。普通启动路径的「非 loopback ⇒ 退出码 `2`」不变。

**空库口径不变**：没有库文件、或没有业务数据且缺表 ⇒ 退出 `0`，不凭空建库（S10）。

### D3. 版本闸门与拒绝正文

- 闸门语义不变：在任何 schema 变更之前比对库版本与本代码常量；**拒绝路径不改库文件一个字节**（`PRAGMA journal_mode = WAL` 等任何会改文件头的动作都必须排在闸门之后，`app/alibot/db.py:788-799` 的既有纪律）。
- 拒绝正文必须包含：库路径、库里的版本、本代码需要的版本、`--migrate` 命令、备份指引。
- 拒绝正文**必须不再出现**「本版不做数据迁移」这句话。
- 三条路径（启动 / `--migrate` / `--repair-targets`）对同一个库给出同一个答复与同一个退出码。

### D4. 支持的源版本范围

- 从 **3** 连续支持到 `SCHEMA_VERSION`。理由（沿革清单 §0.1）：号段起点其实是 1，但 **3** 是改名 worksplice → alibot 落地时的号，是**唯一**同时存在于新旧数据目录的号；v1 / v2 的库只可能在旧数据目录 `~/Worksplice`，`app/README.md` 已明写改名不保留兼容。
- **拒绝**（退出码 `3`）：版本低于 3；版本号缺失**但库里有业务数据**（判据是 `BUSINESS_TABLES` 里任意一张表有任何一行，`db.py:109-130`）；认不出的版本号；未来版本。
- **未来版本一律拒绝**（库版本 > 代码版本），三条路径一致：本仓没有降级步骤，「旧代码打开并改写新版库」是数据损坏的唯一来源。

### D5. 迁移步骤的组织（注册表 + 形态步骤）

- **骨架是逐版步骤注册表**：每步声明 `from_version → to_version`，**严格 +1、唯一、链连续覆盖 `3..SCHEMA_VERSION`**，执行器从库里的版本起**逐步走、不跳步**。
- 步骤内部允许两种实现形态（组合，不是二选一）：**显式数据搬迁**（如 channel 型作用域数据从 `channel_*` 搬到 `target_*`）或**按目标 `SCHEMA` 幂等对齐**（建表 / 加列用 `IF NOT EXISTS` 兜底）。
- **链前另有一个形态步骤（shape-conditioned）**：不依赖版本号，只看形态。判定「`channel` 行在，而 channel 型的**影子行 / 成员 / 已读 / 预算**有缺」即执行搬迁，幂等（重复跑改动 0 行）。四张表必须一起补齐——只补三张会让 `GET /api/channels/{id}/budget` 从 404 变成「200 且 `used` 归零」，即沉默抹掉一个已耗尽的预算（`app/alibot/repair.py:29-33` 的既有记录）。
- 形态步骤是 `--migrate` 与别名共同的**前置**；它存在的原因是 #37 事故形态：库曾被 v4 代码打开、`schema_version` 就地改写成 4、新表建出来但全空、旧表数据还在（修复见 `8c9899d` / PR #38 / issue #37）。按版本号走链会**跳过** `3 → 4`，所以形态步骤不能省。

### D6. 逐版内容（沿革清单的承重事实）

每一步的**主改动**如下表（沿革清单的逐版事实）。所有步骤另外遵循同一条**对齐兜底**：`IF NOT EXISTS` 式地向**当前 `SCHEMA` 声明的对象集**补齐，幂等、只增不减。因此「读数 ↔ 结构」的歧义（例如缺 `reminder` 的 v10 树）在推进中被吸收，而终态判据（D7）始终是唯一的对齐目标。链是**单调**的：不删既有表与列，不因为某个分支局部树缺某对象就把它删掉。

| 步骤 | 该步的库级事实 | 数据搬迁要求 |
| --- | --- | --- |
| `3 → 4` | 新 `target(id, kind, created_at)`；`channel_member/read/budget` → `target_member/read/budget` 三处**表名 + 列名**改名；`message.target_id` / `round_outcome.target_id` 加 `REFERENCES target(id)`（列本身没动） | **是——本区间唯一必须搬既有行的改动**：每个既有 channel → 一行 `kind='channel'` 的影子 target（`id` 与 `channel.id` 同值），三张旧表的行按 `channel_id → target_id` **逐列**搬到新表。影子行必须最先落（新表的引用约束指向它）。列名映射必须显式写出，不赌列顺序 |
| `4 → 5` | 新 `task` 表（含列级 `target_id UNIQUE` 与表级 `UNIQUE(target_id, id)`）；`message.task_ref` 可空列；复合外键 `(target_id, task_ref) → task(target_id, id)`；2 条 `BEFORE INSERT` 触发器 | 否（纯加法；`task_ref` 取 `NULL` 语义正确）。重建表时必须保留 `UNIQUE(target_id, id)`，否则外键建不上 |
| `5 → 6` | `target.dm_peer_member_id` 可空列 + **部分唯一索引** `idx_target_dm_peer_unique`（`WHERE kind='dm' AND dm_peer_member_id IS NOT NULL`） | 否（存量行为 `NULL`，索引 `WHERE` 显式排除 `NULL`）。这是**唯一性收紧**：遇到存量冲突行建不上索引 ⇒ 必须显式检出并处置（拒绝升级），不得假设一定建得上 |
| `6 → 7` | 新单行表 `workspace_settings`（`CHECK (id = 1)`） | 否（纯加法）；迁移后应补 `id = 1` 那行，缺省值 = `zh-CN` + `comfortable`。`locale` 的默认值在 DDL 字面量与 Python 常量两处出现，不得漂移 |
| `7 → 8` | 新 `reminder` 表（`channel_id` 可空、`REFERENCES channel(id)`——注意引用的是 `channel` 不是 `target`） | 否（纯加法） |
| `8 → 9` | 新 `attachment` 表 + 非唯一索引 `idx_attachment_message` + 2 条触发器（`attachment_no_delete`、`attachment_no_rebind`） | 否（纯加法；字节在库外的 `attachments/`）。`message_id` 可空是「先上传、后绑定」的承载点，不得写成 `NOT NULL` |
| `9 → 10` | `workspace_settings.theme TEXT NOT NULL DEFAULT 'system'` + **列级 CHECK** 词表扩展 | 否（有默认值，存量行回填 `'system'`＝缺省档）。**只补 `theme`，不删 `attachment`**（分支局部的 v10 树没有它，那不是对齐目标）。只写 `ADD COLUMN` 而漏 `CHECK` 会让库级约束与 `SCHEMA` 文本不一致 |
| `10 → 11` | 附件对象补齐 + 触发器**替换**：删 `attachment_no_rebind`，建 `attachment_metadata_immutable`（管所有行的元数据列集）与 `attachment_binding_is_immutable`（管 `message_id` 改绑） | 否（不改存量数据，只约束未来写入）。**触发器是「先删后建」而不是「`IF NOT EXISTS` 就够」**：`CREATE TRIGGER IF NOT EXISTS` 使「建」幂等但**不使「替换」幂等**，曾按 v9 建过旧触发器的库会出现新旧并存；缺 `attachment` 表的 v10 树也由本步的对齐兜底建出 |
| `11 → 12` | `agent_config.auto_claim INTEGER NOT NULL DEFAULT 0 CHECK (auto_claim IN (0,1))`（列级 CHECK）+ `task.claimed_at TEXT` 可空列 | 否（有默认值 / 可空）。存量 `auto_claim = 0`（关闭，行为安全缺省）；存量 `claimed_at = NULL`（= 从未被认领过，升级后仍可被认领一次并开一次世代） |

**三条必须点明的沿革事实**：

1. **`3 → 4` 是唯一必须搬既有行的改动**；其余各步是纯加法、默认值回填或触发器替换。
2. **`8` 与 `9` 从未作为 `main` 的读数存在过**（它们是分支局部值；`reminder` 随 PR #80 落 main 时读数已是 10，`attachment` 随 PR #83 落 main 时读数已是 11）。因此 `7 → 8` / `8 → 9` 这两步对 main 用户是**空步**，但**仍必须是链上的连续一环**——它们是分支局部号段的库唯一的推进路径，也是链连续性检查的一部分。
3. **同一个读数可能对应不同结构**：读数 10 在 main 上先后对应两棵不同的树（`7f1cb99` 无 `reminder`、`e1c523d` 有 `reminder`）。因此每步的「对齐」目标是**当前 `SCHEMA` 声明的对象集**，不是某个猜出来的历史树；缺表的 v10 库因此在推进中自然收敛。

### D7. 迁移终态契约

一次成功的迁移必须同时满足：

- `schema_meta.schema_version` = 当前 `SCHEMA_VERSION`；
- 当前 `SCHEMA` 声明的**表、列、索引（含 partial 与隐式唯一约束）、触发器**在库级解析形态上齐备且与 `SCHEMA` 文本一致（列级 `CHECK` 也在此列）；
- 各业务表的行数与迁移前一致，除新表、按目标形态补齐的默认行（如 `workspace_settings` 的 `id = 1` 行）；
- **唯一例外**：`channel_member` / `channel_read` / `channel_budget` 三张旧表**原样保留**（它们不在当前 `SCHEMA` 里，属于回退面）；
- 未迁移的库（拒绝路径）与迁移失败的库（回滚路径）**不满足**上述任何一条。

### D8. 备份、事务与审计

- **备份**：迁移前自动复制**整个数据目录**（含 `attachments/`）到**同级** `<数据目录>-backup-<from>-to-<to>-<UTC 时间戳>`。备份单位是数据目录（与 `app/README.md` 既有口径一致：只备份 `alibot.db` 是「有元数据、没字节」的半份）。
- **备份失败即拒绝迁移**（退出码 `5`），不退化成「放行 + 警告」。
- **事务**：`BEGIN IMMEDIATE` → DDL + 数据搬迁 → `COMMIT`。SQLite 的 DDL 是事务性的 ⇒ 中断落在回滚一侧，库停在原版本且仍可被原版本代码打开。**不存在**「新表建了但数据没搬」的中间态。
- **审计**：每次真正执行的迁移写一条 **append-only** 记录（from、to、起止时间、结果、备份路径）；**人类面没有任何写入口**（不存在可写它的 HTTP 端点）。

### D9. 幂等、无事可做与空目录

- 已是目标版本的库：改动 0 行、退出 `0`、**不新建备份**。
- 空数据目录（没有库文件）：退出 `0`，**不凭空创建库**（与 `--repair-targets` 既有口径一致）。

### D10. 预演（`--migrate --dry-run`）

- 在**数据目录内的临时副本**上跑**完整迁移链**：`alibot.db` 与旁边的 `-wal` / `-shm` 一并复制（只复制主文件会读到不完整状态）。
- 报告：将执行的步骤清单 + 每步将改动的行数 + **原库 sha256 的前后两个读数**（必须一致）。
- 结束后删除副本：数据目录里不留临时副本，原库零字节改动。

### D11. 弃用别名 `--repair-targets`

- 保留为**已弃用别名**：与 `--migrate` 同入口、同退出码，先打印一句「请改用 `--migrate`」；README 指引改指 `--migrate`；下个版本周期再删。
- 版本门放宽为 `[3, SCHEMA_VERSION]`（不再要求「恰好等于当前版本」），因为半改名库的号已是 4 而代码常量是 12。
- **别名放宽的是「离目标有多远」，没有放宽「方向」**：未来版本一个都不碰。
- **执行语义（本票 ask 裁定 (A)「真别名」）**：`--repair-targets` 与 `--migrate` **行为逐字相同**——都先跑形态步骤（不可省的前置），随后走**同一条逐版链**；同一个库上两条路径给出**同一结果、同一退出码**。别名只多打印一句「请改用 `--migrate`」。
- 因此别名对半改名库（`stored=4`、影子行缺失）的终态与 `--migrate` 相同（推进到目标版本且形态补齐），而不是「停在 4、用户还得再跑一次」。这条正是设计笔记 §1.2 Q5 与 §3 S13 的「同一入口、同一条链、同一退出码、同一结果」；被否的「别名只跑形态步骤」会复活 Q5 已否决的「同一个库、两个答复、两套语义」（例如 v7 库跑别名得到「成功但什么都没变、仍打不开」）。
- **上游正本的同步修订（本票 ask 授权的最小范围）**：`docs/adr/0015-schema-migration-is-explicit-and-forward-only.md` §5 的「然后**只跑形态步骤**」，以及 `app/specs/schema-migration-design-notes.md` §1.2 E1 行、§3 S13 行，按本裁定做了**最小措辞对齐**（只改与本裁定直接对应的句子，不动其它段落与决策内容）；`app/specs/schema-migration-inventory.md` 一字不改。

### D12. 兼容面（旧表与读路径）

- 迁移后 `channel_member` / `channel_read` / `channel_budget` **原样保留**；不 `DROP`、不双写。
- 当前代码的**读路径只读 `target_*`**；既有端点的读口径一字不改（未读、预算、成员面读数与迁移前一致）。
- 用一条测试断言**旧表名不出现在读路径的 SQL 常量里**（旧表名只允许出现在迁移 / 修复模块与测试里）。
- **边界（必须写清，避免误伤）**：「这个库算不算空库」的判据 `BUSINESS_TABLES`（`app/alibot/db.py:109-130`）里**同时**列着新旧两代表名——它是**空库判定**，不是读路径，**不在**该断言范围内。`BUSINESS_TABLES` 保持不动。

### D13. 纪律的强制点

此后每次 schema 变更必须随票携带一条 `from → to` 步骤，漏带者在三处失败：

## Testing Decisions

### T1. 好测试的判据

只断言**外部可观察行为**：退出码、stdout / stderr 报告文本、数据目录与库的终态（`schema_version`、PRAGMA 级对象清单、各表行数）、文件 sha256。**不**断言私有函数、SQL 文本、注册表内部表示（唯一例外见 T4 的结构性断言）。理由：迁移的内部实现（建表 vs 重建表、步骤怎么分组）应当可以演进而不重写测试。

### T2. 唯一测试接缝：CLI 进程入口（本票 ask 裁定）

- **接缝**：真实子进程 `python -m alibot --migrate [--dry-run] --data-dir <tmp 数据目录>`（别名同理），配一个**磁盘上的真实数据目录 fixture**；断言只落在外部可观察面：退出码、stdout / stderr 报告、数据目录与库的终态、文件 sha256。
- **为什么它是最高且最少的那个**：迁移能力的用户契约就是「跑这条命令 → 看退出码与数据目录状态」，CLI 之上没有更高的层；它同时是**既有**接缝——`app/tests/test_target_repair.py:419-474` 已经在用真实子进程跑 `python -m alibot --repair-targets --data-dir <dir>` 并断言退出码与 stdout，`app/tests/test_schema_version_gate.py` 已用显式 DDL 在 `tmp_path` 造 v3 形态库并在打开前后做版本 / 表清单 / 行数快照。一个接缝覆盖 S1–S10、S12–S16 的全部外部行为。
- **S11 / S17 的链连续性落在同一接缝上**：v3 fixture 上的 `--migrate --dry-run` 报告必须列出「从库版本到 `SCHEMA_VERSION`」的**连续**步骤表（每步严格 +1）——某步 `from` 落后（模拟 `9 → 11`）或 bump 号却不带步骤，都会让这份计划断掉 ⇒ 测试红。因此不需要再开一个读注册表内部的接缝。
- **被否的接缝与代价**：
  1. **`Database` 版本闸门**（construct `Database(data_dir)` / `SchemaVersionMismatch`）：只能观察闸门的裁决与文案，看不到退出码、备份、单事务、审计、预演、幂等 ⇒ 只用它则 S5–S10 不可测；并用则多一个与 CLI 完全重复的接缝，且把测试耦合到内部异常类型。
  2. **步骤注册表**（直接读步骤表数据结构）：内部表示；它要守的不变量（连续、+1、覆盖 `3..N`）在预演计划里已是外部可观察事实，再开一个接缝去读它 = 耦合内部表示，且是第二个接缝，违反「越少越好」。
  3. **端到端数据目录**：与 CLI 入口是同一层（CLI 本身就是带 `--data-dir` 的端到端），单列会变成「两个名字、一个接缝」。
- **既有接缝的维护（不算新增接缝）**：S16 要求在 `app/tests/test_schema_version_gate.py:184` 把断言旧句「不做数据迁移」改为断言新正文——那是既有 `Database` 接缝上一条过时断言的同步；T4 的结构性断言沿用 `test_target_repair.py` 的模块图取证体例。

### T3. 行为契约（S1–S18）→ 唯一接缝上的观察点

| S | 契约要点 | 在唯一接缝上的观察 |
| --- | --- | --- |
| S1 | `--migrate` 布尔旗标、唯一迁移入口、不自动迁移、不监听 | `--help` 列出该旗标；`--migrate` 跑完进程退出且不起监听；无旗标启动不迁移 |
| S2 | 退出码 `0` 成功 / 已是目标版本；`3` 拒绝；`4` 库形态不是本入口能处置的；`5` 迁移失败已回滚；无「部分完成」码 | 当前版且形态完好的库 → `0`；可迁的旧版库 → `0`；未来版 → `3`；版本已等于目标版本但缺当前 `SCHEMA` 对象且有业务数据的库 → `4`（库 sha256 不变、不建备份）；在一步搬迁中注入失败 → `5` |
| S3 | 拒绝正文含库路径 / 两个版本 / `--migrate` / 备份指引，**不含**「本版不做数据迁移」；库零字节改动 | stderr 文本命中新正文断言；库文件 sha256 前后一致；退出码 `3` |

| S9 | 每次真正执行的迁移写一条 append-only 审计（from/to/起止/结果/备份路径）；人类面无写入口 | 迁移成功后库里能查到该条记录；HTTP 面不存在可写它的端点 |
| S10 | 幂等 / 无事可做 / 空目录不建库 | 连跑两次：第二次报告改动 0 行、退出 `0`、备份目录数不增；空目录跑完目录里仍没有 `alibot.db` |
| S11 | 链连续性：覆盖 `3..SCHEMA_VERSION`、每步严格 +1、唯一、不跳步 | v3 fixture 的 `--dry-run` 计划是连续步骤表；人为把某步 `from` 改成落后号（或 bump 号不带步骤）⇒ 该测试红 |
| S12 | 形态步骤不依赖版本号、四张表一起补齐、幂等；`--migrate` 与别名都先跑它 | 造 `stored=4`、影子行缺失的库 ⇒ 两条路径都补齐（成员 / 已读 / 预算 / 消息面恢复，且已耗尽预算的 `used` 不被归零）；再跑一次 ⇒ 改动 0 行 |
| S13 | 别名与 `--migrate` 行为逐字相同、同退出码、先打印一句弃用提示；版本门同为 `[3, SCHEMA_VERSION]` | 对同一个库分别调用两条路径 ⇒ 同一结果、同一退出码；stdout 含弃用提示 |
| S14 | 未来版本一律拒绝，三条路径同一答复 | 造 `stored=SCHEMA_VERSION+1` 的库：启动 / `--migrate` / `--repair-targets` 都返回 `3`，库 sha256 不变 |
| S15 | 旧表原样保留；当前读路径只读 `target_*`；既有端点读口径不改 | 迁移后未读 / 预算 / 成员面读数与迁移前一致；结构性断言：旧表名不出现在读路径的 SQL 常量里 |
| S16 | 旧断言同步 | `app/tests/test_schema_version_gate.py` 绿；旧句不再出现在拒绝正文里 |
| S17 | 纪律三处强制（源码链测试 / 票面 DoD / ADR-0015） | bump 号却不带步骤的模拟 diff ⇒ S11 的测试红；票面 DoD 判据由 ADR-0015 提供 |
| S18 | 文档面（ADR-0015 落盘、`CONTEXT.md` 五词条 + 附件修订、README 两段） | **既有事实**（上一张票已落盘，见 `CONTEXT.md` 的 `### 数据与版本` 小节与 `app/README.md`）；本规格以它们为前提，实施票不重做 |

## Further Notes

### N1. 沿革清单的关键事实（本规格已吸收）

- 取值基线：`main` @ `36e452e`，`SCHEMA_VERSION = 12`。
- main 实际读数序列：`3 → 4 → 5 → 6 → 7 → 10 → 10 → 11 → 12`；`8` / `9` **从未**作为 main 的读数存在。
- `3 → 4` 是**唯一**必须搬既有行的改动（影子行 + 三表逐列改名）。
- 读数与结构不是一对一：读数 10 在 main 上先后对应两棵树（`7f1cb99` 无 `reminder`、`e1c523d` 有 `reminder`）。
- 所有 DDL 都是 `IF NOT EXISTS` ⇒ 重跑 `SCHEMA` 对既有库是 no-op，**不能**用来实现迁移；唯一防线是版本闸门。
- `schema_meta` / `member` / `channel` / `remote_consent` 四张表在 `3 → 12` 全区间无结构变化；区间内没有既存列被删除、没有既存列的 `NOT NULL` / 默认值 / 类型被修改、没有「新增无默认值的 `NOT NULL` 列」加到既有表。

### N2. 未核实项（不得用推测补齐）

- `v8` / `v9` 是否曾被任何非 main 分支**部署**过（是否产生过真实 v8 / v9 库）：本仓只读源码与 git 历史，不触碰本机数据目录，无法从仓库内证实。**契约上不依赖它**：`[3, SCHEMA_VERSION]` 内的任何读数都被接受。
- SQLite 对「向既有表补带 `CHECK` 的新列」的确切机制（是否必须重建表）：属实施票的机制问题，本规格只要求**终态与目标 `SCHEMA` 一致**（D7），不裁定 SQL 写法。
- 各版之间**数据行数**层面的迁移量：需要真实旧库样本；本规格只要求「保真数据 + 行数可核对」。
