## Problem Statement

同一个本机用户在多个项目里用**同一个 Agent**，但今天这个 Agent 的东西只活在单个项目根里。

`<workspace_root>/.alibot/` 是频道级项目边界（ADR-0021）：规则、技能、记忆、会话状态都跟着项目走。于是用户具体地遇到五件事：

1. **同一套规则要抄很多遍。** 每个项目都得把「你是谁、怎么说话、哪些事不要做」重新写进该 Agent 的 `agent_config.system_prompt`；改一处不会传到别的项目，几周后各项目的口径开始互相矛盾。
2. **同一套技能要装很多遍。** 频道级与 Agent 级的技能字节都在各项目的 `.alibot/skills/` 下；换一个项目就得重新安装一遍，项目目录一删技能就没了。
3. **长期记忆只在一个项目里长大。** 记忆落点是项目根内的成员分区（无项目根的私信落数据目录）。用户在 A 项目积累的偏好与背景，在 B 项目完全读不到；「跨项目复用同一个 Agent」在最关键的长期记忆上是空的。
4. **本地与 Docker 会分叉。** Docker 后端今天只把频道项目根挂到容器内的 `/workspace`。如果只让全局层在本地生效，用户切换后端就会**静默丢失**全局规则、技能与记忆——同一个 Agent 换一种执行方式就换了一个人。
5. **数据目录的可见性是一笔已经做出的取舍。** ADR-0031 把默认数据目录从可见的 `~/Alibot` 改到隐藏根下的 `~/.alibot/data/`，让全局层与数据目录共享一个命名空间。这会削弱「看得见就能复制」的可运维性；如果实现时顺手搬移用户数据或悄悄忽略旧位置，用户会以为自己的库没了。

这些不是五个独立需求，而是**同一个缺口**：Agent 没有一层**跨项目的、只读的素材归属**。缺了它，规则、技能与记忆就只能按项目重复维护，后端切换也无法保持一致。

## Solution

在**项目边界之外**增加一层**本机级的 Agent 全局层**，项目层目录结构一字不动：

- **全局层根固定为 `~/.alibot/`。** 成员家目录 `agents/<member_id>/` 承载 `rules/` 规则基座、`skills/` 成员私有全局技能、`memory/Memory/` 全局记忆与 `mcp.json` 全局 MCP 声明；`skills/` 是跨项目公共技能库；`data/` 是数据目录（属于应用可写的业务正本，**不属于**全局素材层）。
- **规则按唯一顺序拼装**：全局基座 → `agent_config.system_prompt` → 项目补充。三段都是文本原样拼接，后段冲突时胜出；无项目根的轮次（私信）只有前两段。
- **技能与 MCP 按「项目就近、同名覆盖」合并。** 技能四层：项目 Agent 级 > 项目频道级 > 全局成员家目录 > 全局公共技能库；MCP 三层：项目 Agent 级 > 项目频道级 > 全局成员家目录。同名只装配胜出的那一条，落选条目**不装配、不连接**，并给一条可读运行期提示。
- **记忆两处可读、默认写项目。** 全局记忆对应用**永远只读**，由人显式维护；私信无项目根时写入沿用数据目录侧的成员记忆。
- **Docker 后端额外只读挂载**成员家目录与公共技能库；数据目录（库与附件字节）**不进容器**；容器内文件工具的根仍只有 `/workspace`。
- **数据目录默认改为 `~/.alibot/data/`，但兼容优先、迁移显式。** 解析顺序是「显式覆盖 → 新默认已存在 → 旧 `~/Alibot` 已存在（兼容读取并提示）→ 新建新默认」；应用**绝不自动搬移**用户数据。
- **全局层是人的维护面。** 应用只读、只校验；目录缺失即该层缺席，不自动创建、不自动写入、不阻断本轮。
- **边界不变。** 全局层不是文件工具的工作路径，不新增可写根，三档**权限档**语义一字不动；远端全局 MCP 仍必须逐项做**远端数据流告知**。

## User Stories

### A. 规则拼装

1. 作为同一个本机用户在多个项目里使用同一 Agent 的人，我想让**全局基座**在任何一个配了项目根的频道里都生效，以便我不用把同一套规则抄进每个项目的 Agent 配置。
2. 作为用户，我想让 **`agent_config.system_prompt`** 排在全局基座之后、项目补充之前，以便我能在不删全局文件的前提下按单个 Agent 微调口径。
3. 作为用户，我想让**项目补充**排在最后并在冲突时胜出，以便某个项目可以对同一个 Agent 加更具体的约束。
4. 作为用户，我想让私信轮次只拼装「全局基座 + `agent_config.system_prompt`」，以便没有项目根时不会凭空出现一段项目规则。
5. 作为用户，我想让全局规则文件缺失时**该段直接缺席**，以便不会出现一个空的规则标题或一句「（无规则）」的噪音。
6. 作为用户，我想让规则文件不可读或不是 UTF-8 时只让该段缺席并记一条可读日志，以便一个坏文件不会让整轮失败。
7. 作为用户，我想在三段规则都为空时保留既有的身份句与回应 rubric，以便「没有自定义规则」不等于「Agent 失去行为纪律」。
8. 作为审查者，我想让每一段规则带一个**可读的段落标签**，以便从系统提示就能看出哪一段来自全局、哪一段来自项目。
9. 作为用户，我想让三段规则**原样拼接、不解析、不裁剪、不做语义合并**，以便顺序就是唯一判定依据，规则不会被某个隐藏的合并逻辑改掉。
10. 作为用户，我想让项目规则只落在项目层自己的 `rules/` 目录里，而不是复用我项目根下的 `AGENTS.md`，以便 alibot 的状态不会写进我自己的工具配置。

### B. 技能与 MCP 的四层优先级

11. 作为用户，我想让项目 Agent 级技能覆盖项目频道级同名技能，以便单个 Agent 能在共享频道里用自己那一版。
12. 作为用户，我想让项目层任一级的同名技能覆盖全局成员家目录里的技能，以便项目可以就近压过全局。
13. 作为用户，我想让全局成员家目录的同名技能覆盖全局公共技能库，以便更具体的归属胜出。
14. 作为用户，我想让同一个名字在某一轮的工具/技能清单里**只出现一次**，以便我不会看到两个同名技能同时挂上。
15. 作为用户，我想让落选的技能**不装配**、落选的 MCP 声明**不连接**，以便覆盖是真正的覆盖而不是「两个都挂着、谁先响应算谁的」。
16. 作为用户，我想在落选条目存在时看到一条**可读的运行期提示**（含名字与胜出层），以便排查「为什么我改的全局技能没生效」。
17. 作为用户，我想让全局技能保持**纯文件**——不进 `skill` 表、没有 hash 行、没有安装端点——以便全局层由我手工维护，不和应用的数据面混在一起。
18. 作为用户，我想让 `SKILL.md` 非法、路径越界或不可读的全局技能条目被**跳过**而其余技能照常装配，以便一个坏条目不会拖垮整轮。
19. 作为用户，我想让全局技能目录或公共技能库缺失时**零条技能、不报错**，以便没建全局层的人行为和今天逐字相同。
20. 作为用户，我想让全局 `mcp.json` 是非法 JSON 时全局层**零条声明**并记日志，而项目层声明不受影响，以便坏文件只影响它自己那一层。
21. 作为用户，我想让全局 MCP 的 `env_names` 仍然**只存变量名**、值只从进程环境读，以便库与文件里都不出现密钥。
22. 作为用户，我想让全局 stdio MCP 的 `cwd` 仍是项目侧的成员分区（Docker 内是 `/workspace`），以便全局声明不会把进程的工作目录搬到全局层。

### C. 记忆的读写

23. 作为用户，我想让长期记忆**读两处**——项目记忆与全局记忆——以便跨项目保留一套背景与偏好。
24. 作为用户，我想让应用只把新记忆**写进项目侧**，以便全局记忆不会在应用运行时被悄悄改写。
25. 作为用户，我想让私信轮次读「数据目录侧成员记忆 + 全局记忆」、写入仍落数据目录侧，以便没有项目根时沿用既有口径。
26. 作为用户，我想让全局记忆对应用**永远只读**，以便它是我显式维护的素材，不是自动同步盘。
27. 作为用户，我想在未开启长期记忆时两层都**不挂、不建目录**，以便关闭记忆不留空壳目录。
28. 作为用户，我想让全局记忆目录缺失或不可读时只读项目侧并记日志，以便降级是「少读一处」而不是「整轮失败」。
29. 作为用户，我想让 `sessions/` **只在项目层、不共享**，以便跨项目的会话状态与工具缓存不会串味。
30. 作为用户，我想让同一成员的轮次串行、应用侧写入天然不并发，以便不需要为全局记忆引入额外的写锁；跨进程同时打开同一项目根仍不在支持范围。

### D. Docker 只读挂载

31. 作为 Docker 后端的用户，我想让成员家目录被**只读**挂进容器，以便容器里的 Agent 也能读到全局规则、技能与记忆。
32. 作为 Docker 后端的用户，我想让公共技能库也被**只读**挂进容器，以便跨项目共享技能不因切换后端而丢失。
33. 作为用户，我想让数据目录（库与附件字节）**不进容器**，以便容器拿不到业务正本与附件内容。
34. 作为用户，我想让 local 与 Docker 对全局层的可观察行为一致，以便切换后端不会静默改变这个 Agent。
35. 作为用户，我想让容器内文件工具的根**仍只认 `/workspace`**，以便全局挂载点不会变成第二个可写工作根。
36. 作为用户，我想在成员家目录或公共技能库不存在时**跳过对应挂载**、容器照常启动，以便没建全局层的人不受影响。
37. 作为审查者，我想让全局挂载点**不是文件工具的合法输入**，以便路径越界检查的目标集合不扩大。

### E. 数据目录的解析顺序

38. 作为用户，我想让 `--data-dir` 与 `ALIBOT_DATA_DIR` **优先于一切默认**，以便既有显式覆盖的语义完全不变。
39. 作为用户，我想在新默认 `~/.alibot/data/` 已存在时直接使用它，以便我按文档搬过去之后应用认这个位置。
40. 作为用户，我想在只有旧 `~/Alibot` 存在时**继续用旧位置**并看到一条可读提示，以便升级不会让我以为库丢了。
41. 作为用户，我想在两者都不存在时新建 `~/.alibot/data/`，以便全新安装只得到一个隐藏根。
42. 作为用户，我想在新旧目录**同时存在**时确定地选择新默认，并在启动提示里说明旧位置被忽略，以便结果不依赖时间戳或目录顺序。
43. 作为用户，我想让应用**绝不自动搬移**旧数据，以便「把库搬到新位置」永远是我显式做、且先做整目录备份的动作。
44. 作为用户，我想让启动时**照旧打印实际数据目录**（含它是显式覆盖、新默认、旧位置兼容还是新建），以便隐藏目录下我也能随时确认应用在用哪里。
45. 作为用户，我想让**备份**单位仍是整个数据目录（库 + 附件 + 审计台账），并让文档明确全局层不在其中、需要单独备份，以便我不会以为备了库就备全了。
46. 作为用户，我想让隐藏目录的备份与恢复在文档里给出**显式路径命令**，以便它不可见也仍然可运维。

### F. 全局远端 MCP 的确认

47. 作为用户，我想让全局 `mcp.json` 里的远端（`http` / `sse`）条目在**首次使用前必须确认**，以便全局层不会绕过数据面纪律。
48. 作为用户，我想让确认按合成标识 `global:<member_id>:<name>` 记录，以便同名条目在不同成员下互不串用确认。
49. 作为用户，我想让确认在重启后仍然有效（幂等、持久），以便我不必每次启动都重新点一次。
50. 作为用户，我想在人类面按「成员 + 名字」看到并提交这个确认，以便我清楚知道是哪个 Agent 的哪一条远端声明要出网。
51. 作为审查者，我想让这条确认复用既有的 `scope_kind='mcp'` 与自由文本 `scope_id`，**不新增 `scope_kind`、不改 schema、不 bump `SCHEMA_VERSION`**，以便不触发带 CHECK 的表重建。
52. 作为用户，我想让全局 stdio 条目**不需要确认**，以便本机进程不被无谓地挡一道。

### G. 安全与创建纪律

53. 作为审查者，我想让全局层**不是文件工具的工作路径**——Read/Write/Edit/Glob/Grep 的相对路径仍从项目根起算——以便根检查的语义不扩大。
54. 作为审查者，我想让全局层另设一道**只读守卫**，以自己的根做 `realpath` 并拒绝根外 symlink 祖先与根外目标，以便全局读取不会成为根外写入的跳板。
55. 作为用户，我想让 `read-only` / `ask-writes` / `trusted-writes` 三档**语义一字不动**、不引入 `BYPASS`，以便全局层只增加只读输入、不增加可写根。
56. 作为用户，我想让应用**绝不自动创建或写入**全局目录，以便「全局层是人的维护面」不是一句口号。
57. 作为用户，我想让全局层缺失就是**该层缺席**（规则空段、技能零条、记忆不挂、MCP 零条），以便第一次使用不必先手工建一套目录树。
58. 作为审查者，我想让全局根固定为 `~/.alibot/`、**不随 `--data-dir` 移动**，以便数据目录覆盖不会把素材层一起搬走。
59. 作为审查者，我想让全局层不新增任何可写根或第二工作根，以便权限档、Docker 挂载与根检查不会同时复杂化。

### H. 可观察读数与运维

60. 作为用户，我想让某一轮的技能/MCP 清单只反映**胜出条目**，以便清单本身就是合并结果的读数。
61. 作为用户，我想让落选条目的运行期提示能读出**名字与胜出层**，以便覆盖关系可解释。
62. 作为用户，我想让未确认的远端全局 MCP 在运行时读数里给出可读原因（`consent_required`），以便「没连上」不等于「配置坏了」。
63. 作为用户，我想让启动输出说明数据目录的**来源**，以便我不需要猜它用了新默认还是旧位置。
64. 作为用户，我想让文档明确写出全局层的单独备份命令与数据目录的隐式路径，以便隐藏根不会变成「忘了备份」。
65. 作为用户，我想在完全没有全局层时得到与今天**逐字相同**的行为，以便这项能力是纯增量、不是迁移。

## Implementation Decisions

### D1 · 两层归属与目录模型

**决定**：本机存在两层 Agent 素材归属，项目层结构一字不动，全局层是纯新增。

| 层 | 根 | 内容 | 写权限 |
| --- | --- | --- | --- |
| **全局层**（Agent 家目录） | `~/.alibot/agents/<member_id>/` | `rules/AGENTS.md` 规则基座、`skills/` 成员私有全局技能、`memory/Memory/` 全局记忆、`mcp.json` 全局 MCP 声明 | 只由人维护；应用只读 |
| **全局层**（公共技能库，可选） | `~/.alibot/skills/` | 跨项目公共技能 | 只由人维护；应用只读 |
| **数据目录** | 默认 `~/.alibot/data/` | `alibot.db`、`attachments/`、迁移审计台账 | 应用写；备份与搬迁单位 |
| **项目层** | `<workspace_root>/.alibot/` | 既有技能分区、记忆、会话、MCP 声明；**新增** `rules/<member_id>/AGENTS.md` | 维持现状 |

**语义**：全局层是**只读素材层**，不是文件工具的工作路径；数据目录与全局层共享 `~/.alibot/` 命名空间，但**不属于**全局素材层，也不在全局层备份内。`--data-dir` 只改变数据目录本身，不移动全局层根。

**可观察读数**：配置文件与目录归属可按上表逐项核对；`sessions/` 不出现在全局层。

### D2 · 数据目录的解析顺序

**决定**：数据目录按固定优先级解析，结果是**确定值**，不靠时间戳或目录顺序猜测。

| 优先级 | 条件 | 结果 |
| --- | --- | --- |
| 1 | `--data-dir` 或 `ALIBOT_DATA_DIR` | 使用显式值（既有语义不变） |
| 2 | 新默认 `~/.alibot/data/` 已存在 | 使用新默认 |
| 3 | 旧 `~/Alibot` 已存在 | 使用旧位置，并给可读兼容提示 |
| 4 | 两者都不存在 | 新建 `~/.alibot/data/` |

**同时成立**：第 2 与第 3 条同时成立时使用新默认，启动提示说明旧位置被忽略；**不删除、不搬移、不合并**两份库。迁移永远是显式动作：停应用 → 整目录复制 → 校验（库可打开、附件数量一致、台账存在）→ 指向新位置；复制前先做整目录备份。

**可观察读数**：启动时打印实际数据目录与其来源（显式覆盖 / 新默认 / 旧位置兼容 / 新建）；数据目录内容清单不变（库 + 附件 + 台账）。

### D3 · 规则的三段固定顺序

**决定**：系统提示的规则部分按唯一顺序拼装为三段：**全局基座 → `agent_config.system_prompt` → 项目补充**。

**接口语义**（轮次装配 seam 的输入/输出）：

- 输入：本轮 `(target_id, member_id)`；输出：**有序的规则段列表**，每段带可读段落标签与原文。
- 顺序是唯一判定依据，逐对成立：配置覆盖段胜过全局基座；项目补充段胜过前两段。
- 无项目根的轮次（私信）只产出前两段。
- 三段都是**文本原样拼接**，不解析、不裁剪、不做语义合并。
- 既有的回应 rubric、角色句、任务上下文仍排在配置覆盖段之后，顺序与措辞不变。

**错误降级**：

| 情形 | 行为 |
| --- | --- |
| 全局基座文件缺失 | 该段缺席；不写空标题；本轮继续 |
| 项目补充文件缺失 | 该段缺席；本轮继续 |
| 文件不可读 / 非 UTF-8 | 该段缺席 + 一条可读日志；本轮继续 |
| 两段规则都缺且配置为空 | 没有规则正文；既有身份句与 rubric 照旧 |
| 目录缺失 | 等同于文件缺失；**不创建目录** |

**可观察读数**：真实 provider 请求里的 system prompt 中，三段按上述顺序出现、各带标签；缺失段落不留下空标签。

### D4 · 技能与 MCP 的同名合并

**决定**：去重键是技能名 / MCP 声明名；只装配胜出的那一条，落选条目**不装配、不连接**。

| 对象 | 优先级（高 → 低） | 去重键 |
| --- | --- | --- |
| 技能 | 项目 Agent 级 → 项目频道级 → 全局成员家目录 → 全局公共技能库 | `name` |
| MCP 声明 | 项目 Agent 级 → 项目频道级 → 全局成员家目录 | `name` |

**接口语义**：合并发生在轮次装配 seam 内部，输入是各层的声明集合，输出是**每名恰好一条**的胜出集合，外加一份可读运行期提示（每个落选条目一条，含名字与胜出层）。项目层既有的「Agent 级覆盖频道级」方向不变；同一 scope 内重名沿用既有约束，不新增规则。

**全局技能是纯文件**：不进 `skill` 表、没有 hash 行、没有安装 / 编辑 / 删除端点。加载时校验 `SKILL.md` 存在、路径落在全局根内、内容可读；坏条目跳过并记日志，其余技能照常装配。

**全局 MCP 声明是文件**：`mcp.json` 的条目形状校验 transport（`stdio` / `http` / `sse`）、command / args / url 与 `env_names`；`env_names` 只存变量名，值只从进程环境读。非法 JSON ⇒ 全局层零条声明 + 日志；单条目形状非法 ⇒ 跳过该条目 + 日志；项目层不受影响。

**错误降级**：

| 情形 | 行为 |
| --- | --- |
| 全局技能目录 / 公共库缺失 | 全局层零条技能；不报错 |
| 全局 `mcp.json` 缺失 | 全局层零条声明；不报错 |
| 全局条目路径越界 | 跳过该条目 + 日志 |
| 落选条目 | 不装配；一条运行期提示 |

**可观察读数**：本轮工具/技能清单里同名只出现一次且来自胜出层；落选条目的提示可读。

### D5 · 记忆的读写落点

**决定**：记忆**读两处、写项目侧**；全局记忆对应用永远只读。

| 场景 | 读 | 写 |
| --- | --- | --- |
| 有项目根 + 长期记忆开启 | 项目记忆 + 全局记忆（只读附加工作目录） | 项目记忆 |
| 私信无项目根 + 长期记忆开启 | 数据目录侧成员记忆 + 全局记忆（只读） | 数据目录侧成员记忆 |
| 全局记忆目录缺失 | 只读项目侧；不报错 | 项目侧 |
| 全局记忆不可读 | 跳过全局侧 + 日志 | 项目侧 |
| 长期记忆关闭 | 不挂中间件、不建目录 | — |

**语义**：全局记忆以**只读附加工作目录**的形式挂给记忆中间件，不进入文件工具的根；`sessions/` 只在项目层、不共享。同一成员同时最多一轮 in-flight，因此应用侧写入串行；同一项目根内同一成员的多个 target 共享同一记忆目录；跨进程同时打开同一项目根不在支持范围。全局记忆没有应用写入，因此不存在应用侧的全局写竞争。

**可观察读数**：记忆文件的写入只出现在项目侧（私信为数据目录侧）；全局侧文件的 mtime 不因应用轮次变化。

### D6 · 全局层的只读守卫与权限边界

**决定**：全局层**不是文件工具根**，另设一道**只读守卫**。

- 文件工具（Read/Write/Edit/Glob/Grep）的相对路径仍从频道项目根起算；全局规则由宿主读出后作为提示文本注入，全局技能由装载器直接读文件，全局记忆作为只读附加工作目录挂给中间件。
- 全局只读守卫以**自己的根**做 `realpath`，拒绝根外 symlink 祖先与根外目标；它只提供读取，不提供项目根那样的写分区。
- Docker 侧的文件工具根检查仍只认 `/workspace`；全局挂载点不是文件工具的合法输入。
- **权限档不变**：`read-only` / `ask-writes` / `trusted-writes` 三档语义一字不动，不引入 `BYPASS`，也不因为全局层新增第四档。

**可观察读数**：根外路径与指向根外的 symlink 在文件工具层仍被拒绝；全局层路径不能作为文件工具的输入被写入。

### D7 · Docker 的第二个只读挂载

**决定**：在把频道项目根挂到 `/workspace` 之外，额外把成员家目录与公共技能库**只读**挂到容器内固定路径（本规格取 `/alibot-home`）。

- `~/.alibot/agents/<member_id>/` 与 `~/.alibot/skills/` 只读挂载；`~/.alibot/data/`（库与附件字节）**不进容器**。
- 成员家目录或公共库不存在时**跳过对应挂载**，容器照常启动；不创建目录。
- 容器内文件工具的根检查仍只认 `/workspace`；全局挂载点只供框架级技能装载器与记忆中间件读取。
- 只读挂载同时兑现「全局记忆只读」在容器边界上的语义；local 与 Docker 对全局层的可观察行为一致。

**可观察读数**：容器配置里出现第二个只读 bind；容器内无法写全局挂载点；数据目录路径在容器内不可见。

### D8 · 全局远端 MCP 的数据面确认

**决定**：全局 `mcp.json` 的远端（`http` / `sse`）条目在首次使用前必须确认；stdio 不需要。

- 确认键使用**合成标识** `global:<member_id>:<name>`，写进既有**远端数据流告知**的确认行，`scope_kind` 仍为 `mcp`；幂等，按 `(scope_kind, scope_id)` 唯一。
- **不新增 `scope_kind`、不改表、不 bump `SCHEMA_VERSION`**。若实施选择新增 `scope_kind`，会触发带 CHECK 的表重建——本规格明确不选这条路。
- 未确认 ⇒ 该条目**不连接**，运行时读数给可读原因（`consent_required`）。
- 人类面新增一个按「成员 + 名字」确认的入口；入口形态属实施细节，但必须能唯一定位到这条声明。
- `env_names` 仍只存变量名，库与文件都不存密钥；凭证仍只从进程环境读。

**可观察读数**：未确认时工具清单里没有该远端工具、且运行时状态给 `consent_required`；确认后重启仍保持确认。

### D9 · 创建纪律与统一的降级表

**决定**：应用**绝不自动创建或写入**全局目录；缺失即缺席。

| 情形 | 行为 |
| --- | --- |
| 全局根不存在 | 规则空段、技能零条、MCP 零条、记忆不挂全局只读目录；本轮继续并记可读提示 |
| 成员家目录不存在 | 同上，不影响项目层 |
| 公共技能库不存在 | 只少这一层来源 |
| 项目层目录缺失 | 维持既有创建与守卫语义（项目层仍由应用创建） |
| 数据目录不存在 | 按 D2 解析顺序创建/使用 |

不阻断本轮、不生成空目录、不写占位文件。

**可观察读数**：运行一轮后全局根下不出现任何新文件或新目录；本轮仍正常收口。

### D10 · 可观察读数总表

| 行为 | 读数落点 |
| --- | --- |
| 规则顺序与段落标签 | 真实 provider 请求的 system prompt |
| 技能/MCP 胜出条目 | 本轮工具与技能清单 |
| 落选条目提示 | 运行期可读提示（名字 + 胜出层） |
| 未确认远端 MCP | 运行时读数原因 `consent_required` |
| 记忆只读 | 全局侧文件 mtime 不因轮次变化；项目侧出现写入 |
| Docker 挂载 | 容器配置中的 bind 列表 |
| 数据目录来源 | 启动输出 |
| 「不自动创建」 | 运行前后全局根的目录清单 |

### D11 · Seam 选址（已由 coordinator 裁决）

**决定**：**seam 总数 = 2，全部复用既有装配点，零新增服务模块**。

- **Seam A（核心）：轮次装配 seam。** 落在成员面适配接缝的既有依赖注入构造器上；为全局层新增的读路径钩子（规则基座 / 全局技能 / 全局记忆 / 全局 MCP）记为**既有构造器上的新增注入参数**，不是新 seam。它的语义是：只读、目录缺失即该层缺席、应用不自动创建或写入、不进入文件工具根。工作区装配层、记忆装配层、技能装载器与 MCP 装配层都在这一 seam 之内。
- **Seam B（第二处，既有）：进程启动 seam。** 数据目录解析发生在任何轮次之前，单列为进程启动边界；用临时目录覆盖四种解析顺序，并断言「绝不自动搬移」。
- **不单列 C：** 全局远端 MCP 的确认不是独立 seam——它是 Seam A 的输出后果，复用既有的确认行与「未确认不连接」读数面。

**归属**：coordinator 于本票 ask 中裁决；被否方案见 Testing Decisions 的 T5。

### D12 · 备份与文档

**决定**：**备份**单位仍是整个数据目录（库 + 附件 + 审计台账）；全局层不在其中，必须单独备份。

- 文档必须给出隐藏目录的**显式路径备份与恢复命令**（全局层与数据目录各一份）。
- 启动时照旧打印实际数据目录；数据目录来源（显式 / 新默认 / 旧位置兼容 / 新建）一并可读。
- 应用不提供自动迁移；如需搬迁，文档给出「停应用 → 整目录复制 → 校验 → 指向新位置」的显式步骤，并说明复制前先做整目录备份。
- `--data-dir` 只改变数据目录本身，不移动全局层根。

**可观察读数**：文档中的命令可直接执行；备份内容清单与数据目录内容一致；全局层单独备份清单可核对。

## Testing Decisions

### T1 · 什么算好测试

只断言**外部可观察行为**：真实 provider 请求里的 system prompt 与工具清单、工作区/容器配置对象里的 bind 与路径、记忆文件的磁盘事实、HTTP 与运行时读数、启动输出与退出码、`git diff`。**不**断言私有函数名、SQL 文本、注册表内部表示、目录遍历顺序。

测试必须**不读写真实的 `~/.alibot/`**：把全局根与 HOME 指向临时目录；不联网、不依赖真实用户数据。

### T2 · Seam A：轮次装配 seam

- **接缝**：既有成员面适配接缝的依赖注入构造器 + 公开的装配函数（工作区装配、记忆装配、技能装载、MCP 装配）。全局层的新增读路径钩子作为**既有构造器的新增注入参数**，不新开第二个注入点。
- **怎么观测**：用进程内 stub provider 跑真实 seam，读它收到的 system prompt 与工具清单；用公开装配函数直接读 mount / 装配结果；断言磁盘事实（记忆写入位置、全局根未被创建）。
- **为什么它是最高且最少的那个**：用户契约就是「这一轮 Agent 看到了什么、能调什么、写到哪里」，而这三件事都在这一 seam 的输出里可观察；再高的 HTTP 面看不到系统提示与工具装配，再低的私有函数会耦合实现。
- **覆盖范围**：规则三段顺序与降级、技能四层合并、MCP 三层合并与确认前不连接、记忆两处读一处写、Docker 挂载对象。

### T3 · Seam B：进程启动 seam

- **接缝**：进程启动时对数据目录的解析（显式覆盖 / 环境变量 / 新旧默认）。
- **怎么观测**：在临时 HOME 下构造四种目录组合，启动进程并读实际使用的目录与输出说明；断言新旧同时存在时选新默认、旧位置只兼容读取、任何情况下都不发生搬移（旧目录内容与 mtime 不变）。
- **边界**：不为测试引入第二套解析实现；测试只经进程启动路径断言。

### T4 · 要测的模块与仓库先例

| 行为 | 测试落点 | 先例（自行核对后引用） |
| --- | --- | --- |
| 规则三段顺序、缺失/不可读降级、段落标签 | 真 seam + stub provider，读 system prompt | `app/tests/test_local_workspace.py`（真 seam + provider 请求观测）、`app/tests/test_skill_assembly.py`（system prompt 里出现技能名与描述） |
| 技能四层优先级、同名只一条、坏条目跳过 | 全局临时目录 + 真装配函数 + 真 seam；工具清单与系统提示 | `app/tests/test_skill_assembly.py`（启用/停用、被篡改字节不装配、Docker 路径翻译） |
| MCP 三层优先级、`mcp.json` 解析、`env_names`、确认前不连接 | 最小本地 stdio 服务 + 传输替身；工具清单与 `runtime_status` | `app/tests/test_mcp_assembly.py`（真实 stdio 子进程、远端确认前不建连、失败不阻塞其他 server） |
| 全局记忆只读、两处读、写入落项目侧 | 真实临时目录 + 记忆中间件；文件磁盘事实 | `app/tests/test_runtime_memory.py`（跨会话写回与召回、DM 只有记忆目录权限） |

| 数据目录四种解析顺序、绝不自动搬移 | 临时 HOME + 进程启动路径 | `app/tests/test_migrate_cli.py`（真实子进程 + 临时数据目录）、`app/tests/test_schema_version_gate.py`（启动闸门读数） |
| 全局远端 MCP 确认 | 既有确认行 + 装配层「未确认不连接」 | `app/tests/test_mcp_assembly.py`（确认前不建连） |
| 全局层不被自动创建 | 运行前后全局临时根的目录清单 | 同上组「装配层行为取证」体例 |

### T5 · 被否的 seam 与理由

| 被否方案 | 理由 |
| --- | --- |
| 新建独立「GlobalLayer」服务模块，并作为第三个注入点 | seam 数量翻倍而深度为零；既有装配函数已经隐藏了层级、校验与降级复杂度，再包一层只是多一个转发者。 |
| 只在 HTTP 面测试 | 规则、技能与 MCP 的真实装配不出现在 HTTP 读数里；只测 HTTP 会漏掉本能力最核心的可观察行为。 |
| 把 DB 读路径（技能/ MCP 的库查询）当 seam | 全局层是纯文件、没有库行；合并点不在库读取，而在轮次装配层。 |
| 为规则、技能、记忆各开一个 seam | 它们是同一轮装配的三份输入，同一个 seam 的接口就是测试面；按对象拆分会把一次装配拆成三次注入。 |

### T6 · 测试卫生

- 全局根与 HOME 一律指向临时目录；测试结束删除临时目录。
- 不要求 Docker daemon 才能断言挂载：配置对象层判据优先；daemon 相关端到端整组可跳过。
- 不联网；远端 MCP 与 provider 都用进程内替身。
- 不在测试里等待真实时间；本能力没有时间驱动行为。
- 断言「不自动创建」时比较运行前后的目录清单，而不是只断言某个路径不存在。

## Out of Scope

以下条目**明确不做**，理由随条给；前九条来自设计笔记 §8。

1. **全局技能 / MCP 的 UI 安装、编辑、删除端点。** 理由：全局层是纯文件系统、由人维护；新增写端点会把「人的维护面」变成应用的数据面。
2. **应用写入全局记忆；全局记忆的版本管理、冲突合并、同步。** 理由：全局记忆只读是安全与并发模型的基础；可写会制造跨项目的隐式共享写竞争。
3. **启动时自动迁移 `~/Alibot`；自动创建全局目录。** 理由：不可逆地移动用户数据违背本仓「迁移显式、备份先行」的纪律；自动创建会把只读素材层变成应用生成物。
4. **跨项目共享 `sessions/`。** 理由：会话状态是运行状态，不是记忆或规则；共享会让上下文与工具缓存串味。
5. **全局层的多用户 / 多租户隔离。** 理由：本仓是本机单用户工作台；引入租户隔离会改变身份与权限模型，超出本能力。
6. **新增 `scope_kind` 或任何 `SCHEMA_VERSION` 变更。** 理由：合成确认键可写进既有的自由文本列；新增 `scope_kind` 会触发带 CHECK 的表重建，代价高且无必要。
7. **修改 ADR-0021、ADR-0014 正文。** 理由：ADR-0031 已逐句声明补充、修订与保留；改旧 ADR 会让「当时为什么这么定」消失。
8. **全局规则的热重载缓存策略。** 理由：每轮装配时读取即可；缓存属实施细节，本规格只要求可观察行为。
9. **远端全局 MCP 的凭证存储。** 理由：本仓库里不存密钥；凭证仍只从进程环境读。
10. **本票不写任何源码、测试、迁移脚本或 CI 配置。** 理由：本票是规格票，门禁 G-spec；验收判据是零源码改动与 `SCHEMA_VERSION` 未 bump。
11. **本票不拆实施票、不创建新的 tracker 票。** 理由：拆票与依赖编排属 `to-tickets`；本规格只给 seam 与测试口径，设计笔记 §7 的 A–G 切分建议仍是下一阶段的输入。
12. **本票不重写 ADR-0031、设计笔记或 `CONTEXT.md` 的已定决策。** 理由：规格只把它们合成为可实施契约；术语与决策正本不动。
13. **不新增权限档、不引入 `BYPASS`、不新增可写根。** 理由：全局层只增加只读输入；三档语义是承诺。
14. **不把全局层放进数据目录备份，也不把数据目录挂进 Docker。** 理由：备份单位与容器数据面都是既有承诺；全局层需单独备份，数据目录不进容器。
15. **不要求新增迁移命令。** 理由：搬迁可以是文档化的手工步骤或显式 CLI 入口（实施票自选），但**不得**在启动时自动搬。

### N4 · 隐藏目录的显式取舍
