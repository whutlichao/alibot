## Problem Statement

今天，**「到点」这件事在后端根本不存在**。

`reminder` 表只有 `id / text / time / channel_id / created_at` 五列（`app/alibot/db.py:382-388`），**没有任何「已到点」的落点**；`time` 的形状由正则 `^([01]\d|2[0-3]):[0-5]\d$` 在写路径校验（`app/alibot/db.py:183`、`:1359-1360`），**只有 24 小时钟点、没有日期**。全仓**没有任何定时或轮询设施**（`POLL_INTERVAL` / `Timer(` / `time.sleep` / `asyncio.create_task` 零命中），唯一的时间来源是 `utc_now()` 生成的 UTC 串（`app/alibot/db.py:756-758`），**没有任何时区处理代码**（`ZoneInfo` / `astimezone` / `localtime` 零命中）。

于是用户设的提醒**永远不会响**：

1. **它只存在，不发生。** `GET /api/reminders` 能读出「09:00 · 检查令牌替换进度」，但没有任何路径会把「09:00 到了」变成一条后端事实。用户必须自己盯着时钟回去看那个弹窗。
2. **「到点与否」取决于谁打开浏览器。** 唯一可能的替代做法（前端算 `due` 标记、或打开弹窗时按当前时刻比对 `HH:MM`）会让**浏览器的时钟**成为「到点发生过」这件事的事实来源——两个浏览器各显示各的，而 `CONTEXT.md` **工作台**明写「业务状态的唯一正本是后端；前端不持正本」。
3. **`HH:MM` 表达不了用户最自然的那句话。** 「明天早上 9 点提醒我」说不出来：钟点没有日期，跨天后 `09:00` 到底是今天还是明天，读路径无法回答。
4. **进程不常驻是常态，而「错过」完全无从处置。** 本仓靠 `python -m alibot` 才跑，到点时进程没在运行是**常态**不是异常。今天没有任何机制能在重启后回答「这段时间里有没有一条提醒该响但没响」。
5. **人类面看不出一条提醒响过没有。** `_reminder_payload`（`app/alibot/db.py:1330-1339`）只回 `id / text / time / channel_id / channel_name / created_at`，列表行（`studio/app.js:860-881`）只显示时间、文本、归属频道与删除按钮；rail 指示点的判据是 `state.reminders.length === 0`（`studio/app.js:792`）——提醒响过之后圆点永远亮着，它变成一个「历史计数器」而不是「还有没有事等着」。

后果对用户是具体的：**提醒这个能力在语义上是不完整的**——它承诺「到点提醒我」，而到点什么都不会发生。

## Solution

给提醒补上**到点触发**：到点是**后端产生的事实**，它落一条**系统事件消息**进归属频道的消息流；**不唤醒任何人、不消耗回应预算、不计未读、不进搜索命中**。

- **有归属 ⇒ 落一条 `system` 消息。** 一条到期且未投递过的提醒，若 `channel_id` 非空，后端为它落**恰好一条** `kind='system'` 消息进该频道的消息流，作者恒为 **owner**（提醒是本机用户给自己设的，不是任何对话参与者说出的话）。
- **无归属 ⇒ 只有状态变化。** `channel_id IS NULL` 的提醒到点**只写已投递标记、不落任何消息**。消息必须有一个 **target**，而无归属提醒没有 target；这条分叉是能力的一部分，**不是遗漏**（见 C2，独立成节）。
- **时间语义升级为一次性「日期 + 钟点」。** 到期时刻从 `HH:MM` 扩为 `YYYY-MM-DD HH:MM`，按**本机本地时间**解释；到点后这条提醒就用完了，**不做重复**。
- **一个可注入的到期投递器决定「什么时候算到点」。** 它输入当前时刻、输出这一批的投递后果；生产实现是进程内后台线程按固定间隔（**30 秒**）轮询 + **启动先扫一次**；测试注入时刻，**任何测试不真等 30 秒**。
- **错过在 24 小时窗口内补投一次。** 启动先扫时，已过点且未投递的提醒——距到期 ≤ 24 小时 ⇒ 补投一条消息（正文用**补投**措辞）并记已投递；> 24 小时 ⇒ **只记已投递、不落消息**，人类面标成**已错过**。
- **人类面能看出状态。** 新增控件拆成日期（`type="date"`，默认今天）+ 既有钟点两个原生输入；列表行加状态后缀（待响 / 已提醒 / 已错过）；rail 指示点只在**还有未到点的提醒**时亮。
- **文案严格两层，不许有第三层。** 落库的消息正文只进后端词条表（`app/alibot/i18n.py` 两份）；界面静态文案只进前端词条表（`app/alibot/studio/i18n.js` 两份）；**同一条文案不许两边登记**。

## 行为契约（C1–C19）

每条含三半：**契约陈述**、**可观察验收判据**、**来源**（哪条 S / 哪个 D）。判据一律落在**外部可观察面**：HTTP 读数、库的终态、stdout 报告、进程退出码、`git diff`。**不断言私有函数、SQL 文本、注册表内部表示。**

> 「已投递标记」在下文统一指新增的可空列 **`fired_at`**（C5）。「本机本地时间」指进程所在机器的本地时区（C7）。

### 一、到点的产物与它的分叉

#### C1 · 到点的产物是一条**系统事件消息**（来源：S1 / D1）

**契约陈述**：一条**到期**且**未投递过**（`fired_at IS NULL`）的提醒，若 `channel_id` 非空 ⇒ 后端为该提醒落**恰好一条** `kind='system'` 消息进该频道（channel 型 target）的**消息流**。作者恒为 **owner**。这条消息**不唤醒任何人、不消耗回应预算**。人类面**没有**创建 `system` 消息的端点（`app/alibot/api.py:34-35`），这条消息只能由后端投递器写。

**可观察验收判据**：

1. 造一条 `channel_id` 非空、到期时刻已到的提醒并触发投递 ⇒ 该频道 `GET /api/channels/{id}/messages` 末尾新增**恰好一条** `kind == "system"` 的消息，其 `author.id == "owner"`。
2. 同一 action 前后，`GET /api/channels/{id}/budget` 的 `used` **逐字不变**，`epoch_seq` **逐字不变**。
3. 同一 action 前后，`GET /api/channels/{id}/round-outcomes` **无新增行**。
4. 触发两次投递（见 C5）⇒ 该频道消息条数**只 +1**。

#### C2 · 无归属提醒的**显式分叉**（来源：S2 / D1 的 Q5 边界；**硬点 H1**）

> **这一节不是脚注。** 设计票第 2 轮 ask 明确要求这条写成规格正文的一节（H1）。

**契约陈述**：`channel_id IS NULL` 的提醒到点 ⇒ **只写已投递标记（`fired_at`），不落任何消息**。**任何 target 的消息条数都不变**。分叉的判据是「有没有归属」，而不是「有没有 target」或「落在哪个 target 上」——本能力**不新增 target**（ADR-0012 的「不新增 target」仍有效，ADR-0017 首段载明）。

这条分叉**必须双分支可观察**，因此读路径必须同时给出「已到点」的证据（C20）。否则无归属提醒的到点变成一个不可观察的状态变化。

**可观察验收判据**：

1. 造一条 `channel_id IS NULL`、到期时刻已到的提醒并触发投递 ⇒ `GET /api/reminders` 里该条的 `fired_at` **非 `null`**，`state` 不再是 `pending`。
2. 同一 action 前后，`GET /api/channels` 与 `GET /api/dms` 与 `GET /api/tasks` 三个列表的**元素集合逐字不变**（证明没有凭空造 target）。
3. 同一 action 前后，`GET /api/workspace` 快照的 `unread_total` 与每个频道的 `unread_count`、`last_seq` **逐字不变**。
4. 对无归属提醒触发两次投放 ⇒ 两次 `after` 读数相等（第二次**改动 0 行**，与 C5 同一判据）。

#### C3 · `system` 消息的既有口径**一个都不变**（来源：S3 / D1）

**契约陈述**：到点落的那条消息继承了 `system` 消息的全部既有口径，**本能力不给 `system` 造任何例外**：

| 口径 | 既有落点（实测） | 本能力的处置 |
| --- | --- | --- |
| 不计**未读** | `app/alibot/db.py:496-502` 的 `UNREAD_WHERE_SQL`（`m.kind IN ('human','agent')`，`:500`） | **不改**，`system` 天然落在集合外 |
| 不进**搜索命中** | `app/alibot/db.py:599`（全工作区）与 `:610`（单 target）的 `AND m.kind != 'system'` | **不改** |
| 不**唤醒** | `app/alibot/orchestration.py:183` 的 `notify`，对 `system` 在 `:205` 直接早退返回 0 | **不改** |
| 不消耗**回应预算** | 同上早退 ⇒ 不触及 `target_budget` | **不改** |

**可观察验收判据**：

1. 触发一次有归属投递 ⇒ `GET /api/workspace` 的 `unread_total` **逐字不变**；
   该频道 `GET /api/channels` 行的 `unread_count` **逐字不变**。
2. 触发一次有归属投递 ⇒ 用该 `system` 消息正文里**出现过的词**（例如提醒文本）调 `GET /api/search?q=…`，消息命中里**不含**这条 `system` 消息。
3. 触发一次有归属投递 ⇒ 该频道 `round-outcomes` **无新增行**、`budget.used` 不变（与 C1 判据同源，此处作为 C3 的独立读数点）。

### 二、时间语义与时区

#### C4 · 到期时刻是**一次性**的「日期 + 钟点」（来源：S4 / D2）

**契约陈述**：`reminder.time` 的形状是 **`YYYY-MM-DD HH:MM`**（24 小时制，零填充），语义是**一次性**的到期时刻；**没有重复字段**（不接受「每天 / 每周」）。写路径拒绝任何不合该形状的取值。到点后这条提醒即**用完**（不会再被任何路径投递，见 C5）。**重复**这件事在本仓由**任务**承载，提醒不造第二个重复语义。

**可观察验收判据**：

1. `POST /api/reminders` 带 `time = "2026-10-18 09:00"` ⇒ `201`，响应里该条的 `time` **逐字等于**传入值。
2. `POST /api/reminders` 带 `time = "09:00"`（旧形状）⇒ `400`，`error.code == "validation_failed"`，`error.fields` 的键含 `"time"`，且该字段的文案是可读自然语言（不是键名）。
3. `POST /api/reminders` 带 `{"repeat": "daily"}` 或 `{"date": "2026-10-18"}` 之类本票不做的键 ⇒ `400`、`validation_failed`，**不静默忽略**（沿用既有 `extra="forbid"` 口径）。
4. 同一条提醒**不可能**产生第二条到点消息（C5 判据 4 覆盖）。

#### C7 · 两种时间口径的逐字差异（来源：S7 / D5；**硬点 H2**）

> 设计票第 1 轮 ask 明确要求这句**逐字**进规格正文，不许只写在决策账里。

**契约陈述（逐字）**：

> 「到期判定用**本机本地时间**；`created_at` 仍是 **UTC 审计时间戳**；两者在库里**不做换算比较**，只在需要比较时（S9）才换算到同一时区」

展开成可判定的规矩：

1. **到期判定**：`reminder.time` 里的 `YYYY-MM-DD HH:MM` 按**本机本地时区**解释成一个瞬时。
2. **审计戳**：`created_at`（`app/alibot/db.py:756-758` 的 `utc_now()`）、以及 `fired_at`（C5），都是 **UTC**、毫秒精度、`Z` 后缀。
3. **库内不换算比较**：不给 `reminder` 表加时区列，不在 SQL 里对本地时刻与 UTC 时刻做大小比较。
4. **唯一的换算口径**：全规格只有**一处**换算方法——「本地到期时刻 → UTC 瞬时（按本机时区）」。它的消费点**只有三处**，且三处**必须共用同一个方法**，不许各写一份：C6 的 24 小时窗口判定、C9 的 30 秒精度判据、C21 的准点/补投文案分档。

**必须一起接受的代价**（ADR-0017 §二已记账）：同一张表里两种时间口径；**跨时区搬数据目录后到期语义会漂**。这条不写清就会变成下一个「为什么 09:00 不响」的事故。

**可观察验收判据**：

1. 规格正文里上述逐字句**存在**（可 `grep`）。
2. 固定注入时刻 + 固定本机时区的行为测试：一条到期时刻写成**本地** `2026-10-18 09:00` 的提醒，在注入时刻为本地 `2026-10-18 09:00:05` 时被判定为到点；同一库在注入时刻为本地 `2026-10-18 08:59:55` 时**不**被判定为到点。判据只读「有没有落消息 / `fired_at` 是否变化」，不需要读库内时间格式。
3. 规格与实现里**不存在**「把本地时刻当 UTC 直接比较」的落点（实施票自查项，见 C9 判据 4）。

### 三、已投递标记、错过与文案分档

#### C5 · `fired_at` 是唯一的「已投递」标记，且与落消息**同一事务**（来源：S5 / D4 + 第三轮 ask 的硬要求）

**契约陈述**：新增可空列 **`fired_at TEXT`**（`NULL` = 还没到点；非空 = 已投递）。**任何已写 `fired_at` 的行都不再被任何路径投递**——这一个标记同时承担「至多投递一次」（准点）与「至多补投一次」（C6）。

**写入时机（这是「至多一次」的唯一真实风险点，必须可判定）**：落消息与写 `fired_at` 在**同一个事务**里收口。依据是本仓既有写路径的原子性口径——`append_message`（`app/alibot/db.py:2181`）的行为就是「`_begin()` → 全部写 → `_commit()`，任一步失败 `_rollback()` 后重抛」（事务边界在 `app/alibot/db.py:2238-2277`），因此与附件绑定、预算重置一起落库的写法已有先例。**投递器必须在同一事务里完成「落消息 + 写 `fired_at`」**，于是：

- 落消息成功而写 `fired_at` 失败 ⇒ **不可能发生**（同一事务，整体回滚）；
- 事务回滚 ⇒ 消息没落、`fired_at` 没写，下一轮轮询会**重试**（不是重复投递，是**从未成功**）；
- 因此「落消息成功但标记没写」这条会导致重复投递的中间态**在构造上不可达**，不需要补偿路径。

**本能力的 `state` 不是第三态**：`state`（C20）是从 `fired_at` 与到期时刻之差**推导**出的只读派生值，**不落库、不进 `reminder` 表列、不 bump 额外版本**，因此不违反 D4 否掉的「三态 `pending`/`fired`/`missed`」。

**可观察验收判据**：

1. 连续触发投递器两次 ⇒ 第二次的投递后果里**没有任何一条**成功投递；该频道消息条数**第二次不变**（可断言的「至多一次」）。
2. 造一条到期且未投递的提醒，让「落消息」那一步抛错（测试替身注入）⇒ 该条 `fired_at` **仍是 `null`**，该频道消息条数**不变**，下一次触发能正常投递（证明是「从未成功」而非「已投过」）。
3. `GET /api/reminders` 每条 payload **恒含** `fired_at` 键（未到点时为 `null`）；**无归属**提醒的到点因此仍可观察（C2 判据 1 依赖这一条）。
4. `fired_at` 非空时，它的形状是可解析的 ISO-8601 **UTC** 串（带 `Z` 后缀），与 `created_at` **同一族口径**（C7 契约陈述第 2 条）。

#### C6 · 错过补投：**24 小时窗口内至多一次**（来源：S6 / D3）

**契约陈述**：进程启动时**先扫一次**（与常规轮询同一段代码，不新增第二条时间路径）。对每条 `fired_at IS NULL` 且到期时刻已过的提醒：

| 距到期的间隔（按 C7 的唯一换算口径算出） | 处置 |
| --- | --- |
| `≤ 24 小时` | **补投**一条 `system` 消息（有归属时；正文用**补投**措辞，C21），随后写 `fired_at` |
| `> 24 小时` | **只写 `fired_at`、不落消息**，人类面呈现为**已错过** |

两类都在人类面**可区分**（C16 / C20）。

**可观察验收判据**：

1. 造三条已过点、`fired_at IS NULL`、且有归属的提醒：距到期分别 **1 小时 / 23 小时 / 25 小时**。触发启动扫 ⇒
   - 前两条：各自落下**恰好一条** `system` 消息，正文是**补投**措辞（C21 判据 2）；
   - 第三条：**无消息**，但 `fired_at` 非 `null`；
   - 三条的 `fired_at` **全部非 `null`**。
2. 再触发一次启动扫 ⇒ 三条都不再产生任何消息（`fired_at` 已写，C5 判据 1 同源）。
3. 距到期**恰好 24 小时**的边界：按 `≤ 24 小时` 归入「补投」一侧（边界值有唯一归属，不留含混）。
4. 无归属的过期提醒 ⇒ 两条路径（窗口内 / 窗口外）都**只写 `fired_at`**，无消息（与 C2 同一分叉）。

#### C21 · 准点与补投的文案分档判据（来源：S6 + S18 + S9 的推导；本票第三轮 ask 代答·推导）

**契约陈述**：落库的两条 `system` 消息正文用**两个不同的后端词条**（`system.reminder.fired` / `system.reminder.fired_late`，C18）。它们的分档判据**不是「走的是哪条代码路径」**（那对外部不可观察），而是**投递时刻与到期时刻之差**：

| \|投递时刻 − 到期时刻\|（按 C7 的唯一换算口径） | 词条 |
| --- | --- |
| `≤ POLL_INTERVAL_SECONDS`（= **30** 秒，C9） | `system.reminder.fired` |
| `> POLL_INTERVAL_SECONDS` | `system.reminder.fired_late` |

**两个契约共用同一个常量，不各造一个界**：C9 的精度上界与 C21 的文案分档都是 `POLL_INTERVAL_SECONDS`，因此不会出现「30 秒界在精度判据里、另一个界在文案里」的两套阈值。

**可观察验收判据**：

1. 注入时刻 = 到期时刻 + 5 秒且提醒有归属 ⇒ 落下的消息正文取 `system.reminder.fired` 的渲染值。
2. 注入时刻 = 到期时刻 + 5 分钟（仍 < 24 小时）⇒ 正文取 `system.reminder.fired_late` 的渲染值。
3. 「30 秒」这个阈值在实现里**只出现一次**（同一个常量被两处消费；实施票自查项，测试只断言两个分档的行为，不读常量）。

### 四、调度 seam 与精度

#### C8 · 核心 seam：**可注入的到期投递器**（来源：S8 / D8；见 §Seams）

**契约陈述**：判定「到点」的是一个**窄接口**的模块——**输入当前时刻**，**输出这一批的投递后果**（准点 / 补投 / 窗口外 / 已投过 / 无归属）。它**不暴露**轮询间隔、锁、线程生命周期：

- **生产实现**：进程内后台线程按固定间隔轮询 + **启动先扫一次**；
- **测试实现**：注入手动触发，直接喂时刻——**行为测试一行都不真等时间**。

装配点与既有 `scheduler` 同处（`app/alibot/api.py:303` 的 `create_app`，注入点在 `:321-328`）。

**可观察验收判据**：

1. 用测试替身喂时刻，能在**不等时间**的前提下驱动**全部五个分支**：准点 / 补投 / 窗口外 / 已投过 / 无归属。每个分支的后果只经 HTTP 读数面断言。
2. 生产装配下（真实后台线程）同样可观察：以 30 秒为界的精度判据（C9 判据 1–2）在真实装配下成立。
3. 进程启动后的**第一次**投递由启动先扫完成（不依赖第一次轮询到点）：一条启动前就已过点且在窗口内的提醒，在 `GET /api/reminders` 第一次可读时其 `fired_at` 已非 `null`——不需要等 30 秒。

#### C9 · 精度判据 = **30 秒常量 + 注入时刻的行为判据**（来源：S9 / D8 的 Q12 代答；**硬点 H4**）

**契约陈述**：

1. **`POLL_INTERVAL_SECONDS = 30`** 是一个**模块级常量**，由**一条单元断言**固定（`POLL_INTERVAL_SECONDS == 30`）。
2. **准点投递**的精度上界 = `|system 消息的 created_at − 提醒的到期时刻| ≤ POLL_INTERVAL_SECONDS`；比较时必须把 UTC 的 `created_at` 与本地到期时刻**按 C7 的唯一换算口径**换算到同一时区。
3. **补投除外**：补投的差值只受 24 小时窗口约束（C6），不适用 30 秒上界。
4. **轮询间隔不作为行为测试的对象**：行为测试一律走**注入时刻**。**任何测试不许真等 30 秒**（也不许 `sleep` 出这个窗口）。

**可观察验收判据**：

1. 存在一条单元断言：`POLL_INTERVAL_SECONDS == 30`。
2. 一条**基于注入时刻**的行为断言验「投递后果正确」，并**声明式地**给出 30 秒上界（即：在 `到期时刻 + 30 秒` 这个注入时刻上，投递后果已包含该条提醒）。
3. 全部相关测试的实测墙钟耗时**显著小于 30 秒**（例如整套提醒相关测试 < 5 秒），据此可判定「没有任何测试真的等 30 秒」。
4. 实现里**没有**「把本地到期时刻当 UTC 直接与 `created_at` 比较」的落点（C7 判据 3 的另一面；实施票自查项）。

#### C10 · 线程生命周期接进既有 shutdown 顺序（来源：S10 / D8）

**契约陈述**：新的轮询线程必须在**「停 scheduler」之前**收口。既有顺序是「停事件流 → 停 scheduler → 关库」（`app/alibot/api.py:331-342`：`shutting_down.set()` 在 `:338`、`orchestrator._scheduler.shutdown()` 在 `:339-341`、`database.close()` 在 `:342`）。新线程必须插在这个顺序里、在 `database.close()` **之前**收口——否则关库之后线程还能拿到库句柄。

**可观察验收判据**：

1. 正常关停后进程退出码正常，**不出现**「库已关 / 在已关闭的连接上操作」这类异常（stderr 无相应堆栈）。
2. 反复启停（例如 3 次）后**不留孤儿线程**：进程能干净退出，不挂住。
3. shutdown 顺序里有该线程的一位（实施票自查项；外部可观察的等价判据是判据 1 与 2）。

### 五、读路径的可观察性

#### C20 · 读路径恒给 `fired_at` 与派生 `state`（来源：S2 + S5 + S16 + 本票第二轮 ask 代答·推导(Q4) + 第三轮 ask 代答·推导(Q8)）

**契约陈述**：`GET /api/reminders` 的**每条** payload 恒含两个键：

| 键 | 形状 | 语义 |
| --- | --- | --- |
| `fired_at` | `null` 或 ISO-8601 **UTC** 串（`Z` 后缀） | `null` = 未到点；非空 = 已投递（C5） |
| `state` | `"pending"` / `"fired"` / `"missed"` 三取一 | **只读派生值**，由 `fired_at` 与到期时刻之差**推导** |

`state` 的推导规则（唯一）：

| 条件 | `state` |
| --- | --- |
| `fired_at IS NULL` 且到期时刻**未到** | `pending` |
| `fired_at IS NULL` 且到期时刻**已过**（等待下一轮投递） | `pending`（仍是待处理，尚未投递） |
| `fired_at` 非空，且 `\|fired_at − 到期时刻\| ≤ 24 小时` | `fired` |
| `fired_at` 非空，且 `fired_at − 到期时刻 > 24 小时` | `missed` |

- **`state` 不是第三态正本**：它不落库、不进 `reminder` 表列、不写任何迁移步骤。D4 否掉的是「第三个**状态列**」（一个不可达的 `missed` 状态值），派生字段不是列。
- **为什么在后端推导**：本仓既有纪律是「判定在后端、前端只呈现」（`CONTEXT.md` **搜索命中** / **高亮区间** 两处先例）；且若前端推导，24 小时界会在两份代码里各出现一次，前端还要自己做时区换算——踩**工作台**「前端不持正本」的边界。

**可观察验收判据**：

1. `GET /api/reminders` 的**每一条**都有 `fired_at` 与 `state` 两个键（键存在性，不论取值）。
2. 造四条提醒覆盖四种情形（未到点 / 已过点未投递 / 窗口内已投递 / 窗口外已投递）⇒ `state` 分别为 `pending` / `pending` / `fired` / `missed`。
3. 后端**没有**为 `state` 新增任何库列：`reminder` 表的列清单在迁移后只多 `fired_at` 一列（C11 判据 4 覆盖）。
4. `state` 在两次连续读之间**不会被写入**（它是推导值）：对同一个库连读两次 payload 逐字相同。

### 六、机器面：schema 号与迁移

#### C11 · schema 号 = **13**，并登记 `MigrationStep(12, 13)`（来源：S11 / D7）

**契约陈述**：`SCHEMA_VERSION` 从 **12** 改为 **13**（`app/alibot/db.py:59`），并**登记一步 `MigrationStep(12, 13, …)`** 到 `app/alibot/migrate.py:651` 的 `STEPS` 末尾。理由：链连续性不变量（`migrate.py:664-682` 的 `_assert_chain_is_continuous`）要求链**连续覆盖** `MIN_SUPPORTED_SOURCE_VERSION .. SCHEMA_VERSION`（`db.py:65` 的 `3`）；bump 到 13 而**不**登记这一步会让该守卫在**导入期**直接抛错。号段判据是「**必须高于当前 main**」（`db.py:44-58` 的记账正本），13 是满足该判据的最小号。

**这一步的列改动**：`reminder.time` 的形状改为 `YYYY-MM-DD HH:MM`（C4）；新增 `reminder.fired_at TEXT`（可空，C5）；存量行按 C12 改写。

**可观察验收判据**：

1. `python -m alibot --migrate --data-dir <v12 库>` ⇒ 退出码 `0`，`schema_version` = 13。
2. 链连续性守卫测试**绿**（它经 CLI 接缝解析迁移报告的步骤表，断言连续且终点覆盖 `SCHEMA_VERSION`）。
3. 人为把 `12 → 13` 那一步删掉（或把 `SCHEMA_VERSION` bump 而链止于 12）⇒ 该守卫测试**红**。
4. 迁移后 `reminder` 表的列清单 = 迁移前五列 + `fired_at`，**没有**第三个新列（尤其没有 `state` / `due_date` / 时区列）。

#### C12 · 存量 `HH:MM` 行解释成**「迁移执行当日」**的该钟点（来源：S12 / D7）

**契约陈述**：迁移把存量 `time = 'HH:MM'` 的行统一改写为 `<迁移执行当日的日期> HH:MM`（按 C7 的本地时间口径），`fired_at` 补 `NULL`。**为什么是「迁移执行当日」而不是「下一个该钟点」**：后者的结果**依赖迁移执行的时刻**（同一份备份 08:00 迁与 16:00 迁得到两个不同的到期日），不可复现、难以写测试，且报告给不出准确的改写读数（改写的是**值**而不只是列）。「迁移执行当日」是**唯一不依赖运行时状态**的解释口径。

**可观察验收判据**：

1. 造一条 `time = '09:00'` 的存量行，在**已知日期**（测试注入的当天）执行迁移 ⇒ 该行 `time` = `<该日期> 09:00`，`fired_at` 为 `null`。
2. 造 N 条不同钟点的存量行 ⇒ 全部为同一日期 + 各自原钟点，**没有任何一行的日期不同**（证明口径不依赖执行时刻）。
3. 已是新形状（`YYYY-MM-DD HH:MM`）的行**不被改写**（幂等）。

#### C13 · 时间语义的**一次性收窄**，必须在规格正文与迁移报告里读到（来源：S13 / D7；**硬点 H3**）

**契约陈述**：这是一次**时间语义的一次性收窄**——用户原来的「**每天** 9 点」在迁移后变成「**迁移那天** 9 点」（一次性）。它不丢数据行，但**改变了行的含义**。这句话必须同时出现在两处：

1. **本规格正文**（即本节）；
2. **迁移报告**里——报告必须让读者读到「存量提醒的到期语义已从『每天该钟点』收窄为『迁移执行当日该钟点』」。

**可观察验收判据**：

1. 本规格正文含上述收窄陈述（可 `grep`「一次性收窄」「每天 9 点」「迁移那天」）。
2. 迁移成功后 stdout 报告里能读到该收窄的说明（不止是步数统计）。
3. 报告里 `12 → 13` 这一步的 `改动 N 行` 中的 N 可核对（C14）。

#### C14 · 迁移报告给出**被改写行数**（来源：S14 / D7 + 第二轮 ask 代答·细节(Q6)）

**契约陈述**：复用既有报告的 `changed_rows` 形状——**不新增「改写行数」这个新报告字段**。判据是：迁移报告 stdout 里能读到 `12 → 13` 这一行，其「改动 **N** 行」的 N = 实际被改写的 `reminder` 行数。依据：`app/alibot/migrate.py:848-863` 的 `_render_step_lines` 已经是「真跑与预演共用同一份」的步骤表渲染，每步一个 `changed_rows`；`_step_7_to_8`（`:574-577`）这类纯建表步返回 0 也印证这个形状可用。

**可观察验收判据**：

1. 造 **N = 3** 条存量 `HH:MM` 行 ⇒ 迁移报告 stdout 里 `12 → 13` 那行的「改动 3 行」逐字可读。
2. 造 **N = 0** 条（空提醒表）⇒ 该行显示「改动 0 行」。
3. 报告里**没有**新增的「改写行数」独立字段（`git diff` 里不出现新的报告字段名）。

### 七、人类面

#### C15 · 新增控件是**两个原生输入**（来源：S15 / D9）

**契约陈述**：提醒弹窗的新增控件 = `<input type="date">`（默认**今天**）+ 既有 `<input type="time">`。提交时前端把两者拼成一个到期时刻（`YYYY-MM-DD HH:MM`）交给后端。**这是对原型的显式偏离**（原型 `alibot-design-system/alibot-app.html:1579` 与现产物 `app/alibot/studio/index.html:679` 都只有 `type="time"`），必须记账。

**可观察验收判据**：

1. 弹窗里同时存在**日期**与**钟点**两个原生输入（DOM 上存在两个 `input`，类型分别为 `date` 与 `time`）。
2. 日期输入的默认值是**当天**（打开弹窗即可见，不需手填）。
3. 只改日期不改钟点也能提交成功（钟点保留默认 `09:00`，与现行为一致）。
4. 提交后的 payload 里 `time` 是 `YYYY-MM-DD HH:MM` 一个串（不是一个数组、不是两个键）。
5. 日期输入有可访问名（`aria-label` 取自前端词条 `reminder.dateLabel`，C18）。

#### C16 · 列表行**状态后缀**，且**不加新色位**（来源：S16 / D9）

**契约陈述**：提醒列表的每一行按 C20 的 `state` 显示状态后缀：

| `state` | 后缀语义 |
| --- | --- |
| `pending` | 显示**到期时刻**（不是「待响」这种标签） |
| `fired` | 「已提醒」（前端词条 `reminder.stateFired`） |
| `missed` | 「已错过」（前端词条 `reminder.stateMissed`） |

**只用既有档位 token**（`CONTEXT.md` **档位** / **角色族**：`--muted` / `--warn-*` 一族），**不加新色位**。已到点**不是错误**，不该用 `--error`；**视觉契约**的 token 名集合是承诺。

**可观察验收判据**：

1. 三种 `state` 的提醒在同一个列表里**可区分**（同一个列表渲染出三种不同的后缀文本）。
2. 前端呈现层的 `git diff` 里**没有**新增 token 名（实现只消费既有 token）。
3. 已到点的行**不显示**成错误态（不出现 `--error` 一族）。
4. 到点**不计未读**：`state` 变化不改变任何未读读数（与 C3 判据 1 同源）。

#### C17 · rail 指示点判据改为「**有未到点的提醒**」（来源：S17 / D9）

**契约陈述**：`renderReminderDot`（`app/alibot/studio/app.js:789-793`）的判据从 `state.reminders.length === 0` **改为**「没有未到点的提醒则隐藏」，即等价于 `state.reminders.some(r => !r.fired_at)` 的取反。指示点的语义是「有**一件事**还等着发生」——已响 / 已错过不等待任何事。

**可观察验收判据**：

1. 全部提醒都已到点（`fired_at` 全非空）⇒ 指示点**隐藏**。
2. 新增一条未到点的提醒 ⇒ 指示点**出现**。
3. 删除唯一那条未到点的提醒 ⇒ 指示点**隐藏**（既有行为保持）。
4. 判据不读 `length`：一条已到点 + 一条未到点时指示点仍是**出现**（`length` 判据在此情形下也对，故需另加一条：**只有**已到点的提醒时**隐藏**——这条在旧判据下是红的）。

### 八、文案与存量落点

#### C18 · 文案严格**两层**，不许有第三层；同一条文案不许两边登记（来源：S18 / D9；**硬点 H5**，ADR-0009）

**契约陈述**：

| 文案键 | 层 | 唯一载体 | 为什么只能在这一层 |
| --- | --- | --- | --- |
| `system.reminder.fired`（准点投递） | **后端第二层** | `app/alibot/i18n.py` 的 **两份**词条（`zh-CN` 与 `en`） | 它是**落库的 `system` 消息正文**，由投递器在 HTTP 请求之外写入、**没有请求头可读** ⇒ 只能按**库内语言偏好**渲染（ADR-0009 的决定性理由）；落库后是 append-only 取证面，**历史不回溯** |
| `system.reminder.fired_late`（补投） | **后端第二层** | 同上 | 同上；且准点与补投是**两条落库路径**（分档判据见 C21）⇒ **必须是两个键**，不能靠参数区分 |
| `reminder.dateLabel`（日期输入的可访问名） | **前端第一层** | `app/alibot/studio/i18n.js` 的 **两份**词条 | 界面静态文案，只出现在浏览器里、随语言偏好即时重渲染 |
| `reminder.stateFired` / `reminder.stateMissed`（行状态后缀） | **前端第一层** | 同上 | 它是**呈现**不是落库内容；同一个 `fired_at` 在不同语言下应显示不同说法 |

**四条硬纪律**：

1. **同一条文案不许两边登记**（那是第三层，明确违反 ADR-0009）。
2. 后端两份词条必须覆盖**同一个键集、无落单键**（既有 `app/tests/test_backend_copy.py` 的机器判据已覆盖）；前端两份同理（既有 `app/tests/i18n_ui.test.cjs` 的键集相等判据已覆盖）。
3. 已落库的 `system` 消息**保持写入时的语言**，不随偏好切换回溯（ADR-0001 / `CONTEXT.md` **语言偏好**）。
4. **既有词条的改写**（不是新增键）：`error.reminder_time_shape`（`i18n.py:60` zh / `:242` en）现在写「需要是 `HH:MM`（例如 09:00）」，时间形状变后必须改成新形状的说法——它是**既有键的取值改写**，不是新增键，仍在后端层。

**可观察验收判据**：

1. `system.reminder.fired` 与 `system.reminder.fired_late` **只**出现在 `app/alibot/i18n.py`，**不**出现在 `app/alibot/studio/i18n.js`。
2. `reminder.dateLabel` / `reminder.stateFired` / `reminder.stateMissed` **只**出现在 `app/alibot/studio/i18n.js`，**不**出现在 `app/alibot/i18n.py`。
3. 后端两份词条的键集相等且无落单键（既有测试绿）。
4. 前端两份词条的键集相等且无落单键（既有测试绿）。
5. 拿一个 `system.reminder.fired` 的落库正文，在**切换语言偏好后**重读 ⇒ 正文**逐字不变**（历史不回填）。
6. 用不可见请求头（`Accept-Language: en`）触发投递、而库内偏好是 `zh-CN` ⇒ 落库正文取 `zh-CN` 的取值。

#### C19 · 存量「到点不在授权范围内」断言必须改口径，但**本票不改**（来源：S19；**硬点 H6**）

**契约陈述**：现在有三处注释声称「到期触发的唤醒不在本票授权范围内」，**本能力成立后其中一半变成不实**：

| 落点（实测） | 现状 | 本能力成立后 |
| --- | --- | --- |
| `app/alibot/studio/index.html:651-659`（设计票记 `656-659`，实测整块在 651 起） | 注释写「副标题与空态正文**不**照抄原型那句『到点后 ⏰ 系统消息会直接出现在对应频道的消息流中』：『到期触发的唤醒』不在本票授权范围内……」 | **前半变真**（有归属的提醒到点确实落一条 `system` 消息进该频道消息流）；**后半仍不成立**（到点**不唤醒**任何人）。注释必须改口径。 |
| `app/alibot/studio/i18n.js:394-397`（zh 注释块） | 同上断言 | 同上 |
| `app/alibot/studio/i18n.js:858-861`（en 注释块） | 同上断言 | 同上 |

**建议的替换后注释全文**（逐字可抄；**本票不改它**，改它是实施票的活）：

```html
<!-- ─── 提醒（ADR-0012：库内对象，后端是唯一正本；到点产物见 ADR-0017） ─────────

     `type="time"`、没有日期与重复字段（ADR-0017 §六）。列表与空态都由 app.js 按后端读数
     渲染：正本不是这份标记。
```

对应的词条注释（同一次实施票处置，措辞可自定但口径必须一致）：`i18n.js` 的 zh/en 两个注释块里的「到期触发的唤醒不在本票授权范围内」必须改成「到点落 `system` 消息但**不唤醒**」。

**关于 `reminder.modalSub` / `reminder.emptyBody` 的取值**：本规格**不强制**改这两条取值（它们现在说的是「提醒保存在本机后端，刷新或重启后仍在」，仍然为真）。若实施票选择改，必须遵守 C2 的分叉——**不许**笼统声称「一定会落到消息流」，因为无归属提醒不落消息。

**可观察验收判据**：

1. 实施后，`app/alibot/studio/index.html` 的注释**不再**声称「到点不产生消息」或「到期触发不在授权范围内」。

3. 弹窗副标题与空态正文**不出现在点相关的不实承诺**：不声称「会唤醒 Agent」，不声称「一定落消息」。
4. **本票的判据**：本票的 `git diff` 里 `app/alibot/studio/**` 为空（把改注释留给实施票）。

## Seams

> 用 `codebase-design` 词汇。**seams 越少越高，理想一个。**

### 唯一的 core seam：**可注入的到期投递器**（C8）

```text
                 ┌──────────────────────────────────────────┐
   注入时刻 ───▶ │  到期投递器（Seam）                       │ ───▶ 投递后果（准点/补投/窗口外/已投过/无归属）
                 ├──────────────────────────────────────────┤
                 │  轮询节奏 · 事务边界 · fired_at 幂等写      │
                 │  时区换算（唯一一处）· 24h 窗口 · 文案分档   │
                 │  与 EventBus 的发布顺序                    │
                 └──────────────────────────────────────────┘
```

- **接口宽度**：1 个输入（当前时刻）+ 1 个输出（这一批的投递后果列表）。生产实现是进程内后台线程按固定间隔轮询 + 启动先扫一次；测试实现直接喂时刻。
- **隐藏的实现复杂度**：轮询节奏、事务边界（落消息 + 写 `fired_at` 同事务，C5）、`fired_at` 的幂等写、时区换算（C7 的唯一口径）、24 小时窗口判定（C6）、准点/补投文案分档（C21）、与 `EventBus` 的发布顺序。
- **深度判据**：能否用一个**几行的测试替身**（喂时刻 → 断言后果）覆盖**全部五个行为分支**——**能**，就是这个深度合适。这个替身的存在本身证明了 seam 的位置对（接口即测试面）。
- **落点**：装配点与既有 `scheduler` 同处——`app/alibot/api.py:303` 的 `create_app`，注入点在 `:321-328`，关停顺序在 `:331-342`（C10）。**不新开第二个装配点**：新模块以参数注入的方式挂进同一个组装函数，生产默认值是一个真实后台线程，测试默认值是手动触发。

### 为什么**不**立第二个 seam

按票面授权（第一轮 ask 的 Q1 = (a) 人定），**只声明这一个**。以下三处**都是这个 seam 输出的可观察后果**，不是独立 seam：

| 看似像 seam 的东西 | 为什么不是 seam |
| --- | --- |
| `GET /api/reminders` 的 payload（`fired_at` + `state`，C20） | 它是**既有** HTTP 读数面的一次字段扩展，不是新的注入点。它读的是 `reminder` 行上的 `fired_at`（由 core seam 写的），自己不产生任何行为分支。 |
| `system` 消息出现在归属频道的消息流里（C1） | 同上：它是 core seam 的**后果**，在既有的 `GET /api/channels/{id}/messages` 上读数。 |
| rail 指示点判据（C17） | 纯前端呈现，输入是 C20 的 payload。判据里的 `!r.fired_at` 消费的是 seam 的产物，不是新的行为来源。 |

**`codebase-design` 的判据**：**接口就是测试面**——callers 与 tests 跨同一道 seam。把「同一个行为的两个观察点」记成两个 seam，会让 seam 数量翻倍而深度为零；而**读数面不是 seam**，它是断言落点。**一个 adapter 只意味着假想的 seam**：本能力只有「生产轮询」与「测试注入」两个 adapter，跨在**同一个** seam 上——这也是它成为**真实** seam 的依据。

### 被否的 seam 落点与代价

| 被否的落点 | 代价 |
| --- | --- |
| **在 `GET /api/reminders` 里顺带算到点**（读路径即触发） | 把「到点」变成「有人读才有」；C6 的启动补投**永远不会在无人打开浏览器时发生**，C1 的「后端持有事实」也随之失效。 |
| **复用 `ThreadScheduler`**（`orchestration.py:76-88`） | 它的语义是「把一轮提交到线程池去跑」，**没有「何时提交」的能力**；复用它其实是复用线程池而不是调度，还会让人误以为唤醒编排已由到点驱动。 |
| **`Timer` 睡到最近到期时刻** | 系统休眠 / 时钟变化后不可靠；新增一条更早的提醒必须打断并重排定时器；它把「错过」处理成「睡过头」，与 C6 的补投语义打架。 |
| **轮询间隔做成可配置项** | 为单用户本机场景新增一档设置面（`CONTEXT.md` **工作区设置** 明写本轮只有三档），且配错了的表现是「静默不响」。 |
| **第二个 seam：可注入的「当前时刻提供者」+ 投递器分两个模块** | 时刻提供者是投递器的**内部**关注点（`codebase-design` 的 internal seam），不是接口的一部分；把它提到接口上会让 callers 多学一件事而深度不变。测试替身本来就直接喂时刻。 |

## User stories

### A. 到点会发生什么（C1 / C2 / C3）

1. 作为本机用户，我想让有归属的提醒到点时在归属频道的消息流里出现一条系统事件消息，这样我在聊天的地方就能看到它，不用另外回去翻弹窗。
2. 作为本机用户，我想让那条消息的作者显示为 owner（我自己），这样它不会被误读成某个 Agent 说的话。
3. 作为本机用户，我想让这条消息**不唤醒**任何 Agent，这样我设 5 条提醒不会把整个世代的回应预算吃掉。
4. 作为本机用户，我想让这条消息**不计未读**，这样未读徽标仍然只回答「有多少话要对我说」。
5. 作为本机用户，我想让这条消息**不出现在搜索结果里**，这样搜消息时不会被系统事件噪音干扰。
6. 作为本机用户，我想让不归属任何频道的提醒到点**只记已到点、不落消息**，这样它不会为了一个备忘列表去伪造一个频道或一个 target。
7. 作为本机用户，我想在提醒列表里**看得出**那条无归属提醒已经到点了，这样「不落消息」不等于「什么都没发生」。
8. 作为本机用户，我想让同一轮投递不会重复落消息，这样我不会在消息流里看到同一条提醒出现两次。

### B. 时间怎么表达（C4 / C7）

9. 作为本机用户，我想给提醒同时指定**日期**和**钟点**，这样「明天早上 9 点提醒我」这句话我能说出来。
10. 作为本机用户，我想让提醒**只响一次**（一次性），这样它不会在我没要求的时候每天重复。
11. 作为本机用户，我想让到期时刻按**我墙上的钟**（本机本地时间）解释，这样我写 09:00 就是我的 09:00，不用自己换算 UTC。
12. 作为本机用户，我想在提交旧形状（只有 `HH:MM`）时得到一条**可读的拒绝**并指出是哪个字段错了，这样我知道要补日期。
13. 作为本机用户，我想在提交本票不做的键（重复 / 单独的 date 字段）时被**整体拒绝**而不是静默忽略，这样我不会以为设置生效了。
14. 作为开发者，我想让「到期=本地 / 审计戳=UTC / 库内不换算比较」这条差异写死在规格里，这样我不会在某个下午把一个本地时刻当 UTC 比了一遍。

### C. 错过与补投（C5 / C6 / C21 / C20）

15. 作为本机用户，我想在**关机之后重启**时看到这段时间里错过的提醒被补投出来（只要还没超过 24 小时），这样「我关机了」不等于「提醒作废」。

### D1. 到点的产物与分叉（C1 / C2 / C3）

到点的产物是**一条 `system` 消息**，落进**归属频道**的消息流。作者恒为 **owner**（`db.py:36` 的 `OWNER_ID = "owner"`）。

**为什么不唤醒 Agent**：唤醒编排的唯一触发点是「消息**成功落库之后**」的 `notify(target_id, from_seq)`（`orchestration.py:183`），而 `notify` 的第一件事就是按 `from_seq` 读库里那条消息（`:190-191`），`append_message` 本身也要求一个真实 target（`db.py:2181`）。这条结构事实的推论是：**「唤醒一个 Agent」必然蕴含「先落一条消息」**——「落消息」是「唤醒」的**构造性前置**。选「落消息」保留了以后要不要唤醒的余地；而且 `system` 消息在 `notify` 里直接早退（`orchestration.py:205`），所以本能力**继承**了「不唤醒、不耗预算」，没有给 `system` 造任何例外。

**无归属的分叉（C2）是能力的一部分**：`reminder.channel_id` 今天可空（`db.py:386`），空 = 不归属任何频道（空工作台 / DM 视图下也设得成提醒），而消息必须有一个 target。本能力**不新增 target**（ADR-0012 的「不新增 target」仍有效），因此无归属提醒的到点只能落在**行上的标记**上。

### D2. 时间语义（C4 / C7）

`reminder.time` 的形状从 `HH:MM` 扩为 `YYYY-MM-DD HH:MM`，**一次性**。写路径的正则（`db.py:183` 的 `REMINDER_TIME_PATTERN`）随之扩；`error.reminder_time_shape`（`i18n.py:60` zh / `:242` en）的取值随之改写（C18 硬纪律 4）。

**两种时间口径**：`reminder.time` 按**本机本地时区**解释；`created_at`（`db.py:756-758` 的 `utc_now()`）与 `fired_at`（C5）都是 **UTC**。库内**不做换算比较**，只在三处判据里用**同一个方法**换算（C7 契约陈述第 4 条）。

**本仓没有时区处理代码**（`ZoneInfo` / `astimezone` / `localtime` 零命中），因此「本机时区」这件事是**本能力新引入的第一个时区依赖**——实施票必须让它只有**一个**落点（一个函数），不能散在三处判据里各写一遍。

### D3. 已投递标记与错过（C5 / C6 / C21）

`fired_at TEXT`（可空）。**唯一标记，承担两件事**：「至多投递一次」与「至多补投一次」。

**写入时机与原子性**：与落消息**同一事务**。依据是 `append_message` 的既有形状（`db.py:2181`；事务边界 `:2238-2277`：`_begin()` → 全部写 → `_commit()`，异常 `_rollback()`）。因此「落消息成功但标记没写」这条会重复投递的中间态**在构造上不可达**，不需要补偿路径。

**24 小时窗口**：`≤ 24 小时` ⇒ 补投；`> 24 小时` ⇒ 只写标记。边界值归「补投」一侧（唯一归属）。

**文案分档（C21）**：`|投递时刻 − 到期时刻| ≤ POLL_INTERVAL_SECONDS` ⇒ `system.reminder.fired`；否则 `system.reminder.fired_late`。**两个契约共用同一个常量。**

### D4. 调度 seam 与精度（C8 / C9 / C10）

见 §Seams。三条实现要点：

1. **装配点唯一**：`create_app`（`api.py:303`），注入点在 `:321-328`，与既有 `scheduler` / `seam` 同族。
2. **关停顺序**：`api.py:331-342` 的顺序是「`shutting_down.set()` → `orchestrator._scheduler.shutdown()` → `database.close()`」；新线程必须收口在 `database.close()` **之前**。
3. **精度上界 = 轮询间隔 = 30 秒**，写成 `POLL_INTERVAL_SECONDS` 常量 + 一条单元断言；行为测试走注入时刻，**一行都不真等**。

### D5. 读路径（C20）

`_reminder_payload`（`db.py:1330-1339`）加两个键：`fired_at`（原样给出，`null` 或 UTC 串）与 `state`（后端派生）。`REMINDER_SELECT_SQL`（`db.py:563-565`）用的是 `r.*`，因此加列**不需要**改这段 SQL（实施票需核对）。

`state` **不落库**：它是 `fired_at` + 到期时刻的纯函数，在 payload 组装处算。这条保证它不会变成 D4 否掉的「第三态」。

## Testing Decisions

### T1. 什么算好测试

只断言**外部可观察行为**：HTTP 读数（`GET /api/reminders` 的 payload、消息条数、未读、预算、轮次结果）、库的终态（`schema_version`、列清单）、迁移报告 stdout、进程退出码、`git diff`。**不**断言私有函数、SQL 文本、注册表内部表示。

理由：内部实现（轮询怎么起线程、`state` 在哪一步算、SQL 怎么写）应当可以演进而不重写测试。这条与既有 `app/tests/test_reminders.py` 的开篇声明同源（"只断言**外部可观察行为**……测试不连数据库、不读表结构"）。

### T2. 唯一测试 seam：**可注入的到期投递器**（C8）

- **接缝**：投递器的窄接口——喂一个时刻，拿到「这一批的投递后果」；后果的一切可观察痕迹都经**既有 HTTP 读数面**断言（消息流、`/api/reminders`、`/api/workspace`、`/api/channels/{id}/budget`、`/api/channels/{id}/round-outcomes`）。
- **为什么它是最高且最少的那个**：本能力的用户契约就是「到点会发生什么」，而「到点」的唯一可注入输入是**时刻**。`create_app` 的注入点（`api.py:321-328`）已经是**既有**接缝——既有测试用 `ManualScheduler` / `ScriptedAgentSeam` 在同一个函数上注入（`app/tests/conftest.py:42-46`、`app/tests/scripted.py` 的 `ManualScheduler`）。本能力沿用同一个注入点、加一个参数，**不新开第二个**。
- **`POLL_INTERVAL_SECONDS` 的落地**：一条**单元断言**（`== 30`）+ 注入时刻的行为判据。**轮询间隔不作为行为测试的对象**（C9 判据 3 用实测墙钟耗时反证「没真等」）。
- **被否的接缝与代价**：
  1. **真实后台线程 + `sleep` 等待**：慢、不稳、且 C9 明确禁止（H4「任何测试不许真等 30 秒」）。
  2. **直接调私有投递函数**（不经 seam）：把测试耦合到函数名与签名；且看不到「装配点是否真的接上了」。
  3. **`GET /api/reminders` 作为 seam（读路径即触发）**：这正是 D8 否掉的方案——它让「到点」变成「有人读才有」，与 C1 的「后端持有事实」直接冲突。
  4. **迁移侧另开一个 seam（读 `STEPS` 注册表）**：`STEPS` 是内部表示；C11 的判据（链连续性）已在 CLI 接缝上可观察（既有 `app/tests/test_migration_chain_guard.py` 的体例：真实子进程 + 解析报告步骤表）。**不新开。**
- **既有接缝的维护（不算新增 seam）**：`app/tests/test_reminders.py` 里断言「旧形状 `HH:MM` 合法」与「`date` / `repeat` 键被拒绝」的用例需要随 C4 更新——那是既有 `client` 接缝上对**契约变更**的同步，不是新 seam。

## Out of Scope

**每一条都给理由。前五条是设计票里显式被否的方案**（连同代价）。

1. **重复提醒（每天 / 每周 / 每月）。** 理由：需要维护 `next_due` 并与补投策略纠缠（错过 3 天要不要补 3 次？）；本仓**已经有**任务承载「重复做一件事」（`CONTEXT.md` **任务** 是可变行 + 状态机），给提醒再加一层重复语义会让「提醒 vs 任务」的边界消失。被否时登记的代价：用户说不出「每天早上 9 点」这类周期性请求，得每天手动设一条。
2. **到点唤醒归属频道的 Agent。** 理由：由结构事实（`notify` 必须先有一条已落库的消息，`orchestration.py:183`/`:190-191`）它**必然包含**本能力的「落消息」，额外代价是每一次提醒消耗一次 **agent→agent 跳**（ADR-0002 的三跳上界，8 条提醒就能吃掉一个世代的预算）；`channel_id` 为空时根本没有唤醒面；而且**唤醒是注意力不是命令**（`CONTEXT.md` **唤醒**），「到点提醒我」不需要任何人的反应。被否时登记的代价：提醒只是一个通知，不会带来 Agent 的后续动作。
3. **新增时区列（每条提醒带自己的时区标识）。** 理由：为**单用户本机**场景新增一列 + 一档界面 + 两份 i18n，收益为零（本仓没有多时区用户）。被否时登记的代价：**跨时区搬数据目录后到期语义会漂**——这条已在 C7 与 ADR-0017 §二显式记账，是采纳「本机本地时间」的代价栏，不是遗漏。
4. **把 `channel_id` 改成必填。** 理由：会破坏已发布的写路径契约（「空工作台也能设提醒」是当前合法状态，`db.py:386` + `test_reminders.py` 已有无归属用例），且存量无归属行没有自然归宿。被否时登记的代价：C2 的显式分叉必须一直存在——同一能力有两种可观察行为。
5. **给提醒造专用 target / 自动建一个「提醒」频道 / 就近落到 owner 最近活跃频道。** 理由：前两者推翻 ADR-0012 的「不新增 target」（ADR-0017 首段载明该条**仍有效**）；第三者让落点取决于运行时状态，「我 9 点的提醒落进了哪个频道」变成要查才知道的事。被否时登记的代价：无归属提醒的到点只能是一个行上标记，人类面必须能读到它（C20 因此成为必须）。

以下为本票范围内**明确不做**的事项：

6. **本票不写任何生产代码或测试。** 理由：本票是规格票，门禁 `G-spec`；票面 Constraints 明写「不许写任何生产代码或测试」「不 bump `SCHEMA_VERSION`」「不写 `MigrationStep` 代码」。改 `studio/index.html` 那句注释（C19）也属实施票的活。
7. **本票不新增 ADR、不改任何既有 ADR 正文。** 理由：ADR-0017 已覆盖本能力的全部决策；票面 Constraints 明写「ADR-0012 与其它既有 ADR 正文一字不改；不新增 ADR」。
8. **本票不碰 `CONTEXT.md`。** 理由：上游 PR #108 已把**提醒**改新口径、**系统事件消息**加第四来源、新增**到点**词条（实测 `CONTEXT.md:76-81` / `:295-297` / `:299-301`），**无词条缺口**；票面又禁止重排既有词条。因此最安全的处置是**零改动**。
9. **本票不在 tracker 上创建实施票。** 理由：拆票是 `to-tickets` 的活。本规格只给**切分建议**（下一个不编号小节），不建票、不打标签、不挂依赖。
10. **不提供「手动立即触发一次投递」的人类面入口。** 理由：这是给测试用的注入点，不是给用户的按钮；为一个单用户本机场景新增一档操作面（`CONTEXT.md` **工作区设置** 明写本轮只有明确列出的档位），且它会让「到点」这件事出现两个人可以按的按钮（进程时钟 + 用户），事实来源分叉。
11. **不做提醒的「稍后再说 / 贪睡」语义。** 理由：它需要一个新的可变状态（贪睡到几点的第二时间字段）与一条新的调度路径；本仓同族纪律是「状态在行上、历史不可丢」，而贪睡会把 `time` 与 `fired_at` 的关系变成三元的。**这不在设计票的授权范围内**，属新决策。
12. **不做提醒的批量 / 清理 / 归档策略。** 理由：既有 `DELETE /api/reminders/{id}` 已够「想清掉就手动删」；引入自动清理会新增一条「什么算过期」的策略，而本能力刚把「已错过」定成**呈现**（C20 的派生值），自动删会让那个呈现永远看不到。
13. **不改 `system` 消息的既有口径。** 理由：不计未读（`db.py:496-502`）、不进搜索（`db.py:599`/`:610`）、不唤醒不耗预算（`orchestration.py:205`）四条都是**继承**，本能力不给 `system` 造任何例外（C3）。
14. **不做提醒的成员面适配（Agent 不经 HTTP 读提醒）。** 理由：提醒是**人类面**的备忘，`CONTEXT.md` **成员面**的输入里没有它；把它塞进成员面会给每个 Agent 一轮额外上下文，而本能力已决定**不唤醒** Agent，也没有任何一轮会用上它。
15. **不改历史取证面。** `app/specs/issue-60-spec.md`、`app/specs/issue-68*` 里「提醒不落消息」的口径**故意不改**：它们记录的是当时那次交付的口径，改写会让「当时为什么这么定」消失（与 ADR-0012 不改正文同一条理由）。

### N3. 未核实项（不用推测补齐）

- **本机时区的 DST 行为**：C7 依赖「本地时刻 → UTC 瞬时」这一个换算方法。该方法在夏令时切换日的具体行为（不存在的本地时刻 / 重复的本地时刻）属**实施票的机制问题**；本规格只要求「换算方法只有一个落点」，不裁定它的 DST 策略。
- **轮询线程的线程模型**（daemon 与否、异常后是否自杀重启）：属实施票的机制问题。本规格只要求 C10 的外部可观察判据（正常退出、不留孤儿线程、关库后不访问库）。
- **`state` 在「已过点但仍未投递」这一瞬态下的取值**：本规格定为 `pending`（C20 的规则表第 2 行）。这个瞬态在有后台线程时通常只有毫秒级，但它是**可判定的**——不是推测。
- **真实旧库样本上的改写行数**：C14 只要求「报告的 N = 实际改写行数」，可核对性靠造行测试证明；本规格不声称某个真实库有多少行要改。
